# 9. History

Everything is kept and readable.

- **Messages:** one table of conversation items per project: user ⇄ foreman turns (a user message, §4.2 item 3, is kept with author `user`), foreman tool calls and their results, worker task specs and results, questions and answers, reviews, notifications. A job's `discoveries` (§5.4) stay with that job's result message. A task's record carries its skills by name and digest and the digests of the role texts it was given (§5.9, §5.10), so a recorded prompt is reproducible. `brigada history [--plan N|--task N|--job N]` shows them as one timeline.
- **Transcripts:** after every job, the runner uploads the session's full transcript (the CLI's own event log) to the engine as an artifact, linked from the job. The foreman's chat transcript is archived the same way after each attach and each headless turn.
- **Plan filter:** the history read takes a plan filter beside the task and job ones: it returns the plan's own events (`plan_created`, `plan_amended`, `plan_reviewed`, `plan_done` and the like, which carry the plan in their payload, since the events table has no plan column) and the events of its tasks and jobs, with the messages those events produced. It composes with the task and job filters, the `since` cursor pages it and `last` reads its newest page. `brigada status --plan N` reads the newest items of the same timeline as its recent transitions.
- **Events:** an append-only event log is the backbone. Messages and transcripts reference events. A job's lease event carries the task's `tool_grants` (§6.1) when it granted any, the template version and the digests of the instruction and skill texts its prompt was composed from (§5.9, §5.10), and `brigada history --job N` shows them shortened. A `plan_amend` note set, replaced or cleared records one `task_note_set` event with the note verbatim (empty when cleared) and the caller, the foreman or the user; delivery writes no event of its own, the note leaving the task's status line and appearing in the job's prompt (§6.2). A pick's `job_agent_picked` event is the placement decision in words — the pick, the chosen agent's score, cost and draw, the requested and served tier, the review's policy, placement and fallback, a pin or session, the exclusions, and every dropped candidate with the reason — and a `job_cap_held` event names the layer a job waited on (§8, §8.1); `brigada history --job N` and the MCP bridge's history read the same words for both.
- **Land batches:** not implemented (§7.1): brigada lands one task per land job and records no batch events. In the design, batch events record formation and ordered membership, lease and fence, each publication attempt with predecessor and final heads, gate observations and baseline evidence, and completion. Per-member events link task, plan and batch: squash/check commit and artifact, landing recorded and push state, parking reason or environment cause, dropped dependency, hold, approval or rejection, and reservation release. A drop is a history outcome, never a landing record. Replayed reports do not duplicate events or records.

  Gate events preserve the verbatim first line, checked-head evidence and suspect list or unknown marker. Publication records retain the batch heads and members used for attribution (§7.1), including waiting prefixes released across batches; losing that evidence through retention makes suspects unknown, never reconstructed from git history.
- Retention is the config file's `retention_days`: messages and artifacts older than that many days are pruned on the engine's sweep, and the event log never is. The default, 0, keeps everything.
