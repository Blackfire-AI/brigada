# 16. Open questions

1. Gemini CLI's headless resume support.
2. The foreman's wake-up budget defaults.
3. `tool_call_cap_minutes` defaults per class.
6. Whether an explicit no-check task (`check: none`) is allowed at all (§6.1).
7. Cross-project plans: out of scope for the coordinator (§4.6); revisit only with a use case. A project is one repo URL with its own foreman, and a plan belongs to one project, so a change spanning `api` and `web` is two plans the user coordinates. Either one foreman over several projects, or a plan whose tasks each name a repo. Either keeps product §5 rule 4 (repos are addressed by URL, never by path or name), and either must settle whose foreman owns the plan, what the foreman token's project wall (§12.1) allows, and how a task waits on a branch of another repo. Read-only context from another repo for a task that still changes one repo is the smaller thing in §5.8, and does not answer this.
8. Setup and its cache (§5.7; with 15 minutes, 30 days and 3 entries per repository, a copy per job, and no clear command, all open to revision): the default `timeout_minutes`; the age and size bounds and the eviction rule of the cache; whether to share an entry read-only instead of copying it per job; the name and scope of the clear command; whether the key should also cover the toolchain version.
9. Extra repositories (§5.8): write access to one, which is a cross-repo question (item 7) and not settled by the read-only field; detecting a worker that changed a read-only checkout; credentials for a repo the runner's own cannot reach; whether to resolve a moving ref to a commit at task creation instead of at the job.
10. Landing (§7.1): landing a whole stack in one command by hand beyond the dependency chain given by task ids (for example `--plan <id>`, or a stack across plans); a time bound for the check land runs; `--onto` a branch that is not checked out; the family-to-address table for the co-author trailer beyond the five shipped families, and a display name for the trailer — no adapter exposes one, so the model id, or the family, stands in.

    For the `land` job: the names of the land and push approve commands; whether a runner must advertise landing separately from its adapters; how the job's clone of the target is kept and pruned; landing by hand a task without an `approve` verdict (a hand review); whether `after_land` also runs for the hand-driven command.
11. Instructions and skills (§5.9, §5.10): tuning the 8192-byte and 4096-byte bounds and the 16384- and 24576-byte per-prompt bounds; a bulk "apply to tasks already created"; a plan-time/every-turn split of the foreman text if its bound ever binds; moving the coordinator's text (`internal/foreman/coordinator.md`) out of the binary, which is wired in a parent folder and owned by no project; which of the eight provisional default skills the record keeps. Answered: the foreman is handed the project's text in its wake prompt, and reviewers have a text of their own.
12. Tiers and effort (§6.1, §8, §13.1): the tier table's patterns and their staleness as vendors rename models; whether brigada's four effort levels should reach a CLI's extremes (`xhigh`, `ultra`) or those stay reachable through an agent's own `effort=` only; the per-account default caps and the tasks-at-once default; whether `--max-parallel` unset should keep meaning one job at a time once init sets it; how a tier bump should count against the restart cap when the bumped attempt fails too.

Note for remote: §6.4 gives the engine push credentials to user repos; that is fine for local use and needs re-examination for remote or multi-user use.
