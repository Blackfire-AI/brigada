# brigada: design

Status: **v0.1, approved** 2026-10-12 after a cross-model review, as the Go design baseline. What and why: [product.md](product.md). Terms: [glossary.md](glossary.md). It supersedes the design of the earlier Python implementation ("v3.2"), which stays the reference for what is ported (§14). Tags: **(decided, date)** is settled; everything else is a proposal. A decision is a direction for the design, not a claim that the code supports it yet: §4.6, §13.1 and the "Your own session" phase of §15 are designed, not shipped.

## 1. Principles

1. **The foreman decides; the engine enforces.** Judgment (planning, answering, re-planning) is an LLM worker (the foreman, §4). Mechanics (queues, leases, eligibility, caps, routine retries) are deterministic Go code.
2. **The engine is the mailbox.** The foreman and the task workers never talk directly. Every message goes through the engine, and every message is kept (§9).
3. **No state lives only in a session.** Any session, the foreman's or a task worker's, can die at any moment; the engine and the plan file hold everything needed to continue.
4. **Prompts: templates plus verbatim data.** The engine may compose a prompt only from fixed, versioned templates plus verbatim data (a task spec, review text, check output, a foreman answer). Verbatim data is always wrapped in explicit data delimiters, so one worker's output can't pose as instructions to the foreman or another worker. Anything that needs judgment goes to the foreman. This relaxes Python v3.2's "the server never builds prompts", which assumed no routine fix rounds in the server. **The one other input that is not data is a user message** (§4.2 item 3; proposal, 2026-10-14): the user's own words, sent through the client API, reach the foreman as a request to act on, in their own section and never inside an event's. Only a `client` or `admin` token can send one, which stops a worker or a foreman turn from *posting* one. Delimiters stop the rest: in the foreman's prompts the engine neutralizes the delimiter tags (`<event>`, `</event>`, `<user-message>`, `</user-message>`) inside any verbatim data it wraps, so no data can close its section and open another; the worker prompts' delimiters get the same treatment (backlog).
5. **Remote-ready** (product §5): clients only through the API, runners only through the lease protocol, tokens everywhere, repos by URL, self-contained state.

## 2. Processes

| Process | What | Local (launch) | Remote (backlog) |
|---|---|---|---|
| `brigada` (client) | CLI: chat, ask, status, history, stats, cancel, restart, review, budget, recover | your terminal | any device |
| engine | API, store, rules, dispatcher, foreman wake-ups | background process, started on demand | a server |
| runner | leases jobs, runs agent CLIs, runs checks | same host, separate process | any host with logged-in CLIs |
| foreman session | your harness session (mode A, §4.6; decided 2026-10-16), or a brigada-owned headless session for wakes; `brigada attach` (§4.2) remains the fallback for a harness that cannot host the tools | opened by you in your repo; the headless one is started by the runner | same |
| worker session | a **worker**: one instance of an official CLI, a harness plus a model, running headless. A task worker runs one task; the foreman is a long-lived worker (§4) | started by the runner | same |

The client, engine, runner and the MCP bridge (`brigada mcp`, §12.2) are the one `brigada` binary in different roles. The harness CLIs are the vendors' own official binaries, which brigada drives headless or which host the bridge as a child process; they are never the `brigada` binary.

## 3. Communication: the engine as a mailbox

```
 you ⇄ foreman ──tools──▶ engine ◀──lease/result── runner ──▶ worker CLI
            ▲                │
            └──── events ────┘  (judgment events wake the foreman)
```

- **Down:** the foreman calls tools (create a plan, add tasks, answer, restart). The engine turns ready tasks into jobs; a runner leases a job and starts the worker.
- **Up:** a worker can't message anyone mid-run. It ends its job with a structured result (§5.4). The runner adds the check result and progress data. The engine records it as events.
- **Routine events are handled by rules, judgment events go to the foreman:**

| Event | Handled by | Action |
|---|---|---|
| check failed, rounds left | rule | fix round: same session, template + check output |
| review "changes", rounds left | rule | fix round: same session, template + review text |
| transient error (CLI crash, network) | rule | retry the job, capped |
| a dependency is done | rule | the dependent task becomes ready |
| quota limit hit by a worker | rule | cool the account (§8); re-dispatch to another eligible agent as a **fresh** attempt (on the task's next `-r<n>` branch, §6.4) carrying the previous job's summary if it produced one, else its last progress events (a session can't move between agents), counting toward the task's attempt caps; no eligible agent in any tier (§8; decided 2026-10-19; shipped) → after the queue timeout the task parks and the user is notified when notifications are enabled (§10) |
| worker `needs_help` | **foreman** | answer → next job on the same session, or re-plan |
| task out of rounds or retries | rule, then **foreman** | (decided 2026-10-19; shipped) the tier escalation of §8 first, while the task is below heavy and its attempts are not spent; then the foreman: re-plan, switch agent, split, or ask the user |
| worker stalled (§5.6) | **foreman** (decided 2026-10-12: always; no automatic nudge) | restart with a new instruction, switch agent, or ask the user |
| plan above the approval limit | **user** | approve, edit or reject (§6.3) |
| foreman limit hit (§4.4) | **user** | wait, switch foreman, or continue without it (decided 2026-10-12) |
| job finished with `discoveries` (§5.4; proposal, 2026-10-14) | **foreman** | read them on the next turn as verbatim data in delimiters (§1.4); then `plan_amend`, put the fact into the spec of a task that hasn't started, or ignore it |
| plan done | rule | notify the user directly (§10); the foreman may add a summary on its next turn, skipped when it's `limited` or out of budget |

## 4. The foreman

**The brigada-owned headless foreman is a worker** (decided 2026-10-13). The *foreman role* is logical: the project's single decision authority, exercised either by this headless worker or, in mode A, by the user's own interactive session (§4.6), which brigada does not run and which is not a worker. The rest of this section and §4.1 describe the headless worker. A worker is an instance of a headless harness plus a model (§2); what it does comes from its instructions, permissions and lifecycle. The foreman runs on the same machinery as any other worker: an official CLI driven through the same adapters (§5.2), with headless resume, transcripts, quota and limit detection, and stall handling. A headless foreman turn is a job (kind `foreman`, §11). Where task-specific rules say "worker" (§3, §5.3–5.5, §7, §8), they mean a task worker: the foreman job is excluded from dispatcher scoring, quota re-dispatch, review routing and the runner's checks; its harness and model are fixed by the user, and its limit goes to the user (§4.4). It differs from a task worker in three ways:

- **Instructions:** the foreman instructions, where a task worker gets the worker instructions (the result block of §5.4, `needs_help`, check discipline, no dispatch tools).
- **Permissions:** the `foreman` token, scoped to its project (plans, answers, restarts), where a task worker runs under the runner token with no plan scope (§12.1).
- **Lifecycle:** one long-lived resumable session per project (`foreman:<project>`), with harness and model chosen by the user, woken by events and attachable. This is the brigada-owned session: in mode A (§4.6) the user's own interactive conversation is a different one, and only the project's foreman *authority* is shared between them. A task worker's jobs all belong to one task and one session (`task:<id>`), its agent picked by the dispatcher.

Task workers never get the foreman instructions. A task worker that thinks its task should be split returns `needs_help` with a proposed split, and the foreman decides.

### 4.1 What it is

- An official CLI session, **harness and model chosen by the user** (decided 2026-10-12), e.g. Claude Code with a given model, with brigada's MCP tools (§12.2) and the foreman instructions (a versioned file shipped with brigada). Since 2026-10-16 the user's own harness session can be the foreman too (§4.6); this section and §4.2 describe the brigada-owned session.
- One foreman per project (repo). Its session is a **resumable session key** `foreman:<project>` (decided 2026-10-12: option B). The harness must support headless session resume (claude, kimi, zcode: yes, verified in the Python implementation; codex: `exec resume`; gemini: to verify). Setup refuses a harness without resume.

### 4.2 Two ways in, one session

This is the brigada-owned session: headless wakes and `brigada attach`. Attach is the fallback for a harness that cannot host brigada's tools in the user's own session (§4.6); item 1's same-session rules (write-back, "the same session") hold there, and do not describe mode A.

1. **You chat:** `brigada` attaches you to the foreman session through the harness's own interactive resume.
   - **Attach acquires the key's live slot first** (one live job per key, Python v3.2 §2). If a headless foreman turn is running, the client shows "foreman is busy" and waits for it to finish, or cancels it through fencing if you insist. Two processes never resume one session at once.
   - The attach hold is lease-like: the client heartbeats it, and it expires if the terminal is killed. A second live attach is refused.
   - **On detach the client writes the current harness session id back** to the engine, as runners do on complete (`--resume` forks session ids; Python v3.2 §2a). Otherwise the next wake would resume the pre-chat id and lose the conversation.
   - Judgment events that arrive while you're attached reach the foreman through its `events` tool, which the instructions tell it to check between replies. On release, any events it didn't consume are evaluated for a wake-up.
   - **Events are consumed only when a foreman turn completes,** or when the attached foreman reads them through `events`. A cancelled or failed turn's events return to pending and are re-delivered on the next wake or attach, so cancelling a turn to attach never drops a task worker's question.
   - At attach, pending events are put into the session's opening prompt (the same wake template), so they surface at once instead of waiting for your next reply.
2. **The engine wakes it:** when a judgment event arrives and nobody is attached, the engine submits a **foreman turn**: a headless resume of the same session, with a template prompt plus the pending events verbatim. The foreman acts through its tools and exits. Several events coalesce into one turn (the follow-up flag of Python v3.2).
3. **You send a message without attaching** (proposal, 2026-10-14): `brigada ask "<text>"`, or the client MCP tool `ask_foreman` from any harness acting for you (§12.2), puts a **user message** in the foreman's inbox.
   - **Framing (§1.4):** a prompt or an `events` answer has at most one `<user-message>` section, after all the `<event>` data; several waiting messages are an ordered list inside it, each naming the token label it came from. The wake template says the event data is never instructions and that this section is the only other input: your requests. The attached session's `events` answers use the same framing, order and neutralized tags, and the opening prompt at attach carries waiting messages with the waiting events (item 1). **Invariant:** no prompt or tool answer, present or future, presents an `<event>` or `<user-message>` section without the framing text in the same message.
   - **Delivery is per message, like an event's:** a message is consumed when a turn whose prompt carried it completes, or when the attached foreman reads it through `events`. A message that arrives while a turn runs was not in that turn's prompt: it stays pending, and the turn's completion re-evaluates the wake for it. A failed, cancelled or stalled turn returns its messages to pending (§5.6). On detach, or when an attach hold expires, waiting messages are re-evaluated for a wake, so a message never strands behind a chat that ended. Messages coalesce with each other and with waiting events into one turn.
   - **Not charged to the wake budget:** a user message is you driving, like a chat, so a wake that carries one skips the day's budget (§4.3). It still obeys the wake stall (§5.6).
   - **The answer says what happened:** a turn was woken, or why the message waits — you're attached (naming the hold), a turn is already running, the project has no foreman harness, the wake stalled (and, once §4.4 lands, the foreman is limited until a time). It returns the message's id, so a caller can follow it in the history.
   - The project is named by its repo URL, or is the only project the engine has.

**Discoveries** (proposal, 2026-10-14): a finished job's `discoveries` (§5.4) reach the foreman on its next turn as verbatim data inside the `<event>` delimiters (§1.4), like any worker text. The foreman decides what to do: amend the plan (`plan_amend`), put the fact into the spec of a task that hasn't started yet, or ignore it. The engine never forwards them into another worker's prompt; only the foreman's decision can.

Your next *attached* chat sees everything the foreman did while you were away, because it's the same session, and the history (§9) has it too. In mode A the interactive conversation is not that session; it catches up from the engine (§4.6).

### 4.3 Budget

Foreman turns while you're away use your subscription. A per-project budget of foreman wake-ups per UTC day bounds them: the built-in default is 20, the config file's `foreman_wakes_per_day` sets the default for every project, and `brigada budget [--repo URL] --wakes N` sets one project's budget for the day — a local project setting (`foreman_wakes_per_day` through the settings path, refused in the shared project.yaml, which names local-only keys by that rule). When it runs out, judgment events wait for you, and visibly: one `foreman_wake_budget_spent` event per project per budget window records the count and the window's end, a notification is raised (§10), and the needs-you queue in `brigada status` shows the entry — the use, the reset time, the events waiting — while events wait, gone when nothing waits or the budget is raised or the day resets at UTC midnight. Raising it re-evaluates the waiting events' wake at once. A wake that carries a user message (§4.2 item 3) is not charged: the budget bounds the foreman reacting to events on its own, not you asking it something, which is as attended as a chat. (The per-plan task-worker-minutes budget of the earlier design has no enforcement of its own yet; `brigada budget` carries the wake budget alone.)

### 4.4 When the foreman hits its limit

The runner detects the limit-hit error from the foreman's CLI. The engine marks the foreman `limited(until)`, or `limited(unknown)` when the error carries no reset time, stops waking it, and **notifies the user** (§10), who chooses: wait for the reset, switch the foreman's harness or model (the new session rebuilds its context from the engine, per product §4's kill-and-rebuild test), or let approved plans continue without it. Routine rules keep working throughout. When the same account also serves task workers, a foreman limit-hit cools that account in the dispatcher (§8), and a worker limit-hit on that account stops foreman wakes until the reset.

### 4.5 Capacity

(decided 2026-10-13) The foreman instructions tell it to check `capacity` (§12.2) when it plans, and to use it to choose how wide the task graph is, when to sequence instead of fanning out, which tasks can wait for a cheaper agent, and to give honest time estimates ("3 tasks now, 2 after the reset at <time>"). The engine stays binding: if the foreman's view is stale, the dispatcher queues the extra tasks and never exceeds a cap (§8.1). The foreman decides; the engine enforces (§1).

### 4.6 The foreman in your own session

(decided 2026-10-16: direction set by the maintainer; settles §16 item 4.) Engineers do not want a separate CLI chat in a scratch folder. They want the harness they already use to be the foreman, or one session of it to coordinate several projects' foremen. Everything below is design: none of it is implemented, and every mechanism marked **(proposal)** waits only for the harness facts it depends on, as recorded in the verification at the end of this section: a fact still marked (not verified) blocks the parts that need it, not the rest.

#### Mode A: your session is the foreman

`brigada init` (§13.1) registers brigada's MCP server for that repo and installs the foreman instructions where that harness reads project instructions (a skill, an MCP prompt, or both). Registration is harness-specific (see "What the facts allow" below): Claude Code takes it in the shared project scope; Codex has no verified project-scope path, so init prints a user-level command for the user to run. The user opens the harness in the repo and talks. The session calls `plan_create` and the other project-scoped foreman tools (§12.2); results arrive as events, through the `events` tool or a harness-native channel if one is verified, else by polling.

**Two conversations, one authority** (decided 2026-10-16). Headless wakes use a SEPARATE brigada-owned resumable foreman session (`foreman:<project>`, §4.1), not an automatic resume of the user's conversation. The engine journal is the handoff. Why: no dependency on a vendor exposing a portable resumable id for the user's session, and no unattended execution of the user's broader interactive permissions and conversation. The cost, stated plainly: two conversations and no automatic chat-transcript continuity. Decisions must be durable in the engine before a turn ends, and an interactive return catches up through `status`, `history` and `events`, not through memory of a chat. The project has one *logical* foreman authority at a time; it is exercised by one of two distinct conversations (the user's, or the headless one), never both.

**Identities** (proposal). Three things must not be conflated:
- **Bridge instance:** an id the `brigada mcp` process mints at start. A stdio MCP process is not proven to live exactly as long as one conversation (it may be pooled, restarted or shared by forks), so the id names a process, nothing more.
- **Hold:** the engine-minted, exclusive claim on the project's live slot (below), with a monotonic **fence**. This, not any conversation id, authorizes mutations.
- **Harness session metadata:** separate fields, filled only with values that a documented harness channel supplies and the verification below has confirmed (`harness_session_id`, source, observed time). An identifier first seen in a tool call is stored apart as `session_hint`: display and diagnostics only, never proof of ownership or resumability. A session id, and any other request metadata, is a selector and an observation, never a credential: it cannot authorize a mutation, and a hook or bridge that quotes it still acts only through the bound bridge instance, the hold credential and the fence. When the harness exposes no session id, mode A works on the bridge and hold identity alone. brigada never invents a conversation id and never uses one to resume the user's CLI; it does not resume the user's conversation at all.

**Startup, presence, project selection** (proposal). The shared registration carries no repo argument (`brigada mcp --foreman`), so the bridge selects the project itself. **Claude Code:** from the repository containing the bridge's cwd, which is the session start directory and may be a subdirectory; the bridge discovers the git root and reads its origin, and does not assume `CLAUDE_PROJECT_DIR` is the root. **Codex:** from the workspace remote URLs in the first `tools/call` request metadata (verification item 4). Both normalize the URL by the canonical resolution of §13.1. An explicit repo URL (`--foreman <repo URL>`, §12.2) stays an explicit override, subject to the same canonical project checks. No match, an ambiguous one, or several workspace remotes with no single canonical match selects nothing and never widens the credential's project scope: tools answer with an actionable error naming `brigada init`, and the bridge never guesses a project. It then registers **presence** with the engine: project, bridge instance, harness, label. Presence is informational: `brigada status` shows "your session is connected, not holding". It carries no authority and does not hold the slot, and its absence changes nothing (headless wakes work without any mode A session).

**The hold** (proposal). The key's live slot (glossary) has one holder at a time. Mode A adds an interactive holder beside the headless turn and the attach (§4.2):

| Slot state | Entered by | Left by |
|---|---|---|
| free | start; yield; hold expiry; turn end; detach | a wake, `hold_acquire`, or an attach |
| interactive hold | `hold_acquire`, on the session's call | `hold_yield`; liveness failure; inactivity expiry; forced release |
| headless turn | a wake, only from free | turn end (§5.6 time caps apply) |
| attach (fallback) | `brigada attach` (§4.2) | detach; expiry |

- **Acquire:** the first foreman-tool call that needs authority (or the instructions' explicit `hold_acquire` at the start of a working turn) acquires the hold and returns a **state digest**: plan and task states, pending events and messages, and decision notes since this session last held. Acquire is refused while a headless turn or an attach holds the slot; the answer names the holder, its label and since when. A second interactive session on the same project is refused the same way, but only when it reaches the engine through a different bridge instance. **Shared bridges fail closed** (proposal): the credential and hold belong to one bridge instance, and brigada can tell two conversations apart inside one process only through verified per-call caller metadata (verification items 3 and 4). Without it, a bridge that may serve several conversations is treated as one holder: the bridge reports that it has seen traffic that cannot be attributed (for example concurrent calls that overlap, or a hold already in use when a new call arrives with a different `session_hint`), and then it drops the credential, ends the hold, and answers `hold_lost` with an explanation until the user reconnects with one conversation. Isolation is preferred over detection: where the harness can start one bridge process per conversation, init registers it that way, and each such bridge gets its own bridge-instance and hold identity, so no-session-id operation stays safe because the isolation comes from the process, not from a conversation id. Where a harness can only pool a bridge across conversations and offers no caller metadata, mode A is not offered for that harness (attach remains the fallback). A user-directed forced release goes through fencing, as for attach (§4.2).
- **Credential:** acquire mints the mode A foreman credential: project-scoped, tied to the hold, kept in the bridge's memory, revoked when the hold ends (§12.1).
- **Liveness vs activity.** Two separate clocks. *Liveness:* the bridge heartbeats the hold on a short lease, and a missed lease ends the hold. Heartbeats only show that the bridge process and its transport are alive: they must not reacquire a hold and must not extend exclusive authority past the activity bound. *Activity:* the time of the last foreman-tool call the session itself made that changes or consumes engine state (`plan_*`, `task_*`, `answer`, `ask_user`, `decision_note`, an `events` call that consumed something, `hold_acquire`). Empty `events` polls, `status`, `history` and `capacity` do not count, so a long-polling session cannot pin the slot. MCP cannot see whether the harness is thinking; a tool call is the only evidence there is.
- **Bounded inactive-hold fallback** (proposal; the activity definition above and these defaults are to verify before code): the hold expires after `hold_idle_minutes` without activity (starting default 15) and after `hold_max_minutes` regardless (starting default 240). A session that is merely slow loses its hold and meets `stale_hold` on its next mutation, which is safe and recoverable (below). The defaults are a guess and are open in §16.
- **Yield:** the instructions tell the session to call `hold_yield` at the end of a turn, after recording its decisions. Yield releases the hold, revokes the credential and re-evaluates pending events and messages for a wake. **Claude Code** (proposal, from item 6): init wires the project `Stop` hook to `brigada hold yield --session <id>`; the wrapper always exits 0 and logs locally, so a failing hook never breaks the user's turn. The hook's session id only correlates: a yield is honored only for the bound bridge instance with its hold credential and fence, so a stale `Stop` hook, or an old bridge with the same session id, cannot release a newer holder. **Codex:** yield is by instruction (`hold_yield`) until its hooks are verified. In both, the inactivity expiry and liveness lease remain the fallback, and a missing clean stdin EOF is never read as a clean release.
- **Open but idle:** a harness left open with no turn running does not block wakes forever. After a yield the slot is free; a session that never yielded (the model forgot, the user walked away) lapses at the inactivity bound. Until then wakes coalesce (events and messages stay pending, and the session sees them through `events`), so the worst delay is bounded by `hold_idle_minutes`.
- **Before a wake:** after yield or expiry the engine revokes the credential and bumps the project's hold fence *before* the headless turn is submitted. Old mutation authority is dead by then.
- **Stale calls:** a mutation carrying a revoked credential or an old fence is rejected whole (`stale_hold`) and applies nothing. A rejection is not recorded as a call's result for idempotency (§12.1). The bridge never retries it under a new hold and never replays queued mutations. The session must call `hold_acquire`, read the digest, and decide again, because the state may have changed under it (a headless turn may have amended the plan).
- **Crash and EOF:** stdin EOF or a signal on the bridge releases the hold at once, best effort (a headless Claude Code run was observed to end its server with no clean stdin close logged, so EOF is never relied on); a SIGKILL or a lost machine is covered by the liveness lease. A restarted bridge is a new instance and must acquire again.
- **Failed heartbeats:** the bridge retries inside the lease. If it cannot renew, it drops the credential and its tools answer `hold_lost` until `hold_acquire` succeeds. It does not assume the engine is merely slow.
- **Seen by the user when a headless turn owns the slot:** the session's mutating calls answer `foreman_busy`, naming the turn, its start and the events it carries; the instructions tell the foreman to say so, offer to wait, and keep to read-only tools meanwhile. `brigada status` shows the same. Turns are bounded (§5.6), and the forced release above applies if the user insists.

**Handoff is the journal.** Plan decisions are durable because they are made through engine tools. Reasoning not yet expressed as a tool call (why the user rejected an approach, a preference, what they are about to do) lives only in the private chat, which no headless turn can see. brigada does not capture private transcripts automatically; a mode A transcript is the user's harness's own and is not uploaded (§9). So the instructions require the session to record such things before it yields. `decision_note` (proposal) is a new foreman-set tool: it appends a note to the project's history (§9) under author `foreman-interactive`. Headless wakes receive notes as verbatim data inside the delimiters of §1.4, like any other worker text; a note is never a user message and never instructions. It fits the tool boundary: it only writes a message through the API (no direct store access, §12.1) and is subject to the same project scope, hold and idempotency rules as the other foreman mutations. The user's own words reach the foreman only as user messages (§4.2 item 3), whichever conversation holds the slot.

**Permission boundary.** The interactive session runs under the user's own harness permissions and edits as the user does. brigada cannot enforce that this user-controlled session never edits the repo; the foreman instructions say it must not, and init widens nothing. brigada does enforce its own side: the API role and project scope of the credential (a foreman credential cannot approve plans or touch another project, §12.1), and the restricted tool scope of its own headless foreman turns (the adapter's scope, §5.2: brigada's tools, no edits). Interactive turns are not charged to the wake budget, since the user is driving (§4.3); headless wakes are. If the user's own session or subscription hits a limit, that is theirs to notice: the hold lapses and wakes proceed on the foreman configured for the project (§4.4).

#### Mode B: a coordinator session over several projects

A session opened in a folder holding several repositories gets the **coordinator** tool set (§12.2) over every project the engine knows: list projects, ask a project's foreman, approve or reject plans, status and history across projects. Each project keeps its own foreman, in either mode, for plan mechanics: the coordinator never calls `plan_create` and never mutates a task graph. Projects are named by canonical repo URL (§13.1); a monorepo is one project. Cross-project plans stay out of scope: a coordinator sends separate requests, one per project, through `ask_foreman`, and each project's foreman plans on its own. Init in a non-repo parent folder registers the repositories it discovers, under explicit boundaries and a visible selection (§13.1).

Approval is the user's act. `plan_approve` and `plan_reject` use client authority, never a foreman credential, and take the plan id and the plan version the user was shown, so an amendment made after the user looked invalidates the call. The engine's "awaiting approval" is a result to present, not a permission: the instructions tell the coordinator to show the plan and wait for the user's explicit yes in chat, and an LLM must not turn that result into self-approval. The instructions cannot enforce that; the boundary that can is the harness's own per-call permission prompt, which init leaves on "ask" for these two tools and never pre-allows (verification item 8). In mode A the user approves through the client path (the `brigada` command, or a coordinator session), not through the foreman tools.

#### Required verification before any code

Each item is answered for **Claude Code** and for **Codex** separately and marked **(verified 2026-10-16, <harness> <version>)** or **(not verified)**. The verified observations come from a probe MCP server run by the maintainer on 2026-10-16 in a throwaway repository, using per-invocation flags and project-scope files only. ## 5. Workers and runners

### 5.1 Runner

- Registers with a runner token and advertises its adapters: harness, models, family, account label, classes it can take (product §5 rule 5). (decided 2026-10-19; shipped) An agent is one (harness, model, account): a runner offers several models of one harness as several agents, `--agent` once per model, with each agent carrying the tier of §8.
- Leases jobs (long-poll), heartbeats with progress, completes with a fencing token. Lease expiry plus fencing make crashes safe (Python v3.2's lease engine, ported with its tests).
- Materializes its own workspace: clone or fetch the repo URL with its own git credentials into a per-task worktree, and push result branches to the remote (product §5 rule 6).
- Starts each CLI with its working directory and its `PWD` set to its worktree (a foreman turn's scratch directory for a foreman turn), replacing the runner's own `PWD`, because some CLIs, opencode among them, read `PWD` before the working directory.

### 5.2 Adapters

One per CLI: build the headless command (fresh or resume), parse the CLI's event stream into progress events, detect limit-hit and auth errors, find the session id for resume. Copied where useful from Orchestrator.inc's Apache-2.0 adapters, keeping upstream license headers, carrying their NOTICE and marking modified files (CodexBar, if used, is MIT: same idea). The claude adapter's default worker scope allows exactly `go build`, `go test`, `go vet` and `gofmt` — the worker compiles and tests its own work as it goes; the runner still runs the check, so no new code reaches execution — and an agent config's explicit tool scope replaces the default (decided 2026-10-15).

### 5.3 The worker prompt

A fixed worker template (versioned) plus the task spec verbatim, plus the answer or feedback for follow-up jobs. The template tells the worker to end with the result block (§5.4). A project may add its own instruction text, injected as verbatim data in its own delimiters after the template's contract and before the task spec (§5.9; implemented).

### 5.4 Worker result contract

The worker's final message ends with one JSON block:

```json
{"status": "done" | "needs_help" | "failed", "summary": "…", "question": "…", "branch": "…", "discoveries": "…"}
```

`discoveries` is optional (proposal, 2026-10-14). It holds facts the worker learned that matter beyond its own task: an API quirk, a flaky test, a wrong assumption in the plan, something a later task will trip over. An absent or empty field means none. A review's verdict block (§7) and foreman turns don't carry it. Workers never message each other, and the engine never forwards discoveries into another worker's prompt on its own. Only the foreman's decision can carry them (§4.2).

A missing or malformed block counts as `failed` with reason `no-result`. The runner verifies the branch was pushed.

The contract binds task jobs (`work`, `fix`, `review`, §11); a review job's block is the verdict block of §7. A foreman job is exempt: its turn's output is its tool calls (§12.2), and ending without a result block is not `failed`. On `needs_help`, `question` carries the question or a proposed split of the task; the foreman answers it or re-plans through `plan_amend` (§3, §6.2), so the split needs no field of its own.

### 5.5 Checks run by the runner

After the worker exits with `done`, **the runner runs the task's check** in the worktree, not the worker. Exit code plus the output tail are the check result. That keeps the outcome record honest (a self-reported check would bias it).

### 5.6 Stalled workers and restart with a new instruction

Workers sometimes get stuck: alive, but making no progress (seen in practice).

- **Detection:** the adapter turns the CLI's event stream into progress events (tool calls, messages); the runner sends the time of the last one in each heartbeat. **Stalled = 10 minutes with no activity at all** (decided 2026-10-12; `stall_minutes`, configurable). A tool call in flight (a long build or test run) suspends the clock, bounded by its own `tool_call_cap_minutes` per class (default 30). Stalled, or the class time cap reached → the runner kills the process tree and completes the job with the outcome `stalled` or `time_cap`; either ends the job in the terminal `stalled` status, and the result block names which, with the last progress events attached.
- A stalled job **always goes to the foreman** (decided 2026-10-12); there is no automatic nudge.
- A stalled foreman turn is killed and completed like any stalled job, but never routes to the foreman itself: its unconsumed events return to pending and are re-delivered on the next wake or attach (§4.2), the engine may wake it again while wake-up budget remains (§4.3), and the user is notified when it stalls repeatedly or the budget runs out.
- **Restart:** `restart(task, instruction, mode, agent?)` cancels any live job and creates a new job on the same task with the new instruction.
  - `mode=resume`: same session, the instruction appended (the worker keeps its context);
  - `mode=fresh`: a new session, the instruction plus the previous job's summary and last progress (for a worker stuck in a loop);
  - optional `agent` to move the task to another agent.
- **Who restarts:** the foreman (a judgment event), or the user directly: `brigada restart <task> -m "…" [--fresh] [--agent …]`. A restart is a new attempt on the task and counts toward its attempt caps. A resume that fails (the session is gone or forked) restarts fresh in place, as in Python v3.2 §2a.

### 5.7 An environment for checks and reviews (proposal, 2026-10-16)

A worktree is a fresh clone (§5.1), so it has no `node_modules`, no Python virtualenv, no downloaded modules. A check such as `npm test` or `pytest` fails there for want of dependencies, not for want of working code. Today the only ways out are a check that installs dependencies on every job, or one that names a path on the host, which breaks product §5 rule 7 (a check is repo-relative and host-independent, because it is recorded as task data). Neither is acceptable, so the environment becomes a step of its own. Implemented (see *Implemented* at the end of this section); the nested spelling below is the design's, and schema 1 of the file spells it flat.

**`setup`.** A project may set `setup` in `.brigada/project.yaml` (§13.1), a repo-relative command with optional fields:

```yaml
setup:
  command: npm ci --cache "$BRIGADA_CACHE_DIR"
  cache_key_files: [package-lock.json]   # repo-relative, named by the project
  timeout_minutes: 15                    # default is open (§16 item 8)
```

- **When it runs.** The runner runs it in the task's worktree, as the runner, in two places: before the worker starts, and again before the check. A review job (§7) gets the same environment: setup runs in the reviewer's worktree before the reviewer starts, and again before a check the job has. The command is the project's recorded setting, never read from the worktree at run time (the same rule as the check, §5.5, and the default check, §6.1). The engine copies the effective command into the task record when the task is created, with its source and settings version, so a later change to the project setting does not alter a recorded task.
- **What "again" means.** The worker may have changed a lock file or a script the command calls, so the runner always runs the command a second time; it does not skip it on a guess. The command must be idempotent. When nothing it depends on changed, the cache key (below) is the same, the cache is hit, and the second run is cheap: it finds its inputs in the cache, links or unpacks them into the worktree and exits. When the worker did change a named key file, the key differs and the second run is a cold install, paid before the check and not stored (below).

**Caching.** The cache exists so that a job does not download the world again, and is a convenience of the runner, never part of the task record.
- **What it holds.** A directory the setup command fills through `BRIGADA_CACHE_DIR`, an absolute path the runner sets in the command's environment: package downloads, a module cache, a wheel cache. The command decides how to use it (`npm ci --cache`, `UV_CACHE_DIR`, `GOMODCACHE`). The runner never looks inside.
- **Key.** A hash of the contents of the files named in `cache_key_files` (for example `go.sum`, `package-lock.json`, `uv.lock`; the project names them, brigada guesses nothing), of the command text, and of the runner's OS and architecture. A named file that is missing hashes as absent. With no `cache_key_files` there is no cache and the command runs cold every time.
- **Where.** In the runner's state directory, under the canonical repo URL (§13.1 item 1) and then the key. Never in the worktree, never in the repo. An entry is never shared across repositories, since two repos could otherwise read each other's dependencies, and never across runners, since the cache is local files of one host and a remote runner (product §5 rule 5) has its own.
- **How a job gets its copy.** Per job, by copy: before the first setup run the runner copies the entry for the key into a directory private to the job (a clone-on-write copy where the filesystem allows it) and sets `BRIGADA_CACHE_DIR` to that copy. A job writes only into its own copy. The entry is replaced only by the **first** setup run of a job (the one before the worker starts), and only if that run succeeds, by moving its copy into place atomically. The second run (before the check) and every run after a worker has touched the worktree never update the shared entry. So a worker that writes bad bytes into `BRIGADA_CACHE_DIR`, or edits what setup calls, can spoil its own job at most, never the next one. Read-only reuse without a copy is cheaper and is open (§16 item 8).
- **Invalidation.** A different key is a different entry, so a changed lock file never reuses a stale one. Entries older than an age bound, or the least recently used ones beyond a size bound, are removed by the runner; the defaults are open (§16 item 8). A user command (`brigada cache clear`, optionally for one project; the name is a proposal) removes entries at once, for a poisoned or confused cache.

**Tool scope.** Setup runs as the runner, not as the worker, and its commands are not bound by the worker's `tools=` scope (§5.2). That scope keeps bounding what the worker itself may run: setup does not widen it, and the worker cannot trigger a setup run or choose its command. Setup's output is data, never an instruction: it is kept in the log and may be shown to a reviewer or the foreman only inside the data delimiters of §1.4.

**Failure.** A setup that fails (exit code non-zero, or the timeout) is an infrastructure failure of the job. It is not a failed check, so it starts no fix round, and not a worker failure, so it does not count against the task's attempt caps for the agent. The engine retries it as it does a transient error (§3, the transient-error row), capped; when the retries are out, the task goes to the foreman as "task out of rounds or retries" (§3). Setup's log is an artifact (§9, §11) linked from the job, next to the check log, so the foreman and the user can see why. The time bound is `timeout_minutes`; the stall clock (§5.6) does not run during setup, which is bounded by that timeout alone, and a timeout kills the process tree.

**Trust and what stays out.** Setup commands come from the repo's own committed `project.yaml`, so they run repo code on the runner, with the user's shell and credentials (product §6, "what local gives up"). That is the trust a check already asks for: the check runs repo code the worker may have changed, in the same shell. Setup adds no new kind of exposure, but it adds a second occasion, and one before the worker starts: its command is the imported project setting, so changing it needs the same explicit import as any setting (§13.1), and a worker that edits a script the command calls takes effect at the second run, as for a check. Containers and per-job credential injection stay in the backlog (product §6); until they land the answer to untrusted repo code is the one product §11 gives, which is to document it.

*Implemented:* the project file's reader is a flat subset (§13.1), so schema 1 spells the three fields as sibling keys, `setup` (the command), `setup_cache_key_files` and `setup_timeout_minutes`, each a project setting with the provenance of the others (`project show`, `project set`, import); a nested `setup:` map is refused like any nested structure. The engine copies the effective setting (command, key files, timeout, source and imported-file hash) into `tasks.setup` when a task is created by a plan, an amendment or a submit; a lease grant carries the task's record, and a review job with no task the project's setting. The runner runs it as `sh -c` in the worktree with the runner's own environment plus `BRIGADA_CACHE_DIR`, in its own process group (killed whole on the timeout), before the worker (work, fix and review jobs) and again before the check. The cache is `<state>/setup-cache/<repository mirror>/<key>`; a job's copy is `<state>/setup-jobs/job-N-aM/cache`, removed with the job; the first run, on success, replaces the entry by an atomic rename. Defaults chosen for the open points of §16 item 8: timeout 15 minutes, entries unused for 30 days or beyond the three most recently used per repository are removed, and a copy per job (no read-only sharing). A failed setup completes the job with an error of kind `setup` and the message `setup failed: exit code N` or `timed out after D`, never the output. The engine retries a failed work job up to twice on any eligible agent, as a transient error, charging neither a restart round nor the agent's failure streak; a fix job, a standalone review or a spent retry count goes to the foreman (a review gets its one retry on another reviewer as for any error). The log of every setup run is an artifact of kind `setup_log`, linked as `setup_log_id` on the job. Not implemented: `brigada cache clear`.

### 5.8 A second repository in a task's worktree (proposal, 2026-10-16)

Some tasks need to read another repository: a shared schema, a generated client's source, a sibling service whose code the check builds against. A task still changes exactly one repository (below); the extra ones are context.

**Naming them.** A task may carry `extra_repos`, a list of entries:

```yaml
extra_repos:
  - name: schema                 # [a-z][a-z0-9_-]*
    repo: git@example.com:org/schema.git   # canonicalized as in §13.1 item 1
    ref: v2.3.0                  # branch, tag or commit; default: that repo's default branch
```

The URL is canonicalized as the project's is (§13.1 item 1), so SSH and HTTPS forms of one repo are one entry and a token in a URL is dropped. A commit SHA is the only reproducible ref: a branch or tag moves. The runner records the commit it resolved in the job record, so the history shows what the job saw, and the plan shown for approval says when a ref is not a commit.

**Where and what variable.** The runner checks each one out beside the task's worktree, at `<task worktree>.extra/<name>`, a stable path inside the runner's state directory and never in the main worktree, so nothing it holds can be committed by accident. For each entry the runner sets an environment variable naming the absolute path, for setup (§5.7) and for the check, and also for the worker: `BRIGADA_REPO_<NAME>`, where `<NAME>` is the entry's `name` uppercased with `-` turned into `_`. A check says `go test ./... -schema "$BRIGADA_REPO_SCHEMA"`, so the recorded command stays repo-relative and host-independent (product §5 rule 7): the path comes from the runner at run time and is never in the task data. Two entries in one list whose names give the same variable (`a-b` and `a_b`) are rejected when the task is created, never silently dropped. An entry that clashes with the project default's name replaces it (below). A name that would give a variable the runner itself sets (`BRIGADA_CACHE_DIR` and the like) cannot occur, because the prefix `BRIGADA_REPO_` is reserved for this use.

**Read-only, never pushed.** The checkout is read-only for the worker, and the runner never pushes it: it is cloned with no push remote, and the files are made read-only for the job's user. Be clear about what that is. It is a convention plus a read-only checkout, not a sandbox. The worker's tool scope (§5.2) is what keeps a claude worker away from it by default, since the default scope runs only `go build`, `go test`, `go vet` and `gofmt`; a worker with a shell or a wider scope runs as the same user and could change the permissions and the files. Whatever it changes is discarded, because the checkout is deleted with the worktree and is not a branch the runner pushes. Enforcement beyond that, such as a check that the checkout's `HEAD` and tree are unchanged after the job, is not in this proposal; real enforcement is a container's read-only mount (backlog, product §6). The runner needs read access to each extra repository with its own git credentials (product §5 rule 6); an entry the runner cannot fetch is an infrastructure failure of the job, handled like a failed setup (§5.7), not a failed check.

**How a plan names them.**
- **Per task:** the `extra_repos` field in `plan_create` and `plan_amend` (§12.2), part of a task's fields (§6.1), with the shape above. Omitted: the task inherits the project default. Given, even as `[]`: it replaces the default entirely, except that an entry with the same `name` as a default one wins over it.
- **Project default:** `extra_repos` in `.brigada/project.yaml` (§13.1), for repositories every task needs, with the same shape. It is a nonsecret repo-level setting like the default check.
- **Resolution** happens once, when the task is created or amended, as for the default check (§6.1): the engine copies the effective list, canonicalized, into the task record with its source (`project-default` or `task`, and the settings version). A later change to the project default never alters a recorded task, and the task can be run again as it was.
- **Approval.** The plan shown for approval (§6.3) lists each task's extra repositories with their refs, and the list is in the recorded task. It counts toward the approval limit like this (proposal, 2026-10-16): a task that names a repository outside the project's default `extra_repos` is a reason to ask, since it widens what the runner reads with the user's git credentials; the project default itself was imported by the user (§13.1) and is not. The trigger is stated here only; §6.3 is unchanged.

*Implemented:* the project file's reader is a flat subset (§13.1), so the nested entry above is spelled as one string, `name url [ref]`, in the shared file and in `brigada project set` (`extra_repos="schema git@example.com:org/schema.git v2.3.0"`; several entries are a YAML list, or joined by `+` on the command line, so a URL holding `+` cannot be spelled there). A nested `extra_repos:` map is refused like any nested structure. The file's URL is not required to be in canonical form, unlike `repo`: it has to be fetchable, so the engine canonicalizes it and keeps the credential-free transport URL beside the identity, and a bare `host/path` is refused as the project's own is. `plan_create` and `plan_amend` take the field as `extra_repos: [{name, repo, ref}]`; omitted inherits the default, `[]` or a list replaces it entirely (an entry with a default's name is simply the task's own). The engine resolves it in `plan_create`, `plan_amend` and the debug submit and copies the effective list into `tasks.extra_repos` (entries with identity, fetch URL and ref, the source `task` or `project-default`, and for a default the hash of the imported file); the lease grant carries the record, a task-less review the project default. A name that is invalid, a repeated name, two names giving one variable, a ref that starts with `-` or holds white space, and an unusable URL refuse the plan or amendment whole. The approval trigger is as above: an entry whose canonical repository is not among the project default's is a reason to ask, even when approval is otherwise unchanged by it (`approval_max_tasks` negative still turns the whole limit off); the reason lists each such entry as `name (repository, ref R, not a commit)` or `(repository, commit SHA)`, in the answer, the `plan_awaiting_approval` event and so `status`. On an amendment the whole amended plan is evaluated again, each task's own list included, as for classes and protected paths. The runner clones each entry with its own git credentials to `<state>/worktrees/job-N-aM.extra/<name>`, checks out the ref (a branch, tag or commit; empty is the default branch), removes the `origin` remote, and clears the write bits of every file and directory; it exports `BRIGADA_REPO_<NAME>` (absolute path) to the setup command, the worker (after the git-credential scrub) and the check, and a review job gets the same checkouts. The directory goes with the worktree (the startup sweep makes it writable first). A clone or ref that fails completes the job with the error kind `setup` and the message `setup failed: extra repository <name> could not be checked out` (git's output goes to the runner log, redacted), so it is retried like a failed setup. The commit each entry resolved to is in the work job's result block as `extra_repos: {name: sha}`, set by the runner over anything the worker wrote. The plan file mirror writes `extra_repos: [["name", "repo", "ref"], ...]` on a task that has some, the canonical identity and never the fetch URL; a file with none is unchanged, and recovery from a plan file does not restore the field.

**What it does not decide.** A plan spanning repositories, tasks that *change* two repositories, stays out of scope (§16 item 7). `extra_repos` does not answer that question and must not be read as the first step of an answer. It only supplies read-only context to a task that still changes exactly one repository: one branch, one repo URL, one project and foreman, one set of pushed branches. It brings none of the open items of item 7: whose foreman owns the plan, what the foreman token's project wall (§12.1) allows, how a task waits on a branch of another repo. Write access to an extra repository, a task that pushes to it, or a task that waits for another's branch is a different design.

### 5.9 Project instructions for every worker (proposal, 2026-10-16; implemented)

Workers run official CLIs, and each reads its own harness's project instruction file: `CLAUDE.md` for Claude Code, `AGENTS.md` for Codex and others. A rule written for one harness never reaches a worker of another family, so the same project gets different behaviour from different agents. The project therefore has one **instruction text** that brigada puts into every worker and reviewer prompt itself, whatever the harness. Implemented: the key is `instructions_file`; the local override is the project setting `instructions` (`brigada project set instructions=@<file>`, `@-` for stdin, or the text itself), not a separate `project instructions` command; the foreman reads the text through `status` with `instructions` set. Still open: the bulk apply to existing tasks, and a per-task re-resolution at `plan_amend` (the amend only adds, cancels and re-points tasks; an added task resolves at creation).

**Where it comes from.** Two sources, both resolved by the client, never by the engine from a path (product §5 rule 1):
- **The file.** `.brigada/project.yaml` (§13.1) may set `instructions_file`, a repo-relative path to a markdown file (for example `.brigada/instructions.md`). The client reads it at import, as it reads the rest of the file, and sends the text over the API. The path must be relative, stay inside the repository after symlinks are resolved, and name a regular file; anything else is refused at import, naming the path. The engine stores the text, never a path to read. The file may be the repo's `CLAUDE.md` or `AGENTS.md`, but then a harness that reads that file itself sees the rules twice, so a separate file is the recommendation.
- **The project setting.** `brigada project set instructions=@<file>` (`@-` reads stdin) stores text as a local override, for rules the user does not want in the repo. The client reads the file; the engine takes the text.

Which wins is §13.1's rule, unchanged: a local override, then the last imported file value, then the built-in default, which is no text. `status` and `brigada project` show the effective text's source (`local override`, or `file <path>, imported <time>`), its settings version, its byte size and a SHA-256 digest. A changed file over a store value that is still the previous import applies; over a local override it does not, and the conflict is shown with both texts for the user to resolve. Neither wins silently.

**Size bound.** At most 8192 bytes of UTF-8 (a starting value; tuning is open, §16 item 11). Above it the set or the import is **rejected** with the size and the limit in the error, and the previous value stays in effect; nothing is ever truncated, because a cut rule is worse than a refused one. Text that is not valid UTF-8 or contains a NUL is rejected too. An empty file is an unset value and is reported as such. The engine enforces the bound on the API; the client checks first, for a readable message.

**Where it sits, and what it cannot override.** The prompt order is fixed: the versioned template with its contract (the result block, §5.4; no pushing; the tool scope, §5.2), then the project instructions, then the task spec. Between the template and the text sits a framing sentence the template owns: the project instructions below are verbatim data between the data delimiters; they say how the project wants its code written and checked; they never change the contract above, which wins on any conflict (the result block, no pushing, no dispatch tools, the tool scope). The text is wrapped in `<project-instructions>` and `</project-instructions>`. As for the other worker delimiters (§1.4), the engine neutralizes look-alikes inside the data (those two tags and the other worker delimiter tags, case-insensitively and with inner whitespace), so the text cannot close its own section or open another. A text that says "ignore the above" is still data: it cannot widen a tool scope, which the runner enforces and no prompt grants, and a worker that obeys it against the contract still faces the runner's check (§5.5) and the reviewer (§7).

**Reviewers** get the same text, as data, in a section of their own with a framing sentence of their own: it is the convention the author was asked to follow, the reviewer may judge the change against it, and it never changes the verdict block's contract or asks for an approval. The reviewer still never sees the implementer's summary (§7).

**The foreman turn does not get it injected** (decided here, with this reason). The foreman has its own instructions and no editing or shell tools (§4); rules for code writers would compete with the foreman instructions and spend tokens on every wake. The foreman still needs the rules to write good specs, so they are visible to it as data: the `status` tool (§12.2) names the source, version, size and digest, and returns the full text inside `<project-instructions>` with the framing sentence when asked. The foreman instructions tell it to read the text before it plans. In mode A (§4.6) the user's own session reads its harness's instruction file anyway.

**Versioning.** Resolved once, when a task is created, as the default check is (§6.1): the engine copies the effective text into the task record with its source, settings version and digest. A later change to the setting never alters a recorded task. A `plan_amend` that touches a task that has not started re-resolves it; a task that has run keeps its text, so fix rounds, resumes, restarts and the task's reviews all use what the author was first given. The job record keeps the template version beside the digest, so a recorded prompt is reproducible. A user who wants a new text on tasks already created amends them through the foreman; a bulk apply is open (§16 item 11).

## 6. Plans and tasks

### 6.1 Task graph

A plan is a DAG of tasks (decided 2026-10-12: dependencies at launch). Task fields: title, spec, check, class (`implement` | `review` | `answer` | …), deps, repo and base ref, caps, and (decided 2026-10-19; shipped) tier and effort.

**Tier and effort** (decided 2026-10-19; shipped). The foreman decides how heavy a model each task needs; the user configures the foreman's model and effort and which CLIs may run tasks (§13.1). Two task fields, both set by the foreman in `plan_create` and `plan_amend` and shown in the plan presented for approval (§6.3) and in the plan file (§6.4):

- `tier`: `light` | `standard` | `heavy`, default `standard`: how heavy a model the task needs. The dispatcher resolves it to an agent (§8). The engine keeps the foreman's `tier` and the `effective_tier` the task runs at, which escalation (§8) may raise; the plan file carries the foreman's value only.
- `effort`: `low` | `medium` | `high` | `max`, optional: how hard that model should think. This is brigada's own set, one per task, not a harness level. The runner maps it to the agent's CLI through the adapter's typed effort control (§5.2): claude and codex take the same word; opencode takes `minimal` for `low`, no variant for `medium`, `high` and `max`; kimi has no effort control and ignores it. The job record stores the level actually passed. Omitted, the agent's own `effort=` applies, else `medium` (decided 2026-10-20; shipped), resolved in this vocabulary before the harness maps it, so opencode (`medium` maps to no variant) and kimi (no control) still get nothing; a nonempty mapped task effort overrides the agent's (opencode `medium` still uses the agent's own variant when set), as the shipped foreman effort does today (`brigada project foreman --effort`, GUIDE §11: it rides the foreman turn's grant and overrides the serving agent's own level).

Neither field is an approval trigger (§6.3). A task may still name an agent outright (`agent: harness/model`, proposal), shown in the plan as a pin; the family rule for reviews (§7) applies to a pinned agent as to any other.

**Default check** (proposal, 2026-10-16; not current CLI support): a task may omit `check` to inherit the project's default check (§13.1). Resolution happens once, when the task is created or amended through the engine: the engine copies the effective command into the task record with its source (`project-default` and the settings version it came from). A later change to the project default never alters a task that already has its check, so the recorded check stays reproducible, and the plan shown for approval (§6.3) carries the real commands, not a reference. The runner runs what the task recorded, never a value read from the worktree at run time (§5.5; product §5 rule 7). Omission is distinct from an explicit no-check override, which must be spelled out (`check: none`) if it is allowed at all (open, §16), and a plan containing one shows it plainly. A task that omits `check` in a project with no default is rejected at creation, never run unchecked.

Task states: `pending` (deps not done) → `ready` → `running` → `checking` → `reviewing` → `done`; or `needs_foreman`, `needs_user`, `failed`, `cancelled`. Cancelling a task cancels its dependents unless the foreman re-plans.

### 6.2 Plan lifecycle

`draft` (the foreman builds it) → `pending_approval` (above the limit) → `active` → `done` | `cancelled`. The foreman can amend an active plan (add, split, drop tasks); each amendment is recorded and re-checked against the approval limit.

### 6.3 Approval limit

Approval only above a limit (decided 2026-10-12). Proposed default: more than 5 tasks, any task touching protected paths (config, like a merge policy's protected class), or any task class other than `implement`/`review`/`answer`. Configurable per project.

### 6.4 The plan file in the repo

For fault tolerance, the engine writes each plan as **`.brigada/plans/<plan-id>.yaml`** (decided 2026-10-12) and pushes it, on every plan change, to a separate branch **`brigada/plans`** in the repo's remote by default, so the engine never commits to `main` on its own; committing to the default branch instead is a per-project setting (decided 2026-10-12). The file holds the graph, task states, branches and open questions, not transcripts. The engine store is authoritative; the file is a mirror.

**Backups.** The engine also snapshots its store (SQLite backup API) daily to a configurable directory outside the store.

**`brigada recover`** when the store is lost:
- **Restores:** from the latest snapshot if there is one, then plans, task states, branches and open questions from the plan files (newer wins).
- **Doesn't restore** without a snapshot: messages, transcripts and outcomes; the dispatcher's scores restart from defaults. Said plainly in the command's output.
- **Tokens** live in a config file outside the store (the store keeps only hashes), so clients, runners and the foreman can still authenticate; runners re-register.
- **Fence epoch:** recover bumps a store-wide fence epoch, and every lease, heartbeat or complete that references the pre-recovery epoch is rejected, so a late runner can't write into the rebuilt store.
- **In-flight work:** recover waits one lease-expiry window before re-dispatching, so runners whose heartbeats now fail have killed their workers. Re-dispatched work does not get a new branch name; the rules below decide which branch each kind of re-dispatch works on.
- **Branch names:** a task's first job works on `brigada/task-<id>`, and the engine names each job's branch.
  - **Re-lease** (the lease expired or the runner crashed, and the same job is leased again): keeps its job's branch.
  - **Restart** (§5.6, either mode, or a re-dispatch to another agent): works on `brigada/task-<id>-r<n>`, where `<n>` counts the task's restarts.
  - **Fix round** (§3): continues the task's branch, the one its last job pushed, so the fix lands on top of the work under review.

## 7. Review policy (in the core)

After an `implement` job is done and its check passed, the engine creates a review job for an agent of a **different family** than the author. The reviewer gets the diff (base…branch), the task spec and the check result, **never the implementer's summary** (Python v3.2 §7.1's anti-steering rule), and ends with a verdict block (`approve` | `changes`) plus findings. An approve without substantive findings text (v3.2's minimum length) counts as `no-verdict` and is retried with another reviewer, so lazy approvals don't inflate the outcome record. `changes` → a fix round (§3 rule) up to `review_rounds` (default 2), then a judgment event. Family detection: the job record; for `brigada review --branch` without a job, the `Co-Authored-By` trailer. That standalone command creates a one-task plan of class `review`: the runner runs the repo's configured check, and there are no fix rounds unless you ask. Merging is out of scope at launch: the foreman reports approved branches and the suggested merge order. The one thing brigada adds is a local step the user drives, `brigada land` (§7.1), which stops short of the remote.

### 7.1 Landing approved work locally: `brigada land` (shipped, 2026-10-16)

Today an engineer fetches each approved branch, squashes it onto the default branch, writes a message, reruns the tests and pushes, by hand, per task. `brigada land <task-id>... [--onto <local-branch>] [--repo URL] [--landed <task-id>]... [--no-check]` does the mechanical part and stops before the push. Shipped as designed below, with two gaps: the runner does not yet record the approved head with the verdict (§16 item 10), so the head check is the design's stated fallback (land warns per task and goes on); and the land-note record (see "The landing record") is not written, as the engine has no endpoint for it. The engine adds one read, `GET /v1/tasks/{id}/land` (client and admin tokens only, never the foreman's), which returns the spec, dependencies, approval, the author's summary and family; the client runs every git command.

**How it squares with "brigada does not merge".** Land is a local convenience the user drives, in the user's own working repository. It writes commits on a local branch and nothing on the remote: the remote stays the user's, and the push is the user's command, which land prints. The foreman never calls it and it is in no MCP set (§12.2): it is a client command, authenticated as the user, so approval and merging stay with the person. Auto-merge stays in the backlog (product §6).

**What it does.** Run inside the project's repository, on the target branch: the project's default branch, or the local branch named with `--onto`, which must be checked out (land never switches branches; it says `git switch <branch>`). In order:
1. **Preflight, before anything is changed.** Every named task is checked; one failure refuses the whole call and names the task and the reason.
2. **Fetch refs only,** as `brigada diff` does (a fetch from `origin` of each ref by exact name, no tags, no prune, no checkout): each task's base ref, its latest result branch (`-r<n>` included) and the target's remote counterpart.
3. **Squash in dependency order,** one commit per task, on the target branch (below).
4. **Rerun the project's default check** (§13.1, §6.1) on the result, once, after the last commit, in the user's shell like any check (product §6, "what local gives up").
5. **Stop,** print what it did and the push command (`git push origin <branch>`), and exit. It never runs it.

**What it refuses.**
- a task that is not `done`, or is not approved: an `implement` task needs an `approve` verdict on its last review (§7); other classes carry no review and no branch worth squashing, so they are not landable;
- a result branch whose fetched head differs from the head the verdict approved (proposal: the runner records the pushed head with the result; where no head is recorded, land warns and goes on);
- a dirty working tree (tracked changes, or untracked files that are not ignored), or a merge, rebase, cherry-pick or revert in progress;
- a target branch that is behind or has diverged from its remote counterpart (pull first; being ahead is fine), or that is not the checked-out branch;
- a working directory whose `origin` does not canonicalize (§13.1 item 1) to the task's project, with `--repo` as the same escape `brigada diff` has;
- a dependency that is neither landed nor in the same call (below);
- no default check, unless `--no-check` is given, the same "never run unchecked" rule as §6.1; `--no-check` is shown in the final report.

**Dependencies and stacks.** Tasks are squashed in dependency order; among tasks with no order between them, in the order given. A task's diff is `git diff --binary <base>...<branch>` for **its own recorded base**, not the default branch, so for a task whose base was its dependency's branch (§6.1, repo and base ref) it is only that task's work.
- *Dependency in the same call:* squashed first, so the target already holds its content and the dependent's patch applies on top.
- *Dependency already landed:* land recognizes it by the `Brigada-Task: <id>` trailer on a commit in the target's history. A dependency landed by hand, or on another clone, carries no trailer, so the user says `--landed <id>`, which skips that task's preflight and is shown in the report.
- *Dependency neither:* refused, naming it, since squashing the dependent alone would apply a patch onto a tree that lacks what it was built on.
- If the dependency's branch moved after the dependent was cut (a later fix round), the dependent's patch may not apply cleanly; that is a conflict like any other.
- A task whose diff is empty makes no commit and is reported.

**Conflicts.** The patch is applied three-way. On a conflict land stops at that task, names the conflicting files, and leaves the tree as it is (conflict markers, index staged) for the user. It never resolves anything, never picks a side, never discards the tree. Commits already made for earlier tasks stay; the report gives the target's starting commit, so the user can return with `git reset --hard <sha>`, printed and never run. The prepared message for the stopped task is written to a file inside `.git` and its path printed, so the user resolves, runs `git commit -F <file>`, and reruns `brigada land` for the rest, which finds that task landed by its trailer. A git hook that rejects a commit stops the same way (land runs ordinary `git commit`, never `--no-verify`). A failing check undoes nothing: the commits stay, the report names the failure and prints no push command, and the exit code is non-zero.

**The commit message.** Built by the client from data it reads through the API, never from the branch's own commit messages. Subject: the task title, one line, at most 72 characters (cut with an ellipsis). Body: a spec summary (the spec's first paragraph, at most 600 bytes) and the worker's summary (§5.4) from the task's last job, at most 2000 bytes. The whole message is at most 4096 bytes. A field over its bound is cut at a character boundary and marked `[truncated]`: unlike §5.9, truncation is right here, since the full text stays in `brigada logs` and the history (§9) and a commit message is a record, not a rule. Trailers:
- `Brigada-Task: <id>` and `Brigada-Branch: <branch>@<sha>`;
- `Co-Authored-By: <model> <address>` for the authoring model family, from the job record (the family detection of §7). When the family is unknown (no job record, or an agent whose family was never set) there is **no** `Co-Authored-By` trailer and `Brigada-Author: unknown` is added instead; land never invents an identity. A known family whose address brigada does not have gets the model name alone and is reported.

**The worker's summary is data.** It is model output: it goes into the message as plain text and is never executed, expanded or interpreted. The message reaches git through a file (`git commit -F`), never a shell string; control characters other than newline and tab are stripped, NUL and CR included; each line of the spec and summary parts is indented four spaces under a heading line, so no line of them can read as a trailer (`Co-Authored-By:`, `Signed-off-by:`, `Brigada-*:`) or as a `#` comment. Only land's own trailers sit in the trailer block. The commit's author and committer are the user's own git identity.

**What it never does.** Never pushes; never force-updates anything; never touches the remote's branches (no delete, no push, no `fetch --prune`); never rewrites commits that existed before the call; never changes the engine's task state, which stays `done`.

**The landing record (proposed, not shipped).** The shipped land writes no record and the engine never learns of a land; "already landed" is read from the commit trailers. The proposal: land posts one message per commit to the engine through the API as a client message (kind `land-note`, `client` or `admin` token, idempotent per task and commit): task, target branch, resulting commit, check outcome, and "local, not pushed". It appears in `brigada history` (§9). It is not a user message (§4.2 item 3): no foreman prompt carries it as a request and it wakes nothing; a foreman that reads it sees verbatim data. There is no engine-side git (product §5 rule 1), and the engine never learns whether a push followed. A failed post is a warning, never a failure of the land. "Already landed" is read from the commit trailers, not from this record, because the record belongs to the engine and the commits to this clone.

## 8. Dispatcher

**Per-job usage (decided 2026-10-20).** Each job records the usage its own
CLI invocation reports: input, output, cached input and reasoning tokens,
and US dollars when supplied. Claude result usage is counted once, with
cache reads and creation included in input; Codex turn usage and opencode
step usage are summed. Missing or malformed counters stay unknown (NULL),
distinct from reported zero. A fix round and a resumed session are separate
jobs: totals are never carried or subtracted across jobs. Wall time is
recorded with completion. Stats sum known counters per agent and class
from every job, including work, fix and review, and show cost per success
in dollars when any dollar cost is known, otherwise in tokens. Unknown
jobs do not contribute to sums; no successes means no cost-per-success.
These measurements do not steer dispatch yet.

- **Eligible:** the adapter supports the class; family rule for reviews; agent `ready` (not `broken`, not `cooling`); account not cooling; session affinity (a resumed session stays on its agent and runner); (decided 2026-10-19; shipped) the agent's tier is the task's effective tier, with the fallback below.
- **Cap room:** an eligible agent is picked only if every concurrency cap on its path has room (§8.1). Caps shrink the set of eligible agents with room, so a task whose best agent is cap-blocked goes to the next-best agent with room; it waits in the queue only when no eligible agent has room, and that never parks it. **Parking** means no agent is eligible with caps ignored.
- **Score:** per (repo, class, agent): a success rate with a prior, where success = check passed and review approved within the rounds. Defaults for a cold start. `stats` shows it with its confidence; dispatch no longer sorts by it.
- **Ranking** (decided 2026-10-20; shipped). Within the served tier, each eligible agent draws p from Beta(successes + 0.5, failures + 0.5), its outcome record for the job's (repo, class), and the agents rank by `weight / p`, lowest first, where weight is the configured `cost.<harness>/<model>` (default 1, §8.1). This is Thompson sampling with a cost: a thin record draws widely, so a weaker or newer agent keeps being tried without a separate exploration share, and a clearly better record beats a slightly cheaper agent most of the time. A weight of 0 ranks before every positive weight; among zero weights the higher p goes first. Exact ties break by a further draw, never by agent id alone. The draws come from the engine's injectable uniform source, so tests stay deterministic. Cap room then walks the ranked order and takes the first agent with room. A job pinned to an agent (a fix round) is not ranked, and the automatic restart's pick shares the same sampling. The decision record names the pick `sampled` and holds each candidate's weight and draw; a pinned lease draws nothing and is recorded as `pinned`. Sampling never sends a task to a lighter tier; only the last-resort fallback below may.
- **Quota:** limit-hit errors cool the whole account until its window resets; Codex's reset time is read from its own limit message (`try again at …` in the machine's local zone, or `try again in …`), and a reset beyond eight days is suspect and capped there; CodexBar's CLI JSON is an optional extra signal.
- **Health:** repeated failures, auth errors or a dead runner → `broken(reason)` until a probe passes or the user resets it.
- Every decision is recorded with its reason ("why this agent").

**Tiers** (decided 2026-10-19; shipped). Each agent serves one tier, from brigada's tier table by model name, a segment-prefix and whole-segment table beside the family table (§7's detection): `opus` and `fable` segment prefixes and whole `pro`, `max`, `ultra` and `astra` segments are heavy; the `haiku` segment prefix and whole `mini`, `nano`, `flash`, `lite`, `highspeed`, `free` and `luna` segments are light; any other model is standard. The config override `tier.<harness>/<model>` (same shape as `cost.`, §8.1) corrects the table for every agent of that harness/model, as `cost.` does. Because the tier is an attribute of the agent, like effort, the outcome record keeps its key (repo, class, agent); records earned under one tier stay attached to the agent when an override changes its label. `stats` and `capacity` (§12.2) show the tier beside each agent.

- **Fallback** (cap-0 rule decided 2026-10-20; shipped): a task whose tier has eligible agents that are all cap-blocked waits in the queue as today (§8.1): a cheap wait beats a heavier model. A cap that is merely full waits, but an agent whose model cap or account cap is exactly 0 can never run, so it counts as unavailable: a tier whose agents are all capped at 0 falls back as if it had no ready agent. A tier whose agents are all cooling for no more than an hour (`longCooling`, a constant of the engine, not a config key; decided 2026-10-20) waits too, held as the shipped cooling hold holds a job (bounded by the reset time): only a reset within that hour is waited out, and heavy models drain the same windows faster. An agent cooling for longer, such as under a multi-day or even a 5-hour limit, has an end too far off to wait for and counts like a broken one. A tier with no registered agent, or whose agents are all broken (no end in sight) or cooling for more than an hour, climbs to the next tier up; from heavy, or when no higher tier has an agent, it steps down instead. This holds for work, fix and review jobs alike, with the family rule for reviews applied first: a review of a Claude-written task does not wait days for a Codex reviewer while a standard reviewer of another family is ready. When no tier has an available agent but some are cooling, the job waits in the tier whose agent resets first. A job pinned to its agent (a fix round on the author's session) is not moved and waits for it. The decision record names the tier asked for and the tier served.
- **Escalation:** a task climbs a ladder of effort, then tier (decided 2026-10-20). The task carries an effective effort beside its effective tier, starting as its own effort (possibly empty); the lease resolves the job's effort from the effective effort, then the agent's explicit effort, then medium. When a task's check or review rounds are spent, or a worker ends with the result-block status `failed` (§5.4), and the retry rules of §3 (the transient retry, the quota re-dispatch, the automatic restart) have declined or are spent, the engine first retries on the same tier with the effective effort one step up — low → medium → high, starting from the resolved effort, never stepping to max — with the event `task_effort_bumped` (old and new effort, the reason). Only when the effort is already high (or max) does it raise the effective tier one step, with the effective effort reset to the task's own, and the event `task_tier_bumped`. Each step queues a fresh attempt as the quota re-dispatch does (§3: the next `-r<n>` branch, the previous job's summary carried, counted toward the restart cap on every step); neither event wakes the foreman. A run that ended without a readable result block may be the runner's fault, so it takes the effort steps like any failure but never raises the tier: a no-result at high effort goes to the foreman with the reason. A job that failed for a transient reason (quota, auth, a lost runner) belongs to those retry rules, never to escalation. The task reaches the foreman (`needs_foreman`) only at heavy and high effort, or when its attempts are spent. A stalled worker still always goes to the foreman (decided 2026-10-12). The foreman may change the tier or effort again with `plan_amend`'s `retier`: a new effort sets the effective effort with it, and a tier change resets the effective effort to the task's own; agent pinning remains a proposal (§6.1).
- **Effort** (§6.1) is per job: the runner passes the task's effort to the adapter, so two jobs on one agent may run at different levels. It is not a cap layer (§8.1).

### 8.1 Concurrency caps

**Layered caps** (decided 2026-10-13). A job may start only if every layer has room; the effective capacity is the minimum across the layers:

- **Runner:** max parallel jobs per runner, for the host's CPU, memory and parallel builds and tests. The runner advertises its own cap when it registers; the effective runner cap is the smaller of that and the config's.
- **Account:** max parallel jobs per adapter account, for the vendor's session and rate limits; parallel sessions also drain the 5-hour window faster.
- **Model** (optional): a per-model cap, such as 1 for a heavy model.
- **Plan:** max parallel tasks per plan, because tasks touching the same files end in merge conflicts. A task counts while it has a live job (`running`, `checking` or `reviewing`, §6.1).
- **Global:** an overall ceiling for the engine.

A task job (a task's first run, a fix round or a review) that cannot start because some layer is full waits in the queue, oldest first, and starts when a slot frees; it does not park (§3) and does not notify the user.

**The foreman is never starved.** Foreman turns count toward the runner, account and global caps (not the plan or model caps), and a pending foreman turn outranks every queued task job at each of those layers: the next slot that frees on its path goes to it. Its wait is therefore bounded by the running jobs' class time caps (§5.6). An attached chat (§4.2) is not a job, but it is a live session on the foreman's account: it counts toward that account's cap while held, without ever waiting for room, so the dispatcher starts no new task job there until there is room again.

Each agent also carries a **cost weight** (default 1), a relative cost the user sets, which the foreman sees through `capacity` (§12.2) when it chooses which tasks can wait for a cheaper agent. The dispatcher uses it too (decided 2026-10-20; shipped): agents of one tier rank by `weight / p` (§8), so a dearer agent is picked less often, and a weight of 0 makes an agent free, ranked before every paid one.

**Effort and caps** (decided 2026-10-19; shipped). A task's effort (§6.1) is not a layer: a `max` job and a `low` job on one agent share that agent's caps. A high effort drains the account's window faster per job, which the adaptive caps (backlog, below) absorb; nothing is modelled for it at launch.

**Defaults set by init** (decided 2026-10-19; shipped). Init asks one number, tasks at once (§13.1), and writes it as `caps.global` and the runner's `--max-parallel`; the account caps come from a per-harness default table (claude 3, codex 2, kimi 1, opencode 2), each clamped to that number and shown in init's plan block; `caps.plan` is set to 3. Unset `--max-parallel` still means one job at a time. `brigada config` shows the config file to edit afterwards; the engine reads caps when it starts.

**Defaults** (proposal): conservative per adapter, all set in the engine's config file. An example:

```
caps.global = 6
caps.plan = 3
# a runner may advertise its own (--max-parallel); the smaller wins
caps.runner = 4
# per account label
caps.account.claude = 3
caps.account.codex = 2
caps.account.kimi = 1
caps.model.<heavy-model> = 1
# cost weight per agent, default 1
cost.<harness>/<model> = 2
```

Comments go on their own line; the parser does not strip trailing comments.

**Backlog: adaptive caps.** When an account hits its limit while running N parallel jobs, the engine lowers that account's cap automatically and records the change and its reason; the user can raise it again.

### 8.2 Foreman headroom

(proposal) The foreman's session uses quota on its own account, so task workers must not drain that account and leave the foreman `limited` mid-plan (§4.4). The dispatcher prefers other accounts for task workers, and stops dispatching task workers to the foreman's account above a reserve threshold: by default 80% of the 5-hour window used, when CodexBar data is available; without it, a lower parallel cap for task workers on that account: `max(cap − 1, 0)`, so one slot stays reserved for the foreman even while no foreman turn runs. At an account cap of 1 that is 0: task workers never run on the foreman's account.

## 9. History

Everything is kept and readable (decided 2026-10-12).

- **Messages:** one table of conversation items per project: user ⇄ foreman turns (a user message, §4.2 item 3, is kept with author `user`), foreman tool calls and their results, worker task specs and results, questions and answers, reviews, notifications. A job's `discoveries` (§5.4; proposal, 2026-10-14) stay with that job's result message. `brigada history [--plan|--task]` shows them as one timeline.
- **Transcripts:** after every job, the runner uploads the session's full transcript (the CLI's own event log) to the engine as an artifact, linked from the job. The foreman's chat transcript is archived the same way after each attach and each headless turn. A mode A session's transcript belongs to the user's harness and is not uploaded (§4.6); its decisions reach the history as tool calls and `decision_note`s.
- **Events:** an append-only event log is the backbone. Messages and transcripts reference events.
- Retention is configurable; the default keeps everything.

## 10. Notifications (launch: local)

Local OS notifications plus a "needs you" queue in `brigada status`: plan approval, user-directed questions, the foreman's limit, the foreman's budget out, a broken agent, a task parked with no eligible agent, a plan done. Remote channels (webhook, Telegram) are in the backlog.

## 11. Data model (SQLite, one file)

`projects` (canonical repo URL, default branch, settings with the provenance of each (§13.1), foreman harness and model) · `plans` · `tasks` (+ `task_deps`) · `jobs` (task, kind: `work`|`fix`|`review`|`foreman`, agent, mode, prompt, lease and fence, status, result, check result, last progress, transcript ref) · `sessions` (key, agent, runner, harness session id, state) · bridge presence and holds (proposal, §4.6: bridge instance, hold id, fence, label, verified harness metadata kept apart from hints) · `runners` · `agents` (runner, adapter, harness, model, family, account, classes, health, cooling until) · `outcomes` · `events` (append-only) · `messages` · `questions` · `tokens` (hashed) · `artifacts` (transcripts, check logs).

## 12. Interfaces

### 12.1 Engine API

JSON over HTTP; locally on a Unix socket, remotely over TLS. Bearer tokens with roles: `client`, `foreman` (scoped to its project), `runner`, `admin`. Groups: projects, plans (approve and reject are `client` or `admin` actions; a `foreman` credential cannot call them), tasks (create, amend, cancel, restart), questions (answer), foreman messages (a user message, §4.2 item 3: `client` and `admin` only, idempotent; a message identical to one the same token sent to the same project within the last minute is a duplicate — a double Enter, a shell retry — answered with the first one's id), events (long-poll and SSE), history, stats, budget, agents and runners, artifacts.

**Plan version** (implemented). A plan carries a version, 1 at creation, that every amendment moves (`plan_amend`, including a cancel-only one). `status` shows it for a plan awaiting approval, and `POST /v1/plans/{id}/approve|reject` take an optional body `{repo_url, version}`: a `repo_url` confines the plan to that project, and a `version` other than the plan's current one is refused whole with 409 `stale_plan`, applying nothing. The CLI sends neither and checks nothing; the coordinator's `plan_approve` and `plan_reject` require both.

**Idempotency.** The caller is often an LLM whose tool calls may repeat. `plan_create`, `plan_amend`, `task_restart`, `answer` and a foreman message (§4.2 item 3) take an idempotency key (client-supplied, or derived: task + round for restart and answer); a repeat returns the first call's result. The key is minted by the `brigada mcp` bridge per logical tool call (a hash of the call's content within the session), not left to the LLM; identical `plan_create` content within a short window also dedupes. Task jobs are keyed `task:<id>`: one live job per key makes duplicate job creation coalesce into the follow-up flag, which `status` shows.

**Credentials by mode** (proposal, 2026-10-16). Headless foreman turns keep the job-lease-scoped credential of §12.2, unchanged. A mode A credential is tied to a live hold (§4.6): project-scoped, minted at `hold_acquire`, held in the bridge's memory and revoked on yield, expiry, forced release or bridge loss, so a stale one dies with its hold. To ask for a hold at all, the bridge needs a *hold-only bootstrap credential* that init writes to the state directory, never to the repo: it can register presence and request a hold for one project, and it cannot call a plan tool. The residual local boundary of §12.2 applies to it: any local process that can read the state directory can request a hold. No direct store access and the engine-as-mailbox rule stand for every mode.

### 12.2 MCP tools: three sets on one bridge

`brigada mcp` is one bridge with three tool sets. Authority comes from the credential the engine accepts, never from the flag: a selector only chooses which tools are listed. The foreman set below is as designed on 2026-10-13, plus the mode A additions marked proposed; the other two sets are proposals.

**Project foreman set.** `plan_create` · `plan_amend` · `task_restart` · `task_cancel` · `answer` (a task worker's question) · `ask_user` · `events` (long-poll, for the attached session) · `status` · `stats` · `history` · `capacity`. It is scoped to one project and has no plan approval or rejection authority, and no land tool (§7.1): merging stays with the user. For mode A (§4.6) it adds three proposed tools: `hold_acquire` (returns the state digest), `hold_yield` and `decision_note`; heartbeat and release are the bridge's own and are not tools. A headless turn needs none of them: its job lease is its hold. `capacity` returns, per agent: its effective cap and the layer that sets it (§8.1; on the foreman's account, after headroom, §8.2), running jobs, quota state (`ready`, or `cooling` until a time, plus the percent used of the 5-hour and weekly windows when CodexBar data is available), cost weight and (decided 2026-10-19; shipped) tier. It also returns each layer's cap, use and queue depth: per runner, account and any capped model, per active plan of the foreman's project, and global. A queued task has no agent yet, so queue depth is reported per layer, not per agent. The MCP server is a `brigada mcp` stdio process started by the foreman's harness; it calls the engine API with the foreman token. The token is lease-scoped (decided 2026-10-13): the engine mints a short-lived one when it leases a foreman turn — only its hash is stored, the runner keeps the secret in memory alone — and revokes it when the turn ends, so a runner never holds a long-lived foreman token.

**Ordinary client set** (proposal, 2026-10-14): `brigada mcp --client` is the same bridge for any other harness acting for the user, a coding session or a coordinator: `ask_foreman` (a user message, §4.2 item 3), `status`, `history`. It authenticates with a client token from the state directory and never holds a foreman token, so a harness can talk to the foreman and watch the work without a person relaying between the two. Every client token speaks with the user's voice, which is the point; the token file can hold several, each with its own label (one per device or harness) and revocable on its own, and the label travels with each message into the foreman's prompt and the history (§9), so it's clear which surface sent what. The roles can't close one residual boundary of the local model: any local process that can read the state directory, a task worker with a shell included, can use a client token. That was already true of every client action; it matters more now that a user message is a request by design, and containers (backlog) are the answer.

**Coordinator set** (proposal, 2026-10-16): the client set plus `list_projects`, `plan_approve` and `plan_reject`, every tool taking the project's canonical repo URL (§4.6 mode B). It authenticates with a client token, never a foreman credential. Approval is an explicitly user-directed act with a visible confirmation (§4.6): the result "awaiting approval" is never itself a reason to approve.

**Selectors** are mutually exclusive: two together is a startup error.
- `--client`: the ordinary client set (existing proposal).
- `--foreman` (proposal): the project foreman set for mode A, scoped by the repo URL found from the bridge's repository (git root discovered from the cwd, or the Codex request metadata, §4.6) or given explicitly. It never reads a client token, and its credential comes from a hold (§12.1), not from the flag.
- `--coordinator` (proposal): the coordinator set. It never reads a foreman credential.
- A bare `brigada mcp` stays what the runner starts for a headless foreman turn: it works with the lease-scoped foreman credential the runner hands it and refuses to start without one.

Selecting a flag mints nothing, and a selector that the credential in hand does not match is refused. A client token never appears in the foreman set, nor a foreman credential in the other two.

### 12.3 Runner protocol

**Usage completion (decided 2026-10-20).** Completion optionally carries
`usage` with `input_tokens`, `output_tokens`, `cached_input_tokens`,
`reasoning_tokens`, and `cost_usd`, plus `wall_seconds` for this job's elapsed
wall time before delivery. Each usage field is optional. Older runners may
omit usage and wall time; these remain NULL. Retries of a completion do not
add usage again. Counters describe only the job's own CLI invocation, even
for fix and resumed jobs, and do not steer dispatch yet.

`register` · `lease` (long-poll) · `heartbeat` (progress, last activity) · `complete` (result or error; an outcome of `stalled`/`time_cap` when the runner stopped the run itself, §5.6; check result; artifacts) · `release`. Fencing as in Python v3.2.

## 13. Engine lifecycle

Single instance (a lock on the store); started by any `brigada` command when not running; shuts down after `idle_minutes` with no live jobs, attached sessions, pending wake-ups or unsent notifications (it flushes them first); crash or reboot recovery through lease expiry and fencing, then pending foreman wake-ups are re-evaluated.

### 13.1 `brigada init` (proposal, 2026-10-16)

One step sets a repo up. The GUIDE's §1 describes the shipped questions: the foreman model and effort, worker models, tasks at once, then the check. The amendment below records that order; the earlier outline retains proposals beyond the shipped setup. Init has two phases: it probes and prints what it would do (no writes), then applies on confirmation. Nothing is silent.

1. **Identity.** Read the repo's `origin` and normalize it to the **canonical repo URL**, the project's name. With no `origin`, or several remotes and none named `origin`, ask; a local-only repo is rejected (product §5 rule 4). Scp-like SSH (`git@host:org/repo`), `ssh://` and HTTPS URLs of the same host and path give one project. Userinfo is dropped and never stored, logged or shown, so a token in an HTTPS URL stays out of everything. The host is lowercased; the path is not, because paths can be case-sensitive. One trailing `.git` and trailing slashes are removed. The scheme is dropped, and a port is kept only when it is not the scheme's default, so a non-default SSH port stays a different project from that host's HTTPS URL unless the user confirms they are the same. Anything the string alone cannot settle is ambiguous (a leading-slash or `~` scp path, an SSH config alias that is not a hostname) and init asks; it never guesses. The canonical form is `host[:port]/path`. Each runner still fetches with its own URL and credentials (§5.1).
2. **Probe harnesses.** Find installed harness CLIs and check whether each is signed in, by the harness's own cheapest status check or by asking the user. Detected login state is local and never goes in the shared file. A binary name proves neither a subscription nor a model family: the family comes from the model an agent is configured with, and the user confirms which models an account serves.
3. **Agents and review families.** With zero usable agents init refuses, starts nothing and writes nothing. It counts distinct model *families* among review-capable agents, not CLIs: two CLIs on one family are one. With fewer than two it does not report ready. It stops the normal setup with an actionable warning (sign in to a harness of another family, or add a model of one) and continues only on the user's explicit acknowledgement of a **limited setup** (`--accept-limited`, proposal). A limited setup never disables cross-family review (§7): reviews it cannot serve are named in `status` and park as already designed, and init never presents such a setup as fully ready.
4. **Foreman.** Pick the foreman harness and model from the usable agents (it needs headless resume, §4.1, and for mode A a way to host the tools). The pick is shown and overridable.
5. **Defaults.** Suggest a default check and a worker tool scope from the repo's build files (for example `go.mod`, `package.json`, `Cargo.toml`, a Makefile target). They are shown, overridable, and never executed during discovery. They are repo-relative commands (product §5 rule 7). The suggested scope is the narrowest that runs that check (§5.2); init never silently grants a wider one, and a scope the user sets replaces the default as §5.2 says.
6. **Start.** Start the engine on demand and the runner with the detected agents.
7. **Wire the harness for mode A.** Register the bridge and install the foreman instructions (§4.6): for Claude Code in the shared project scope (`.mcp.json` and `.claude/settings.json`, diffs shown first); for Codex, print the user-level command for the user to run, since no project-scope path is verified. Installation is additive and idempotent: existing `CLAUDE.md`, `AGENTS.md`, skills and settings are never overwritten. Prefer a file brigada owns (a skill directory, an MCP prompt). Where a shared instruction file must change, append one delimited, versioned block, and on a re-run replace only the inside of it; if the markers are damaged, leave the file alone and report. No secret is written to any repo file, and init never commits or pushes.

**Tiers, effort and tasks at once** (decided 2026-10-19; shipped). With tiers (§6.1, §8) the user chooses which models may work: the foreman picks a tier and an effort per task, and the engine picks the agent. The shipped questions are:

1. **The foreman.** After the sign-in probes, a numbered menu of every model the signed-in claude and codex CLIs list (the same sources as the shipped menus: Claude's aliases, Codex's `debug models` catalog, models of unknown family left out as there), then its effort: the shipped effort menu, asked once, for the foreman only. Enter picks the first usable resume-capable model, claude before codex, as the shipped foreman step does. A foreman model whose harness is not used for tasks is registered as an agent with no classes, so it serves foreman turns and nothing else. The runner accepts `classes=none`, and the engine exempts foreman turns from the class filter: the harness-and-model pair is their constraint, so this agent takes no task job.
2. **Workers.** Per installed CLI, the sign-in check as shipped; Claude and Codex then ask `Use <cli>'s models for tasks (<models>)? [Y/n]:` in place of a model menu (Enter is yes on the first run; the shipped `Use kimi? [y/N]:` and `Use opencode? [y/N]:` questions are asked when sign-in is unconfirmed): every model the CLI lists with a family brigada can tell becomes an agent at its tier (§8); unknown-family models stay out, as in the shipped menus, because the family drives review routing. Kimi keeps its writing question. opencode keeps a menu, because its list spans providers, and the menu accepts several numbers. There is no effort question for workers.
3. **Tasks at once.** One number, default `min(4, max(1, cores/2))`, explained with the machine's core count and the per-account caps it implies (§8.1); it becomes `caps.global` and the runner's `--max-parallel`.
4. **The check.** Unchanged.

The plan block gains a tier column in the agents table, the foreman's effort, and an "at once" line with the per-account caps. Every prompt keeps the four parts: what is chosen, why, the valid answers, what Enter does. A rerun defaults to the saved choices. `--agent` keeps working, once per model, so `--yes` runs name each agent; `--foreman HARNESS/MODEL@EFFORT` and `--parallel N` answer steps 1 and 3 without a question; omitting `@EFFORT` leaves the interactive effort question.

**Parent folder (mode B).** Init in a folder that is not a repo scans only its direct children by default (a deeper `--depth` is a proposal). It does not descend into a repo (submodules are not projects), does not follow symlinks out, and skips hidden directories. It prints a visible list: path, canonical URL, new or known, and a skip reason (no `origin`, ambiguous). The user selects, and only the selection is registered. Two children with the same canonical URL are one project. It wires the coordinator set in the folder's project scope and writes nothing into the child repos; a child gets mode A only when init runs in it.

*Implemented:* `brigada init` outside a repository scans the direct children (a symlink, or a `.git` that is a symlink, is listed as skipped and never followed; a directory counts as a repository only when its own top level is itself), prints `path  canonical URL  new|known|unknown (engine not running)` or `skipped: <reason>`, and registers what the user picks at the prompt (`1,3`, `all`, blank for none) or everything new with `--all`. A second child with a canonical URL already seen is a duplicate, not a second project. New projects take the foreman of `--foreman harness/model`, else that of a project the engine already has; with neither, init refuses before writing. It writes the folder's `.mcp.json` entry `brigada-coordinator` (`brigada mcp --coordinator`, additive and idempotent, a damaged file left alone) and the brigada-owned skill `.claude/skills/brigada-coordinator/SKILL.md` (coordinator instructions, `foreman.CoordinatorInstructionsVersion`, golden-tested). It adds no hook and no permission entry, so `plan_approve` and `plan_reject` stay on the harness's own "ask". It starts no runner: agents, a default check and mode A come from `brigada init` inside a repository.

**`.brigada/project.yaml`** (the choice is decided 2026-10-16; its exact schema, flags and import mechanism are proposals, and none is implemented). The portable, versioned, shareable repository configuration, committed by the user so it travels to colleagues and machines. The cost: one brigada-owned file in the user's repo. Only nonsecret repo-level intent goes in it: the canonical repo identity, the default check, the worker-tool policy, `instructions_file` (a repo-relative path to the project's worker instruction text, read by the client at import, §5.9), and project defaults and preferences. Accounts, credentials and tokens, local executable and state paths, detected login state and machine overrides never do; they stay local. Init writes it additively and reviewably (a new file, or a diff the user approves) and never commits or pushes it. The client reads the file and sends its content over the API, so the engine never reads a repo path (product §5 rule 1).

The store holds the *effective runtime settings*, each with its provenance. Precedence, highest first: a local override the user set on this machine; the last imported file value; the built-in default. Detected suggestions only propose. Import is explicit (init, or a sync command), never a side effect of `git pull`, and `status` flags a file that differs from the store. On import, a file change over a store value that is still the previous import's applies. Over a local override it does not: the conflict is shown with both values for the user to resolve. A file against a hand-set store value on first import shows the diff and asks. An unknown schema version is refused. Neither the file nor the store wins silently, and the engine never writes the file back after init.

*Implemented (schema 1 and explicit import; `init` itself is not):* the file holds `schema: 1`, `repo` (the canonical identity, written in canonical form and checked against the origin), `default_check`, `worker_tools` (the `tools=` spelling), `approval_max_tasks`, `approval_classes`, `approval_protected_paths`, the environment step's `setup`, `setup_cache_key_files` and `setup_timeout_minutes` (§5.7), and the default `extra_repos` (§5.8), and nothing else; an unknown key or schema version is refused with the key named. `brigada project import [--repo URL] [--file PATH] [--yes]` reads the file in the client and sends its bytes; the store records the hash of the last import and, per key, the value it set. A key whose stored value is still that import's counts as imported; any other stored value is a local override, and `project set` always makes a key local. `project show` prints `(default)`, `(set)` for a local override, or `(imported <hash>)`. `status` flags a file whose hash differs from the last import, reading the file in the client and changing nothing.

## 14. Porting from Python v3.2

Moves over with its tests: the lease engine with fencing, one live job per key, follow-up coalescing, the run cap and per-key budget, fresh/session modes and affinity, review after implement (from the connector into the core). Stays in the fleet: the merge gate, bot forks, worker images, egress proxy, chat-front-end connectors.

Transformations, so nothing is lost in translation:
- **`trigger` human/bot is obsolete:** there are no human-submitted jobs (your input is chat, not a job). Don't port it.
- **The run cap (bot rounds)** becomes per-task caps on fix, review and restart rounds, plus per-plan task-worker-minutes.
- **The per-key budget raise** becomes `brigada budget` (§4.3).
- **Keys:** task jobs `task:<id>`, the foreman `foreman:<project>`. One live job per key, coalescing, the follow-up flag and affinity hang off them.
- **Session write-back and resume-fail → restart in place** (§2a) are kept for task workers and for the foreman's attach (§4.2).
