# brigada: design

What each part of brigada does and the rules it enforces. What and why: [product.md](product.md). Terms: [glossary.md](glossary.md).

## 1. Principles

1. **The foreman decides; the engine enforces.** Judgment (planning, answering, re-planning) is an LLM worker (the foreman, §4). Mechanics (queues, leases, eligibility, caps, routine retries) are deterministic Go code.
2. **The engine is the mailbox.** The foreman and the task workers never talk directly. Every message goes through the engine, and every message is kept (§9).
3. **No state lives only in a session.** Any session, the foreman's or a task worker's, can die at any moment; the engine and the plan file hold everything needed to continue.
4. **Prompts: templates plus verbatim data.** The engine composes a prompt only from fixed, versioned templates plus verbatim data (a task spec, review text, check output, a foreman answer). Verbatim data is always wrapped in explicit data delimiters, so one worker's output can't pose as instructions to the foreman or another worker. Anything that needs judgment goes to the foreman. **The one other input that is not data is a user message** (§4.2 item 3): the user's own words, sent through the client API, reach the foreman as a request to act on, in their own section and never inside an event's. Only a `client` or `admin` token can send one, which stops a worker or a foreman turn from *posting* one. Delimiters stop the rest: in the foreman's prompts the engine neutralizes the delimiter tags (`<event>`, `</event>`, `<user-message>`, `</user-message>`) inside any verbatim data it wraps, so no data can close its section and open another; the worker prompts' delimiters get the same treatment.
5. **Remote-ready** (product §5): clients only through the API, runners only through the lease protocol, tokens everywhere, repos by URL, self-contained state.

## 2. Processes

| Process | What | Local (launch) | Remote (backlog) |
|---|---|---|---|
| `brigada` (client) | CLI: chat, ask, status, history, stats, cancel, restart, review, budget, recover | your terminal | any device |
| engine | API, store, rules, dispatcher, foreman wake-ups | background process, started on demand | a server |
| runner | leases jobs, runs agent CLIs, runs checks | same host, separate process | any host with logged-in CLIs |
| foreman session | a brigada-owned session: headless turns woken by events, your chat through `brigada attach` (§4.2), one transcript | headless turns started by the runner, the attach by you, both in the project's reading checkout under the state directory | same |
| worker session | a **worker**: one instance of an official CLI, a harness plus a model, running headless. A task worker runs one task; the foreman is a long-lived worker (§4) | started by the runner | same |

The client, engine, runner and the MCP bridge (`brigada mcp`, §12.2) are the one `brigada` binary in different roles. The harness CLIs are the vendors' own official binaries, which brigada drives headless or which host the bridge as a child process; they are never the `brigada` binary.

## 3. Communication: the engine as a mailbox

```
 you ⇄ foreman ──tools──▶ engine ◀──lease/result── runner ──▶ worker CLI
            ▲                │
            └──── events ────┘  (judgment events wake the foreman)
```

- **Down:** the foreman calls tools (create a plan, add tasks, answer, restart). The engine turns ready tasks into jobs; a runner leases a job and starts the worker.
- **Up:** a worker can't message anyone mid-run. It ends its job with a structured result (§5.4). The runner adds the check result and progress data. The engine records it as events.
- **Routine events are handled by rules, judgment events go to the foreman:**

| Event | Handled by | Action |
|---|---|---|
| check failed, rounds left | rule | fix round: same session, template + check output |
| review "changes", rounds left | rule | fix round: same session, template + review text |
| transient error (CLI crash, server error, lost runner) | rule | retry the job, capped; a fetch that could not reach the remote arrives as error kind `infra` (§5.1), a failed setup as `setup` (§5.7). An `infra` or `setup` retry waits a growing not-before delay before it may be leased (5s, 15s, 45s, 2m, capped): the network is not up in the second after a wake, and the delay grows per consecutive failure, so an outage is waited out rather than hammered every second. A work job's first transient failure restarts once on another ready agent (§5.6); a fix round's transient failure retries the round once |
| a dependency is done | rule | the dependent task becomes ready |
| quota limit hit by a worker | rule | cool the account (§8); re-dispatch to another eligible agent as a **fresh** attempt (on the task's next `-r<n>` branch, §6.4) carrying the previous job's summary if it produced one, else its last progress events (a session can't move between agents), counting toward the task's attempt caps; with no eligible agent in any tier (§8), after the queue timeout the task parks and the user is notified when notifications are enabled (§10) |
| worker `needs_help` | **foreman** | answer → next job on the same session, or re-plan |
| task out of rounds or retries | rule, then **foreman** | the tier escalation of §8 first, while the task is below heavy and its attempts are not spent; then the foreman: re-plan, switch agent, split, or ask the user |
| worker stalled (§5.6) | **foreman** | restart with a new instruction, switch agent, or ask the user |
| plan held by a rule at the plan gate | **user** | approve, edit or reject (§6.3) |
| task approved, dependencies landed | rule | a `land` job, unless a rule holds the task at the land gate → **user** (§6.3, §7.1) |
| landed, check on the result passed | rule | push, unless the push gate is `ask` → **user**, or `never` (§6.3, §7.1) |
| land conflict, or the check failed on the landed result | **foreman** | nothing is pushed; restart the task with a note (rebase onto the new target head, resolve), re-plan, or ask the user (§7.1) |
| foreman limit hit (§4.4) | **user** | wait, switch foreman, or continue without it |
| job finished with `discoveries` (§5.4) | **foreman** | read them on the next turn as verbatim data in delimiters (§1.4); then `plan_amend`, put the fact into the spec of a task that hasn't started, or ignore it |
| plan done | rule | notify the user directly (§10); the foreman may add a summary on its next turn, skipped when it's `limited` or out of budget |

The transient retry is once per failure, and the one set of transient error kinds — `limit`, `auth`, `other` (a server error), `runner_lost` — is read in one place by both jobs. A work job's first transient failure restarts the task once on another ready agent: a fresh attempt on a new `-r<n>` branch carrying the failed job's last progress (§5.6). A fix round's transient failure retries the round once, resuming the author's session on the author's agent when that agent can still take it, else on a fresh session on another agent of the tier with the round's feedback — the check's output or the review's findings — in its prompt and the task's branch under it. The retry spends no fix round (the round was never attempted), is gated by the same restart budget the work retry uses, and waits out the same not-before backoff's first step (5 s) before it leases. A second transient failure parks the task at `needs_foreman`, as a non-transient failure does at once; `task_auto_retry = false` parks transient failures at once.

## 4. The foreman

**The brigada-owned headless foreman is a worker.** The *foreman role* is logical: the project's single decision authority, exercised by this headless worker, which the user also joins interactively through `brigada attach` (§4.2) — the same session, not a second conversation. The rest of this section and §4.1 describe the headless worker. A worker is an instance of a headless harness plus a model (§2); what it does comes from its instructions, permissions and lifecycle. The foreman runs on the same machinery as any other worker: an official CLI driven through the same adapters (§5.2), with headless resume, transcripts, quota and limit detection, and stall handling. A headless foreman turn is a job (kind `foreman`, §11). Where task-specific rules say "worker" (§3, §5.3–5.5, §7, §8), they mean a task worker: the foreman job is excluded from dispatcher scoring, quota re-dispatch, review routing and the runner's checks; its harness and model are fixed by the user, and its limit goes to the user (§4.4). It differs from a task worker in three ways:

- **Instructions:** the foreman instructions, where a task worker gets the worker instructions (the result block of §5.4, `needs_help`, check discipline, no dispatch tools).
- **Permissions:** the `foreman` token, scoped to its project (plans, answers, restarts), where a task worker runs under the runner token with no plan scope (§12.1).
- **Lifecycle:** one long-lived resumable session per project (`foreman:<project>`), with harness and model chosen by the user, woken by events and attachable — one session for the headless turns and the attached chat (§4.2). A task worker's jobs all belong to one task and one session (`task:<id>`), its agent picked by the dispatcher.

Task workers never get the foreman instructions. A task worker that thinks its task should be split returns `needs_help` with a proposed split, and the foreman decides.

### 4.1 What it is

- An official CLI session, **harness and model chosen by the user**, e.g. Claude Code with a given model, with brigada's MCP tools (§12.2) and the foreman instructions (a versioned file included in the binary). The user chats with it through `brigada attach` (§4.2), which joins this session; the foreman's turns, headless and attached alike, run in the project's reading checkout under the state directory (§2), so the repository's own instruction files and project memory load as in any clone.
- One foreman per project (repo). Its session is a **resumable session key** `foreman:<project>`. The harness must support headless session resume; setup refuses a harness without it.

### 4.2 Two ways in, one session

`brigada attach` is the interactive foreman, joining the same session the engine wakes headless, so the chat and the headless turns are one transcript.

1. **You chat:** `brigada attach` (a bare `brigada` runs it) joins the foreman session through the harness's own interactive resume.
   - The session runs in the project's reading checkout (§4.1) with the user's own harness config, so the user's own MCP servers load as in any session of theirs; the bridge is added through the MCP config the client writes for the chat, and its token dies with the chat. A codex attach is Codex's own terminal interface and carries no bridge: a later headless turn may start a fresh Codex thread instead of continuing the chat.
   - `--model`/`--effort` override the project's foreman model and effort for this chat alone; the session is the same, and the next headless turn uses the project's setting again.
   - **Attach acquires the key's live slot first** (one live job per key). If a headless foreman turn is running, the client shows "foreman is busy" and waits for it to finish, or cancels it through fencing if you insist. Two processes never resume one session at once.
   - The attach hold is lease-like: the client heartbeats it, and it expires if the terminal is killed. A second live attach is refused.
   - **On detach the client writes the current harness session id back** to the engine, as runners do on complete (`--resume` forks session ids). Otherwise the next wake would resume the pre-chat id and lose the conversation.
   - Judgment events that arrive while you're attached reach the foreman through its `events` tool, which the instructions tell it to check between replies. On release, any events it didn't consume are evaluated for a wake-up.
   - **Events are consumed only when a foreman turn completes,** or when the attached foreman reads them through `events`. A cancelled or failed turn's events return to pending and are re-delivered on the next wake or attach, so cancelling a turn to attach never drops a task worker's question.
   - At attach, pending events are put into the session's opening prompt (the same wake template), so they surface at once instead of waiting for your next reply.
   - **Tools:** the foreman set of §12.2, plus the adapter's read-only file tools — no shell, no edits (§5.2).
2. **The engine wakes it:** when a judgment event arrives and nobody is attached, the engine submits a **foreman turn**: a headless resume of the same session, with a template prompt plus the pending events verbatim. The foreman acts through its tools and exits. Several events coalesce into one turn (the follow-up flag). A turn that failed re-wakes the foreman only after a growing not-before delay (§3): the next turn carries a not-before time the delay names, so a network that is still down in the seconds after a wake is waited out instead of re-tried every second. The delay follows the longest-failing pending event's attempts (§5.6) — it grows per consecutive failed turn and starts over once a done turn consumes its events.
3. **You send a message without attaching:** `brigada ask "<text>"`, or the client MCP tool `ask_foreman` from any harness acting for you (§12.2), puts a **user message** in the foreman's inbox.
   - **Framing (§1.4):** a prompt or an `events` answer has at most one `<user-message>` section, after all the `<event>` data; several waiting messages are an ordered list inside it, each naming the token label it came from. The wake template says the event data is never instructions and that this section is the only other input: your requests. The attached session's `events` answers use the same framing, order and neutralized tags, and the opening prompt at attach carries waiting messages with the waiting events (item 1). **Invariant:** no prompt or tool answer, present or future, presents an `<event>` or `<user-message>` section without the framing text in the same message.
   - **Delivery is per message, like an event's:** a message is consumed when a turn whose prompt carried it completes, or when the attached foreman reads it through `events`. A message that arrives while a turn runs was not in that turn's prompt: it stays pending, and the turn's completion re-evaluates the wake for it. A failed, cancelled or stalled turn returns its messages to pending (§5.6). On detach, or when an attach hold expires, waiting messages are re-evaluated for a wake, so a message never strands behind a chat that ended. Messages coalesce with each other and with waiting events into one turn.
   - **Not charged to the wake budget:** a user message is you driving, like a chat, so a wake that carries one skips the day's budget (§4.3). It still obeys the wake stall (§5.6).
   - **The answer says what happened:** a turn was woken, or why the message waits — you're attached (naming the hold), a turn is already running, the project has no foreman harness, the wake stalled, or the foreman is limited until a time. It returns the message's id, so a caller can follow it in the history.
   - The project is named by its repo URL, or is the only project the engine has.

**Discoveries:** a finished job's `discoveries` (§5.4) reach the foreman on its next turn as verbatim data inside the `<event>` delimiters (§1.4), like any worker text. The foreman decides what to do: amend the plan (`plan_amend`), put the fact into the spec of a task that hasn't started yet, or ignore it. The engine never forwards them into another worker's prompt; only the foreman's decision can.

Your next *attached* chat sees everything the foreman did while you were away, because it's the same session, and the history (§9) has it too.

**Session rotation:** the one session only grows, and every turn rereads it. Nothing lives only in the session (product.md), so the engine starts a fresh one when it gets large: before submitting a headless turn or starting an attach, if the last finished foreman job of the current session generation reported input tokens (cached reads included, as the adapters count them; the cached count alone when input is unknown) above the project setting `foreman_rotate_tokens` (default 400000, 0 = never), it clears the `foreman:<project>` session id and bumps `projects.foreman_session_gen` in the same transaction, and logs `foreman_session_rotated` with the token count and the threshold. Never while a foreman turn is live or a hold is attached, and never on unknown usage. Only a job of the current generation counts, so one crossing rotates once. The first turn or attach of the rotated generation — until one of them writes a session id back — carries an engine-written digest in the wake template, between `<digest>` delimiters as data (§1.4): the plans active or awaiting approval with their tasks' states, the needs-you entries with reasons, the last 10 history events, each list bounded with the omitted count and the whole cut at about 10 KB. A model or effort change on the same harness keeps the session.

### 4.3 Budget

Foreman turns while you're away use your subscription. A per-project budget of foreman wake-ups per UTC day bounds them: the built-in default is 20, the config file's `foreman_wakes_per_day` sets the default for every project, and `brigada budget [--repo URL] --wakes N` sets one project's budget for the day — a local project setting (`foreman_wakes_per_day` through the settings path, refused in the shared project.yaml, which names local-only keys by that rule). When it runs out, judgment events wait for you, and visibly: one `foreman_wake_budget_spent` event per project per budget window records the count and the window's end, a notification is raised (§10), and the needs-you queue in `brigada status` shows the entry — the use, the reset time, the events waiting — while events wait, gone when nothing waits, the budget is raised, the day resets at UTC midnight, or an attach holds the foreman's slot (the budget limits headless wakes only; the attached chat reads the waiting events with `events`). Raising it re-evaluates the waiting events' wake at once. A wake that carries a user message (§4.2 item 3) is not charged: the budget bounds the foreman reacting to events on its own, not you asking it something, which is as attended as a chat.

### 4.4 When the foreman hits its limit

The runner detects the limit-hit error from the foreman's CLI. The engine marks the foreman `limited(until)`, or `limited(unknown)` when the error carries no reset time, stops waking it, and **notifies the user** (§10), who chooses: wait for the reset, switch the foreman's harness or model (the new session rebuilds its context from the engine, per product §4's kill-and-rebuild test), or let approved plans continue without it. Routine rules keep working throughout. When the same account also serves task workers, a foreman limit-hit cools that account in the dispatcher (§8), and a worker limit-hit on that account stops foreman wakes until the reset.

### 4.5 Capacity

The foreman instructions tell it to check `capacity` (§12.2) when it plans, and to use it to choose how wide the task graph is, when to sequence instead of fanning out, which tasks can wait for a cheaper agent, and to give honest time estimates ("3 tasks now, 2 after the reset at <time>"). The engine stays binding: if the foreman's view is stale, the dispatcher queues the extra tasks and never exceeds a cap (§8.1). The foreman decides; the engine enforces (§1).

### 4.6 The coordinator bridge

A session opened in a folder holding several repositories gets the **coordinator** tool set (§12.2) over every project the engine knows, through `brigada mcp --coordinator`: list projects, ask a project's foreman, approve or reject plans, and read status and history across projects. Each project keeps its own foreman for plan mechanics: the coordinator has no `plan_create`, no `plan_amend`, no task mutation and no hold tool. Projects are named by canonical repo URL (§13.1); a monorepo is one project. Cross-project plans do not exist: a coordinator sends separate requests, one per project, through `ask_foreman`, and each project's foreman plans on its own. Init in a non-repo parent folder registers the repositories it discovers and wires the coordinator into the folder's `.mcp.json` (§13.1).

Approval is the user's act. `plan_approve` and `plan_reject` use client authority, never a foreman credential, and take the plan id and the plan version the user was shown, so an amendment made after the user looked invalidates the call. The engine's "awaiting approval" is a result to present, not a permission: the coordinator instructions tell the coordinator to show the plan and wait for the user's explicit yes in chat, and the harness's own per-call permission prompt for the two approval tools stays on "ask" — init never pre-allows them. The user approves through the client path (the `brigada` command, or a coordinator session), never through the foreman tools.

## 5. Workers and runners

### 5.1 Runner

- Registers with a runner token and advertises its adapters: harness, models, family, account label, classes it can take (product §5 rule 5). An agent is one (harness, model, account): a runner offers several models of one harness as several agents, `--agent` once per model, with each agent carrying the tier of §8.
- Leases jobs (long-poll), heartbeats with progress, completes with a fencing token. Lease expiry plus fencing make crashes safe.
- Materializes its own workspace: clone or fetch the repo URL with its own git credentials into a per-task worktree, and push result branches to the remote (product §5 rule 6).
- A fetch of the remote that fails — the mirror's, the worktree's own (a base or result branch fetched by name), the foreman checkout's — completes the job with an error of kind `infra`: right after a wake the network is not up for a few seconds, and `Could not resolve host` is the runner's plumbing, never the task's failure nor the worker's. The engine retries it as a transient error (§3), capped, charging neither a round nor the agent's health, as a failed setup is retried (§5.7); a foreman turn that fails this way is tried again by its next wake.
- A CLI that could not be built or started — the worker's, the reviewer's, the foreman's — completes the job with the same kind `infra`: a command that never ran is the environment's failure, not the agent's, so it never counts toward the failure streak, and a work job so failed is retried like a fetch failure above.
- The worktree path is session-stable: a task job runs at `worktrees/task-<task>-<role>-s<gen>` — role `author` for the work and fix jobs, `review` for the review jobs — and the generation is the one the engine stamps on the lease in `jobs.session_gen`: the attempt, counted in the task's restarts, the same count that names the attempt's branch. A harness session belongs to the directory it started in — opencode resumes only there — so the fix round that resumes the author's session runs where the work job started it, and a resumed re-review where its review did. A restart moves the generation, so a fresh attempt never reuses the directory of the session it does not resume. At most one live job holds a task's key (§12.1), so the path is never shared by two live runs of one runner: a leftover directory from a crashed run is discarded before the worktree is added, and a re-leased job waits for the run that lost the lease to take its worktree down. A task-less review keeps the per-job path (`worktrees/job-<id>-a<attempt>`): no session ever resumes there (§7: a review writes no session back). Foreman turns are unaffected — their checkout is their own (§4).
- Starts each CLI with its working directory and its `PWD` set to its worktree (the foreman's reading checkout for a foreman turn, §4), replacing the runner's own `PWD`, because some CLIs, opencode among them, read `PWD` before the working directory.

### 5.2 Adapters

One per CLI: build the headless command (fresh or resume), parse the CLI's event stream into progress events, detect limit-hit and auth errors, find the session id for resume. The adapters reuse Apache-2.0 code from Orchestrator.inc, keeping upstream license headers, carrying their NOTICE and marking modified files. The claude adapter's default worker scope allows exactly `go build`, `go test`, `go vet` and `gofmt` — the worker compiles and tests its own work as it goes; the runner still runs the check, so no new code reaches execution — and an agent config's explicit tool scope replaces the default.

### 5.3 The worker prompt

A fixed worker template (versioned) plus the task spec verbatim, plus the answer or feedback for follow-up jobs. The template tells the worker to end with the result block (§5.4). A project may add its own instruction text, injected as verbatim data in its own delimiters after the template's contract and before the task spec (§5.9).

Both templates carry a short "Work economically" paragraph. A work job's tool output totals only 100-400 KB, but it makes 60-150 tool calls and every call resends the whole conversation, so it processes 3-18M tokens. The worker paragraph says: prefer few large steps; plan edits to a file and make them in as few as the tools allow; read a file to change once, and search a large document for its heading instead of reading it in slices; use one combined search pattern; run only the tests that cover the change, never the whole or the race suite, since the runner runs the full check; fetch nothing from the web unless the task asks. The reviewer's shorter paragraph says: read the diff first and open only what it touches.

### 5.4 Worker result contract

The worker's final message ends with one JSON block:

```json
{"status": "done" | "needs_help" | "failed", "summary": "…", "question": "…", "branch": "…", "discoveries": "…", "commit_message": "…"}
```

`discoveries` is optional. It holds facts the worker learned that matter beyond its own task: an API quirk, a flaky test, a wrong assumption in the plan, something a later task will trip over. An absent or empty field means none. A review's verdict block (§7) and foreman turns don't carry it. Workers never message each other, and the engine never forwards discoveries into another worker's prompt on its own. Only the foreman's decision can carry them (§4.2).

`commit_message` is optional. It holds the commit message the land job commits the work with: one subject line, a blank line, then the body, written in the repository's own commit style — which the worker reads from the project's instructions (§5.9) and the log. The land job and `brigada land` use it as the message's subject and body under the same bounds and data rules as their own (§7.1); its trailers are never the worker's to write. An absent, empty or subjectless field is no error: the land job builds the message as it does without one. Like every field it is data, kept with the job's result message; a review's verdict block and foreman turns don't carry it.

A missing or malformed block counts as `failed` with reason `no-result`. The runner verifies the branch was pushed.

The contract binds task jobs (`work`, `fix`, `review`, §11); a review job's block is the verdict block of §7. A foreman job is exempt: its turn's output is its tool calls (§12.2), and ending without a result block is not `failed`. On `needs_help`, `question` carries the question or a proposed split of the task; the foreman answers it or re-plans through `plan_amend` (§3, §6.2), so the split needs no field of its own.

### 5.5 Checks run by the runner

After the worker exits with `done`, **the runner runs the task's check** in the worktree, not the worker. Exit code plus the output tail are the check result. That keeps the outcome record honest (a self-reported check would bias it).

### 5.6 Stalled workers and restart with a new instruction

Workers sometimes get stuck: alive, but making no progress.

- **Detection:** the adapter turns the CLI's event stream into progress events (tool calls, messages); the runner sends the time of the last one in each heartbeat. **Stalled = 10 minutes with no activity at all** (`stall_minutes`, configurable). A tool call in flight (a long build or test run) suspends the clock, bounded by its own `tool_call_cap_minutes` per class (default 30). Stalled, or the class time cap reached → the runner kills the process tree and completes the job with the outcome `stalled` or `time_cap`; either ends the job in the terminal `stalled` status, and the result block names which, with the last progress events attached.
- A stalled job **always goes to the foreman**; there is no automatic nudge.
- A stalled foreman turn is killed and completed like any stalled job, but never routes to the foreman itself: its unconsumed events return to pending and are re-delivered on the next wake or attach (§4.2), the engine may wake it again while wake-up budget remains (§4.3), and the user is notified when it stalls repeatedly or the budget runs out.
- **Restart:** `restart(task, instruction, mode, agent?)` cancels any live job and creates a new job on the same task with the new instruction.
  - `mode=resume`: same session, the instruction appended (the worker keeps its context);
  - `mode=fresh`: a new session, the instruction plus the previous job's summary and last progress (for a worker stuck in a loop);
  - optional `agent` to move the task to another agent.
- **Who restarts:** the foreman (a judgment event), or the user directly: `brigada restart <task> -m "…" [--fresh] [--agent …]`. A restart is a new attempt on the task and counts toward its attempt caps. A resume that fails (the session is gone or forked) restarts fresh in place.
- **A host sleep does not end a hold.** The engine and its runners sleep together; the engine notices its own suspension (§13) and restarts the lease and every other wall-clock deadline from the wake, so the runner's first heartbeat after wake answers `ok` — never "the engine ended our hold" — and a live worker is not killed for the laptop's silence.

### 5.7 An environment for checks and reviews

A worktree is a fresh clone (§5.1), so it has no `node_modules`, no Python virtualenv, no downloaded modules. A check such as `npm test` or `pytest` fails there for want of dependencies, not for want of working code. A check that installs dependencies on every job, or one that names a path on the host, breaks product §5 rule 7 (a check is repo-relative and host-independent, because it is recorded as task data). The environment is therefore a step of its own: the project's `setup` command.

**`setup`.** A project may set `setup` in `.brigada/project.yaml` (§13.1), a repo-relative command. Schema 1 of the file spells its fields as sibling keys, `setup` (the command), `setup_cache_key_files` and `setup_timeout_minutes`, each a project setting with the provenance of the others (`project show`, `project set`, import); a nested `setup:` map is refused like any nested structure. The engine copies the effective setting (command, key files, timeout, source and imported-file hash) into `tasks.setup` when a task is created by a plan, an amendment or a submit; a lease grant carries the task's record, and a review job with no task the project's setting.

- **When it runs.** The runner runs it as `sh -c` in the task's worktree, as the runner, with the runner's own environment plus `BRIGADA_CACHE_DIR`, in its own process group (killed whole on the timeout), in two places: before the worker starts (work, fix and review jobs), and again before the check. A review job (§7) gets the same environment. The command is the project's recorded setting, never read from the worktree at run time (the same rule as the check, §5.5, and the default check, §6.1). A later change to the project setting does not alter a recorded task.
- **What "again" means.** The worker may have changed a lock file or a script the command calls, so the runner always runs the command a second time; it does not skip it on a guess. The command must be idempotent. When nothing it depends on changed, the cache key (below) is the same, the cache is hit, and the second run is cheap: it finds its inputs in the cache, links or unpacks them into the worktree and exits. When the worker did change a named key file, the key differs and the second run is a cold install, paid before the check and not stored (below).

**Caching.** The cache exists so that a job does not download the world again, and is a convenience of the runner, never part of the task record.
- **What it holds.** A directory the setup command fills through `BRIGADA_CACHE_DIR`, an absolute path the runner sets in the command's environment: package downloads, a module cache, a wheel cache. The command decides how to use it (`npm ci --cache`, `UV_CACHE_DIR`, `GOMODCACHE`). The runner never looks inside.
- **Key.** A hash of the contents of the files named in `cache_key_files` (for example `go.sum`, `package-lock.json`, `uv.lock`; the project names them, brigada guesses nothing), of the command text, and of the runner's OS and architecture. A named file that is missing hashes as absent. With no `cache_key_files` there is no cache and the command runs cold every time.
- **Where.** In the runner's state directory, under the canonical repo URL (§13.1 item 1) and then the key: `<state>/setup-cache/<repository mirror>/<key>`. Never in the worktree, never in the repo. An entry is never shared across repositories, since two repos could otherwise read each other's dependencies, and never across runners, since the cache is local files of one host and a remote runner (product §5 rule 5) has its own.
- **How a job gets its copy.** Per job, by copy: before the first setup run the runner copies the entry for the key into a directory private to the job (`<state>/setup-jobs/job-N-aM/cache`, a clone-on-write copy where the filesystem allows it) and sets `BRIGADA_CACHE_DIR` to that copy. A job writes only into its own copy. The entry is replaced only by the **first** setup run of a job (the one before the worker starts), and only if that run succeeds, by an atomic rename. The second run (before the check) and every run after a worker has touched the worktree never update the shared entry. So a worker that writes bad bytes into `BRIGADA_CACHE_DIR`, or edits what setup calls, can spoil its own job at most, never the next one.
- **Invalidation.** A different key is a different entry, so a changed lock file never reuses a stale one. Entries unused for 30 days, or beyond the three most recently used per repository, are removed by the runner.

**Tool scope.** Setup runs as the runner, not as the worker, and its commands are not bound by the worker's `tools=` scope (§5.2). That scope keeps bounding what the worker itself may run: setup does not widen it, and the worker cannot trigger a setup run or choose its command. Setup's output is data, never an instruction: it is kept in the log and may be shown to a reviewer or the foreman only inside the data delimiters of §1.4.

**Failure.** A setup that fails (exit code non-zero, or the timeout) is an infrastructure failure of the job. It completes the job with an error of kind `setup` and the message `setup failed: exit code N` or `timed out after D`, never the output. It is not a failed check, so it starts no fix round, and not a worker failure, so it does not count against the task's attempt caps for the agent. The engine retries a failed work job up to twice on any eligible agent, as a transient error, charging neither a restart round nor the agent's failure streak; a fix job, a standalone review or a spent retry count goes to the foreman (a review gets its one retry on another reviewer as for any error). Each retry waits a growing not-before delay before it may be leased — 5s, 15s, 45s, 2m, capped — so a network outage right after a wake is waited out rather than retried every second, the same delay the foreman's re-wake uses (§4.2). The log of every setup run is an artifact of kind `setup_log`, linked as `setup_log_id` on the job, next to the check log, so the foreman and the user can see why. The time bound is `timeout_minutes`; the stall clock (§5.6) does not run during setup, which is bounded by that timeout alone, and a timeout kills the process tree.

**Trust and what stays out.** Setup commands come from the repo's own committed `project.yaml`, so they run repo code on the runner, with the user's shell and credentials (product §6, "what local gives up"). That is the trust a check already asks for: the check runs repo code the worker may have changed, in the same shell. Setup adds no new kind of exposure, but it adds a second occasion, and one before the worker starts: its command is the imported project setting, so changing it needs the same explicit import as any setting (§13.1), and a worker that edits a script the command calls takes effect at the second run, as for a check. Containers and per-job credential injection stay in the backlog (product §6); until they land the answer to untrusted repo code is the one product §11 gives, which is to document it.

### 5.8 A second repository in a task's worktree

Some tasks need to read another repository: a shared schema, a generated client's source, a sibling service whose code the check builds against. A task still changes exactly one repository (below); the extra ones are context.

**Naming them.** A task may carry `extra_repos`, a list of entries:

```yaml
extra_repos:
  - name: schema                 # [a-z][a-z0-9_-]*
    repo: git@example.com:org/schema.git   # canonicalized as in §13.1 item 1
    ref: v2.3.0                  # branch, tag or commit; default: that repo's default branch
```

The URL is canonicalized as the project's is (§13.1 item 1), so SSH and HTTPS forms of one repo are one entry and a token in a URL is dropped. A commit SHA is the only reproducible ref: a branch or tag moves. The runner records the commit it resolved in the job record, so the history shows what the job saw, and the plan shown for approval says when a ref is not a commit.

In the shared file and in `brigada project set`, the entry is spelled as one string, `name url [ref]` (`extra_repos="schema git@example.com:org/schema.git v2.3.0"`; several entries are a YAML list, or joined by `+` on the command line, so a URL holding `+` cannot be spelled there). A nested `extra_repos:` map is refused like any nested structure. The file's URL is not required to be in canonical form, unlike `repo`: it has to be fetchable, so the engine canonicalizes it and keeps the credential-free transport URL beside the identity, and a bare `host/path` is refused as the project's own is. `plan_create` and `plan_amend` take the field as `extra_repos: [{name, repo, ref}]`; omitted inherits the default, `[]` or a list replaces it entirely (an entry with a default's name is simply the task's own).

**Where and what variable.** The runner checks each one out beside the task's worktree, at `<task worktree>.extra/<name>`, a stable path inside the runner's state directory and never in the main worktree, so nothing it holds can be committed by accident. For each entry the runner sets an environment variable naming the absolute path, for setup (§5.7) and for the check, and also for the worker: `BRIGADA_REPO_<NAME>`, where `<NAME>` is the entry's `name` uppercased with `-` turned into `_`. A check says `go test ./... -schema "$BRIGADA_REPO_SCHEMA"`, so the recorded command stays repo-relative and host-independent (product §5 rule 7): the path comes from the runner at run time and is never in the task data. Two entries in one list whose names give the same variable (`a-b` and `a_b`) are rejected when the task is created, never silently dropped. An entry that clashes with the project default's name replaces it (below). A name that would give a variable the runner itself sets (`BRIGADA_CACHE_DIR` and the like) cannot occur, because the prefix `BRIGADA_REPO_` is reserved for this use.

**Read-only, never pushed.** The checkout is read-only for the worker, and the runner never pushes it: it is cloned with no push remote, and the files are made read-only for the job's user. It is a convention plus a read-only checkout, not a sandbox. The worker's tool scope (§5.2) is what keeps a claude worker away from it by default, since the default scope runs only `go build`, `go test`, `go vet` and `gofmt`; a worker with a shell or a wider scope runs as the same user and could change the permissions and the files. Whatever it changes is discarded, because the checkout is deleted with the worktree and is not a branch the runner pushes. Real enforcement is a container's read-only mount (product §6). The runner needs read access to each extra repository with its own git credentials (product §5 rule 6); an entry the runner cannot fetch is an infrastructure failure of the job, handled like a failed setup (§5.7), not a failed check. The runner clones each entry to `<state>/worktrees/<worktree>.extra/<name>` (the job's worktree path plus `.extra`, so the session-stable paths of §5.1 carry their extras beside them), checks out the ref (a branch, tag or commit; empty is the default branch), removes the `origin` remote, and clears the write bits of every file and directory; it exports `BRIGADA_REPO_<NAME>` (absolute path) to the setup command, the worker (after the git-credential scrub) and the check, and a review job gets the same checkouts. The directory goes with the worktree (the startup sweep makes it writable first). A clone or ref that fails completes the job with the error kind `setup` and the message `setup failed: extra repository <name> could not be checked out` (git's output goes to the runner log, redacted), so it is retried like a failed setup. The commit each entry resolved to is in the work job's result block as `extra_repos: {name: sha}`, set by the runner over anything the worker wrote.

**How a plan names them.**
- **Per task:** the `extra_repos` field in `plan_create` and `plan_amend` (§12.2), part of a task's fields (§6.1), with the shape above. Omitted: the task inherits the project default. Given, even as `[]`: it replaces the default entirely, except that an entry with the same `name` as a default one wins over it.
- **Project default:** `extra_repos` in `.brigada/project.yaml` (§13.1), for repositories every task needs, with the same shape. It is a nonsecret repo-level setting like the default check.
- **Resolution** happens once, when the task is created or amended, as for the default check (§6.1): the engine resolves it in `plan_create`, `plan_amend` and the debug submit and copies the effective list into `tasks.extra_repos` (entries with identity, fetch URL and ref, the source `task` or `project-default`, and for a default the hash of the imported file); the lease grant carries the record, a task-less review the project default. A name that is invalid, a repeated name, two names giving one variable, a ref that starts with `-` or holds white space, and an unusable URL refuse the plan or amendment whole. A later change to the project default never alters a recorded task, and the task can be run again as it was. The plan file mirror writes `extra_repos: [["name", "repo", "ref"], ...]` on a task that has some, the canonical identity and never the fetch URL; a file with none is unchanged, and recovery from a plan file does not restore the field.
- **Approval.** The plan shown for approval (§6.3) lists each task's extra repositories with their refs, and the list is in the recorded task. A task that names a repository outside the project's default `extra_repos` is a reason to ask, since it widens what the runner reads with the user's git credentials; the project default itself was imported by the user (§13.1) and is not. An entry whose canonical repository is not among the project default's is a reason to ask, even when approval is otherwise unchanged by it (`approval_max_tasks` negative still turns the whole limit off); the reason lists each such entry as `name (repository, ref R, not a commit)` or `(repository, commit SHA)`, in the answer, the `plan_awaiting_approval` event and so `status`. On an amendment only the added tasks are judged, each task's own list included, as for classes and protected paths.

**What it does not decide.** A plan spanning repositories, tasks that *change* two repositories, stays out of scope (§16 item 7). `extra_repos` does not answer that question and must not be read as the first step of an answer. It only supplies read-only context to a task that still changes exactly one repository: one branch, one repo URL, one project and foreman, one set of pushed branches. Write access to an extra repository, a task that pushes to it, or a task that waits for another's branch is a different design.

### 5.9 Project instructions for every worker

Workers run official CLIs, and each reads its own harness's project instruction file: `CLAUDE.md` for Claude Code, `AGENTS.md` for Codex and others. A rule written for one harness never reaches a worker of another family, so the same project gets different behaviour from different agents. The project therefore has one **instruction text** that brigada puts into every worker and reviewer prompt itself, whatever the harness. The key is `instructions_file`; the local override is the project setting `instructions` (`brigada project set instructions=@<file>`, `@-` for stdin, or the text itself); the foreman reads the text through `status` with `instructions` set.

**Where it comes from.** Two sources, both resolved by the client, never by the engine from a path (product §5 rule 1):
- **The file.** `.brigada/project.yaml` (§13.1) may set `instructions_file`, a repo-relative path to a markdown file (for example `.brigada/instructions.md`). The client reads it at import, as it reads the rest of the file, and sends the text over the API. The path must be relative, stay inside the repository after symlinks are resolved, and name a regular file; anything else is refused at import, naming the path. The engine stores the text, never a path to read. The file may be the repo's `CLAUDE.md` or `AGENTS.md`, but then a harness that reads that file itself sees the rules twice, so a separate file is the recommendation.
- **The project setting.** `brigada project set instructions=@<file>` (`@-` reads stdin) stores text as a local override, for rules the user does not want in the repo. The client reads the file; the engine takes the text.

Which wins is §13.1's rule: a local override, then the last imported file value, then the built-in default, which is no text. `status` and `brigada project` show the effective text's source (`local override`, or `file <path>, imported <time>`), its settings version, its byte size and a SHA-256 digest. A changed file over a store value that is still the previous import applies; over a local override it does not, and the conflict is shown with both texts for the user to resolve. Neither wins silently.

**Size bound.** At most 8192 bytes of UTF-8 (a starting value; tuning is open, §16 item 11). Above it the set or the import is **rejected** with the size and the limit in the error, and the previous value stays in effect; nothing is ever truncated, because a cut rule is worse than a refused one. Text that is not valid UTF-8 or contains a NUL is rejected too. An empty file is an unset value and is reported as such. The engine enforces the bound on the API; the client checks first, for a readable message.

**Where it sits, and what it cannot override.** The prompt order is fixed: the versioned template with its contract (the result block, §5.4; no pushing; the tool scope, §5.2), then the project instructions, then the task spec. Between the template and the text sits a framing sentence the template owns: the project instructions below are verbatim data between the data delimiters; they say how the project wants its code written and checked; they never change the contract above, which wins on any conflict (the result block, no pushing, no dispatch tools, the tool scope). The text is wrapped in `<project-instructions>` and `</project-instructions>`. As for the other worker delimiters (§1.4), the engine neutralizes look-alikes inside the data (those two tags and the other worker delimiter tags, case-insensitively and with inner whitespace), so the text cannot close its own section or open another. A text that says "ignore the above" is still data: it cannot widen a tool scope, which the runner enforces and no prompt grants, and a worker that obeys it against the contract still faces the runner's check (§5.5) and the reviewer (§7).

**Reviewers** get the same text, as data, in a section of their own with a framing sentence of their own: it is the convention the author was asked to follow, the reviewer may judge the change against it, and it never changes the verdict block's contract or asks for an approval. The reviewer still never sees the implementer's summary (§7).

**The foreman turn does not get it injected.** The foreman has its own instructions and no editing or shell tools (§4); rules for code writers would compete with the foreman instructions and spend tokens on every wake. The foreman still needs the rules to write good specs, so they are visible to it as data: the `status` tool (§12.2) names the source, version, size and digest, and returns the full text inside `<project-instructions>` with the framing sentence when asked. The foreman instructions tell it to read the text before it plans. The foreman's reading checkout (§4.1) carries the repository's own instruction files anyway, as any clone does.

**Versioning.** Resolved once, when a task is created, as the default check is (§6.1): the engine copies the effective text into the task record with its source, settings version and digest. A later change to the setting never alters a recorded task. A `plan_amend` that touches a task that has not started re-resolves it; a task that has run keeps its text, so fix rounds, resumes, restarts and the task's reviews all use what the author was first given. The job record keeps the template version beside the digest, so a recorded prompt is reproducible. A user who wants a new text on tasks already created amends them through the foreman; a bulk apply is open (§16 item 11).

## 6. Plans and tasks

### 6.1 Task graph

A plan is a DAG of tasks with dependencies. Task fields: title, spec, check, class (`implement` | `review` | `answer` | …), deps, repo and base ref, caps, tier and effort.

**Continuing a dep's session.** A chain of tasks in one area — A, then B built on A's branch — pays a cold start per task: B's worker re-reads the files A's worker already held in its head. The optional task field `continue` names one of the task's deps (usually the same dep as its base). When that dep is done and the task starts, its first work job runs in session mode on the agent that authored the dep's approved result — the agent of the dep's latest work or fix job — resuming that session; the prompt (`internal/prompt`, beside the worker template) says a new task follows in the same session: the previous task is approved and landed on the base branch, here is the new spec. Everything else — the check, the review, the rounds, escalation — is unchanged. `plan_create` and `plan_amend` (an added task, a retarget) validate the field as they validate `base`: it must name one of the task's deps, else the whole call is refused; and the continued dep is the task's base — a base naming another dep is refused, and a base none names defaults to the continued dep, so the work always starts from the branch whose session it resumes. The engine stores it on the dependency's edge, `status` shows `continues <dep>` beside the task, and the plan file carries it (§6.4). The continuation is a saving, never a requirement: the task starts fresh when the dep's author session id is unknown; when that agent is gone, broken, capped at 0, cooling beyond `longCooling` (§8) or outside the task's tier. A restart of the continuing task always starts fresh (§5.6).

**Tier and effort.** The foreman decides how heavy a model each task needs; the user configures the foreman's model and effort and which CLIs may run tasks (§13.1). Two task fields, both set by the foreman in `plan_create` and `plan_amend` and shown in the plan presented for approval (§6.3) and in the plan file (§6.4):

- `tier`: `light` | `standard` | `heavy`, default `standard`: how heavy a model the task needs. The dispatcher resolves it to an agent (§8). The engine keeps the foreman's `tier` and the `effective_tier` the task runs at, which escalation (§8) may raise; the plan file carries the foreman's value only.
- `effort`: `low` | `medium` | `high` | `max`, optional: how hard that model should think. This is brigada's own set, one per task, not a harness level. The runner maps it to the agent's CLI through the adapter's typed effort control (§5.2): claude and codex take the same word; opencode takes `minimal` for `low`, no variant for `medium`, `high` and `max`; kimi has no effort control and ignores it. The job record stores the level actually passed. Omitted, the agent's own `effort=` applies, else `medium`, resolved in this vocabulary before the harness maps it, so opencode (`medium` maps to no variant) and kimi (no control) still get nothing; a nonempty mapped task effort overrides the agent's (opencode `medium` still uses the agent's own variant when set), as the foreman effort does (`brigada project foreman --effort`, GUIDE §11: it rides the foreman turn's grant and overrides the serving agent's own level).

**Round caps.** The task's `caps` field overrides the engine's round budgets key by key: `fix_rounds` (fix rounds a failed check asks for), `review_rounds` (fix rounds a review's changes verdict asks for) and `restart` (restarts, §5.6), each an integer from 0 to 10; an absent key keeps the engine default. The engine defaults are 2 fix, 2 review and 3 restarts, set by `rounds.fix`, `rounds.review` and `rounds.restart` in the config file. `plan_create` and `plan_amend`'s `add` take it as an optional `caps` object per task; an unknown key or an out-of-range value refuses the whole call. `plan_amend`'s `retier` entries take `caps` too, for a `pending`, `ready` or `needs_foreman` task, merged key by key into what the task has, so the foreman can give a parked task more restarts before `task_restart`. The engine stores it in `tasks.caps`; `status` shows a non-default value beside tier and effort (`restarts 4`) and the plan file carries it (§6.4).

Neither tier nor effort is an approval trigger, and caps are not either (§6.3).

**Default check.** A task may omit `check` to inherit the project's default check (§13.1). Resolution happens once, when the task is created or amended through the engine: the engine copies the effective command into the task record with its source (`project-default` and the settings version it came from). A later change to the project default never alters a task that already has its check, so the recorded check stays reproducible, and the plan shown for approval (§6.3) carries the real commands, not a reference. The runner runs what the task recorded, never a value read from the worktree at run time (§5.5; product §5 rule 7). Omission is distinct from an explicit no-check override, which must be spelled out (`check: none`) if it is allowed at all (open, §16), and a plan containing one shows it plainly. A task that omits `check` in a project with no default is rejected at creation, never run unchecked.

Task states: `pending` (deps not done) → `ready` → `running` → `checking` → `reviewing` → `done`; or `needs_foreman`, `needs_user`, `failed`, `cancelled`. Cancelling a task cancels its dependents unless the foreman re-plans.

### 6.2 Plan lifecycle

`draft` (the foreman builds it) → `pending_approval` (above the limit) → `active` → `done` | `cancelled`. The foreman can amend an active plan (add, split, drop tasks); each amendment is recorded, and an added task is judged against the plan rules (§6.3).

### 6.3 Gates and rules

Approval only above a limit: more than 5 tasks, any task touching protected paths, or any task class other than `implement`/`review`/`answer`, configurable per project. The three keys `approval_max_tasks`, `approval_classes` and `approval_protected_paths` (§13.1) set it.

The loop — plan, work, check, review, land, push — is brigada's, and the user stops it with rules. The engine enforces every stop; the foreman has no tool to pass one, as it has none to approve a plan. There are three **gates**:

- `plan`: before a plan's tasks are queued;
- `land`: before an approved task is squashed onto the target branch (§7.1);
- `push`: before the target branch is pushed.

A gate is `auto` or `ask`; `push` may also be `never`, which never pushes the target: the commit waits on the remote's waiting ref as a push-gated landing's does, and the exact fetch-and-push command — runnable from the user's own repository — is recorded and printed, as the hand-driven `brigada land` prints its push. A **rule** turns `auto` into `ask` for the one plan or task that trips it, and the needs-you entry (§10) names the rule: `heavy; touches infra/**`. The rules are flat keys in `.brigada/project.yaml` (schema 1 is flat by design; no expression language):

| Key | Gate it holds | Default |
|---|---|---|
| `gate_plan` | — | `auto`; a tripped rule holds the plan |
| `gate_land` | — | `auto` |
| `gate_push` | — | `auto` |
| `approval_max_tasks` | plan | `5` (the default once landing is automatic is open, §16) |
| `approval_classes` | plan | `implement`, `review`, `answer` |
| `approval_protected_paths` | plan **and land** | none |
| `approval_tiers` | land | none (`heavy`: the user reads heavy diffs before they land) |
| `approval_restarted` | land | `false` (`true`: a task that spent a restart or a tier bump waits) |
| `land_target` | — | the project's default branch; or a staging branch such as `brigada/landed` |
| `after_land` | — | none: a repo-relative command the runner runs after a successful land, in the user's shell like a check (product §6); its failure is reported, never undone |

A gate set to `ask` holds in the needs-you queue, and `brigada plan approve` and the coordinator's `plan_approve` keep their roles for the plan gate; `brigada land approve <task>` and `brigada push approve` release the other two, and reject cancels the landing, leaving the branch. A held task blocks nothing but its dependents' landings: work on the rest of the plan goes on. A landing recorded for a held task — by its trailer on the default branch, or by its land job — clears the hold and its needs-you line. An amendment of an active plan is judged by what it adds: each added task is checked against the per-task rules — its class, the protected paths its spec or check mentions, its extra repositories — and one that trips a rule is held alone, parked with a needs-you line naming the rule, while the plan stays active and the rest runs on. The whole-plan triggers — the task count and `gate_plan` — never hold an amendment of a plan already running, and cancelling, re-pointing or retiering never holds.

### 6.4 The plan file in the repo

For fault tolerance, the engine writes each plan as **`.brigada/plans/<plan-id>.yaml`** and pushes it, on every plan change, to a separate branch **`brigada/plans`** in the repo's remote by default, so the engine never commits to `main` on its own; committing to the default branch instead is a per-project setting. The file holds the graph, task states, branches and open questions, not transcripts. The engine store is authoritative; the file is a mirror.

**Backups.** The engine also snapshots its store (SQLite backup API) daily to a configurable directory outside the store.

**`brigada recover`** when the store is lost:
- **Restores:** from the latest snapshot if there is one, then plans, task states, branches and open questions from the plan files (newer wins).
- **Doesn't restore** without a snapshot: messages, transcripts and outcomes; the dispatcher's scores restart from defaults. Said plainly in the command's output.
- **Tokens** live in a config file outside the store (the store keeps only hashes), so clients, runners and the foreman can still authenticate; runners re-register.
- **Fence epoch:** recover bumps a store-wide fence epoch, and every lease, heartbeat or complete that references the pre-recovery epoch is rejected, so a late runner can't write into the rebuilt store.
- **In-flight work:** recover waits one lease-expiry window before re-dispatching, so runners whose heartbeats now fail have killed their workers. Re-dispatched work does not get a new branch name; the rules below decide which branch each kind of re-dispatch works on.
- **Branch names:** a task's first job works on `brigada/task-<id>`, and the engine names each job's branch.
  - **Re-lease** (the lease expired or the runner crashed, and the same job is leased again): keeps its job's branch.
  - **Restart** (§5.6, either mode, or a re-dispatch to another agent): works on `brigada/task-<id>-r<n>`, where `<n>` counts the task's restarts.
  - **Fix round** (§3): continues the task's branch, the one its last job pushed, so the fix lands on top of the work under review.

## 7. Review policy

After an `implement` job is done and its check passed, the engine creates a review job for an agent of a **different family** than the author. The reviewer gets the diff (base…branch), the task spec and the check result, **never the implementer's summary**, and ends with a verdict block (`approve` | `changes`) plus findings. An approve without substantive findings text counts as `no-verdict` and is retried with another reviewer, so lazy approvals don't inflate the outcome record. That retry's exclusion of the first reviewer is a preference, not a wall: while at least one other qualifying reviewer is available — ready, or cooling for no more than `longCooling` (§8) — the exclusion holds and the retry waits for another reviewer; when none is, the excluded reviewer itself qualifies again, so a review never sits days behind another family's reset. The lift reaches the tier choice, the lease's candidates and the cooling hold alike, so the status's held line names the agent the job really waits for, and the `job_agent_picked` event records the lifted exclusion. The lift is spent once: a lifted retry that again ends with no verdict from the same agent parks the task at `needs_foreman`, its reason saying the only available reviewer twice gave no verdict. The family rule is never relaxed: an agent of the author's family never qualifies, whatever is available. **A review's tier and effort are its own.** Reading a diff usually takes less than writing it, so a review job asks for one tier below the task's effective tier by default (heavy → standard, standard → light, light stays light) at medium effort, whatever effort the escalation ladder (§8) has pushed the work to. The config keys `review.tier` (`below`, the default, or `same`) and `review.effort` (`low`, `medium`, `high` or `max`, default `medium`) set that default for the engine; a task's own `review_tier` (`light`, `standard`, `heavy`) and `review_effort`, set in `plan_create`, `plan_amend` (on an added task or in `retier`) and mirrored in the plan file, win over it as given: a task's `review_tier` is the tier asked for, not a step from the task's. Every review job uses them: the first review, a retry after an unusable answer and a resumed re-review alike. Work and fix jobs are unchanged. The review tier is what §8 treats as the tier asked for: the family rule, the retry exclusion and the long-cooling fallback apply on top of it, so a review tier with no available other-family reviewer climbs as a work tier does, and the `job_agent_picked` event records the tier asked and the tier served. `brigada status` shows a task's own `review_tier` and `review_effort` beside the task as `review:heavy` and `review@high`; the engine defaults are left unsaid. `changes` → a fix round (§3 rule) up to `review_rounds` (default 2), then a judgment event. **A re-review resumes the reviewer's session.** When a review asked for changes and a fix round answered them, the next review is queued in session mode on the agent that wrote that review, resuming that review's session (the session id is on the review job's result). The reviewer's session is not the task key's: the key's stays the author's, so the next fix round still resumes the author's, and the re-review is placed by its agent pin, not by the key's runner affinity. Its prompt (`internal/prompt`, beside the review template) says this is a re-review: the findings are the reviewer's own and are not repeated; it carries the fix round's summary (the one place a reviewer sees an author's account, to be checked against the diff, never trusted in place of it) and the check result verbatim; the runner writes the fix round's diff alone, the branch's commits since the head the previous review judged, into the diff file (the head is in the author job's result, set by the runner); and the verdict covers the whole change. The verdict block is the same contract. A fresh review on any qualifying reviewer runs instead, with the reason in the `task_reviewing` event, when: the previous reviewer's session id or the judged head is unknown; its agent is gone, broken, cooling beyond `longCooling` (§8), not offering review or failing the family rule against the round's author; or the task was restarted (a restart, a tier or effort step or an automatic retry starts a new attempt, whose first review is fresh). A re-review whose session the CLI cannot resume (`resume_failed`) is requeued as a fresh review and spends no retry. A review retry after an unusable answer, and a requeue after an unavailable reviewer, are fresh too and carry the full review prompt, not the re-review's. A resumed review shows in the history: `task_reviewing` carries the pick `resumed` and the agent, and the lease's `job_agent_picked` the same pick.

Family detection: the job record; for `brigada review --branch` without a job, the `Co-Authored-By` trailer. That standalone command creates a one-task plan of class `review`: the runner runs the repo's configured check, and there are no fix rounds unless you ask. Merging is brigada's by rule (§7.1): the land job squashes each approved task onto the target branch and pushes by the push gate, and `brigada land` (§7.1) is the hand-driven form, which stops short of the remote.

### 7.1 Landing approved work: the `land` job, and `brigada land` by hand

**Landing is a job.** When a task is `done` and approved and every dependency is landed, the engine creates a job of kind `land` for it, leased by a runner like any job (§12.3), with no worker: a runner that advertises git for the project's repo. In order, in a clone of the target branch under the runner's state directory: fetch the target and the task's latest result branch by exact name; squash the task's own diff (base to branch, three-way) as one commit with the message of "The commit message" below; run the project's default check on the result; then, by the push gate (§6.3), push the target, wait for the user, or stop and print the push. It runs where the runner's git credentials are, so the engine still does no git (product §5 rule 1) and a result stays a pushed branch. Landing is **continuous**: per task, not per plan, so a stack lands in dependency order as its tasks finish and the target moves with the plan; the plan's done report names what landed, what waits at a gate, and what the foreman holds. A queued or running land job is live work: the plan closes when the last one has its outcome, so a landing that fails parks its task and keeps the plan open, while a hold at the land gate has no job and lets the plan close under "waits at a gate". A land job that loses its runner too many times fails and parks its task with a land failure, as one the queue TTL fails does.

- **Conflict:** the job stops, pushes nothing, discards its clone's attempt, and parks the task at `needs_foreman` with the conflicting files. The foreman restarts it with a note (rebase onto the target's new head, resolve), as it restarts a failed task (§5.6); the worker resolves, the check and the review run again, and the task lands on its next approval. A rule never resolves a conflict and never picks a side.
- **The check fails on the landed result:** the same, with the check log as the job's artifact; nothing is pushed. (The case seen in dogfooding: two parallel branches adding the same migration number.)
- **The record:** the land job's result is the landing record, kept by the engine without a separate post: target, commit, check, pushed or waiting, the exact push command of gate_push never, and an after_land failure. `brigada history` shows it all, and the hand-driven command recognizes a landed task by the commit trailer.
- **Target:** `land_target` (§6.3), the default branch unless set; a staging branch keeps the default branch for the user's own merge.
- **`after_land`** (§6.3) runs after a push, or after the landing when the push gate is `never`.
- **Waiting at the push gate** (`gate_push = ask`): the landing's commit is pushed, fast-forward only, to `refs/brigada/land/<target>`, a ref outside `refs/heads` that holds the newest waiting landing with every earlier one beneath it. While that ref is ahead of the target, the next landing is squashed onto it instead of the target, so the waiting landings form one stack in landing order, a dependent on its dependency; a rejected push to the ref is retried once from a fresh fetch and squash, as a rejected push to the target is. The push phase that `brigada push approve` queues for each fetches the target and the ref, on whichever runner leases it, and pushes the recorded commit: no new squash. A commit the target already holds (a later landing of the stack pushed it) counts as pushed; a target that moved outside brigada refuses the fast-forward, and the task parks. Under `gate_push = never` the commit waits on the same ref and stacks the same way, so the recorded command — fetch the ref, push it to the target — is exact and runs from the user's own repository; the needs-you queue carries it, and keeps carrying it until the project is archived, for the engine never learns that the user ran it (§10).
- **Never:** force-push, touch another branch (the waiting ref is brigada's own and no branch), rewrite an existing commit, change the task's state away from `done`, or run with a foreman credential: the job is the engine's, created by a rule, and the foreman has no tool for it.

**By hand.** `brigada land` stays, sharing the squash and message code with the job: for `gate_push = never`, for a branch the user wants on their own machine, and for landing a task by hand. An engineer fetches each approved branch, squashes it onto the default branch, writes a message, reruns the tests and pushes, by hand, per task. `brigada land <task-id>... [--onto <local-branch>] [--repo URL] [--landed <task-id>]... [--no-check]` does the mechanical part and stops before the push. Two gaps remain: the runner does not record the approved head with the verdict (§16 item 10), so the head check is the design's stated fallback (land warns per task and goes on); and the land-note record is not written by the hand-driven command, as the engine has no endpoint for it. The engine adds one read, `GET /v1/tasks/{id}/land` (client and admin tokens only, never the foreman's), which returns the spec, dependencies, approval, the author's summary and family; the client runs every git command.

**Who merges.** The hand-driven land is a local convenience the user drives, in the user's own working repository. It writes commits on a local branch and nothing on the remote: the remote stays the user's, and the push is the user's command, which land prints. The foreman never calls it and it is in no MCP set (§12.2): it is a client command, authenticated as the user. Merging is brigada's by default, through the `land` job above, and the person's by rule: the gates and rules of §6.3 are the user's, enforced by the engine, and the foreman can pass none of them.

**What it does.** Run inside the project's repository, on the target branch: the project's default branch, or the local branch named with `--onto`, which must be checked out (land never switches branches; it says `git switch <branch>`). In order:
1. **Preflight, before anything is changed.** Every named task is checked; one failure refuses the whole call and names the task and the reason.
2. **Fetch refs only,** as `brigada diff` does (a fetch from `origin` of each ref by exact name, no tags, no prune, no checkout): each task's base ref, its latest result branch (`-r<n>` included) and the target's remote counterpart.
3. **Squash in dependency order,** one commit per task, on the target branch (below).
4. **Rerun the project's default check** (§13.1, §6.1) on the result, once, after the last commit, in the user's shell like any check (product §6, "what local gives up").
5. **Stop,** print what it did and the push command (`git push origin <branch>`), and exit. It never runs it.

**What it refuses.**
- a task that is not `done`, or is not approved: an `implement` task needs an `approve` verdict on its last review (§7); other classes carry no review and no branch worth squashing, so they are not landable;
- a result branch whose fetched head differs from the head the verdict approved (the runner records the pushed head with the result; where no head is recorded, land warns and goes on);
- a dirty working tree (tracked changes, or untracked files that are not ignored), or a merge, rebase, cherry-pick or revert in progress;
- a target branch that is behind or has diverged from its remote counterpart (pull first; being ahead is fine), or that is not the checked-out branch;
- a working directory whose `origin` does not canonicalize (§13.1 item 1) to the task's project, with `--repo` as the same escape `brigada diff` has;
- a dependency that is neither landed nor in the same call (below);
- no default check, unless `--no-check` is given, the same "never run unchecked" rule as §6.1; `--no-check` is shown in the final report.

**Dependencies and stacks.** Tasks are squashed in dependency order; among tasks with no order between them, in the order given. A task's diff is `git diff --binary <base>...<branch>` for **its own recorded base**, not the default branch, so for a task whose base was its dependency's branch (§6.1, repo and base ref) it is only that task's work.
- *Dependency in the same call:* squashed first, so the target already holds its content and the dependent's patch applies on top.
- *Dependency already landed:* land recognizes it by the `Brigada-Task: <id>` trailer on a commit in the target's history. A dependency landed by hand, or on another clone, carries no trailer, so the user says `--landed <id>`, which skips that task's preflight and is shown in the report.
- *Dependency neither:* refused, naming it, since squashing the dependent alone would apply a patch onto a tree that lacks what it was built on.
- If the dependency's branch moved after the dependent was cut (a later fix round), the dependent's patch may not apply cleanly; that is a conflict like any other.
- A task whose diff is empty makes no commit and is reported.

**Conflicts.** The patch is applied three-way. On a conflict land stops at that task, names the conflicting files, and leaves the tree as it is (conflict markers, index staged) for the user. It never resolves anything, never picks a side, never discards the tree. Commits already made for earlier tasks stay; the report gives the target's starting commit, so the user can return with `git reset --hard <sha>`, printed and never run. The prepared message for the stopped task is written to a file inside `.git` and its path printed, so the user resolves, runs `git commit -F <file>`, and reruns `brigada land` for the rest, which finds that task landed by its trailer. A git hook that rejects a commit stops the same way (land runs ordinary `git commit`, never `--no-verify`). A failing check undoes nothing: the commits stay, the report names the failure and prints no push command, and the exit code is non-zero.

**The commit message.** Built by the client from data it reads through the API, never from the branch's own commit messages. The worker may write the message itself: the result block's optional `commit_message` (§5.4), from the task's last author job, carries a subject and a body in the repo's own style, and the land job and `brigada land` use them — the subject its first line under the same 72-character cut, the body indented four spaces like the spec and summary parts, so no line of it can read as a trailer or a `#` comment. An absent, empty or subjectless `commit_message` falls back to the built message. Subject: the task title, one line, at most 72 characters (cut with an ellipsis). Body: a spec summary (the spec's first paragraph, at most 600 bytes) and the worker's summary (§5.4) from the task's last job, at most 2000 bytes. The whole message is at most 4096 bytes. A field over its bound is cut at a character boundary and marked `[truncated]`: unlike §5.9, truncation is right here, since the full text stays in `brigada logs` and the history (§9) and a commit message is a record, not a rule. Trailers:
- `Brigada-Task: <id>` and `Brigada-Branch: <branch>@<sha>`;
- `Co-Authored-By: <model> <address>` for the authoring model family, from the job record (the family detection of §7). When the family is unknown (no job record, or an agent whose family was never set) there is **no** `Co-Authored-By` trailer and `Brigada-Author: unknown` is added instead; land never invents an identity. A known family whose address brigada does not have gets the model name alone and is reported.

**The worker's summary is data.** It is model output: it goes into the message as plain text and is never executed, expanded or interpreted. The message reaches git through a file (`git commit -F`), never a shell string; control characters other than newline and tab are stripped, NUL and CR included; each line of the spec and summary parts is indented four spaces under a heading line, so no line of them can read as a trailer (`Co-Authored-By:`, `Signed-off-by:`, `Brigada-*:`) or as a `#` comment. Only land's own trailers sit in the trailer block. The commit's author and committer are the user's own git identity.

**What it never does.** Never pushes; never force-updates anything; never touches the remote's branches (no delete, no push, no `fetch --prune`); never rewrites commits that existed before the call; never changes the engine's task state, which stays `done`.

**The landing record.** The hand-driven `brigada land` writes no record itself, but the engine sees a landing made outside the land job: wherever the project's default branch is freshly fetched — the runner's foreman checkout refresh, on a headless turn or at attach — the runner scans the branch for `Brigada-Task: <id>` trailers and reports each to the engine (`POST /v1/landed`, runner or client token), which records it as the task's landing with the commit that carries the trailer. A task the land job landed is already recorded; either record counts, and the read is idempotent. This is what lets `brigada status`, the plan listing and the plan's done report tell "already merged" from "not yet landed".

## 8. Dispatcher

**Per-job usage.** Each job records the usage its own CLI invocation reports: input, output, cached input and reasoning tokens, and US dollars when supplied. Input means all input, cache reads included, and cached input is the cached part of it, so the columns mean the same for every adapter: Claude's result usage is counted once, with cache reads and creation added to its input; Codex input already includes the cached part; opencode reports input without cache reads, so the adapter adds them. Each job also records `model_calls`, the model requests the CLI reported: Claude's `num_turns`, one per Codex turn, one per opencode step and one per kimi assistant message with usage. Calls is the unit for plans that limit requests per time window. Codex turn usage and opencode step usage are summed. Missing or malformed counters stay unknown (NULL), distinct from reported zero. A fix round and a resumed session are separate jobs: totals are never carried or subtracted across jobs. Wall time is recorded with completion. Stats sum known counters per agent and class from every job, including work, fix and review, and show cost per success in dollars when any dollar cost is known, otherwise in tokens. Unknown jobs do not contribute to sums; no successes means no cost-per-success. These measurements do not steer dispatch.

- **Eligible:** the adapter supports the class; family rule for reviews; agent `ready` (not `broken`, not `cooling`); account not cooling; session affinity (a resumed session stays on its agent and runner — a continuing task's first work job (§6.1) is placed the same way a fix round is: session mode, pinned to the dep author's agent, its key's session row seeded with the dep's session id so the affinity holds the runner); the agent's tier is the task's effective tier, with the fallback below; for a review job it is the review tier: by default one tier below the task's effective tier, per §7, and then the same fallback.
- **Cap room:** an eligible agent is picked only if every concurrency cap on its path has room (§8.1). Caps shrink the set of eligible agents with room, so a task whose best agent is cap-blocked goes to the next-best agent with room; it waits in the queue only when no eligible agent has room, and that never parks it. **Parking** means no agent is eligible with caps ignored.
- **Score:** per (repo, class, agent): a success rate with a prior, where success = check passed and review approved within the rounds. Defaults for a cold start. `stats` shows it with its confidence.
- **Ranking.** Within the served tier, each eligible agent draws p from Beta(successes + 0.5, failures + 0.5), its outcome record for the job's (repo, class), and the agents rank by `weight / p`, lowest first, where weight is the configured `cost.<harness>/<model>` (default 1, §8.1). This is Thompson sampling with a cost: a thin record draws widely, so a weaker or newer agent keeps being tried without a separate exploration share, and a clearly better record beats a slightly cheaper agent most of the time. A weight of 0 ranks before every positive weight; among zero weights the higher p goes first. Exact ties break by a further draw, never by agent id alone. The draws come from the engine's injectable uniform source, so tests stay deterministic. Cap room then walks the ranked order and takes the first agent with room. A job pinned to an agent (a fix round) is not ranked, and the automatic restart's pick shares the same sampling. The decision record names the pick `sampled` and holds each candidate's weight and draw; a pinned lease draws nothing and is recorded as `pinned`. Sampling never sends a task to a lighter tier; only the last-resort fallback below may.
- **Quota:** limit-hit errors cool the whole account until its window resets; Codex's reset time is read from its own limit message (`try again at …` in the machine's local zone, or `try again in …`), and a reset beyond eight days is suspect and capped there; CodexBar's CLI JSON is an optional extra signal.
- **Health:** repeated failures, auth errors or a dead runner → `broken(reason)`. The failure streak counts terminal completions that failed on the agent whatever the job kind — work, fix, review or foreman; a failed setup (§5.7) or an infrastructure failure (§5.1) is the environment's or the runner's plumbing, not the agent's, and never advances the streak. The three reasons recover differently. `repeated failures` is self-healing: a few minutes after the agent was marked broken the runner, on the engine's instruction over the runner protocol (§12.3), runs a cheap probe of the agent's CLI — the same kind of check `brigada init` uses to see that the CLI answers — and a passing probe clears the broken state with an event; a failing one waits longer before the next probe, the delay doubling and capped. `auth` is never probed: it stays broken until the user fixes the login and `brigada agent reset`. `runner stale` clears the moment the runner is seen again (a register or a lease poll). A missing heartbeat while the engine itself was asleep proves nothing: the sweep's suspension rule (§13) restarts the stale window from the wake, so a runner that slept with the engine keeps its agents.
- Every decision is recorded with its reason ("why this agent").

**Tiers.** Each agent serves one tier, from brigada's tier table by model name, a segment-prefix and whole-segment table beside the family table (§7's detection): `opus` and `fable` segment prefixes and whole `pro`, `max`, `ultra` and `astra` segments are heavy; the `haiku` segment prefix and whole `mini`, `nano`, `flash`, `lite`, `highspeed`, `free` and `luna` segments are light; any other model is standard. The config override `tier.<harness>/<model>` (same shape as `cost.`, §8.1) corrects the table for every agent of that harness/model, as `cost.` does. Because the tier is an attribute of the agent, like effort, the outcome record keeps its key (repo, class, agent); records earned under one tier stay attached to the agent when an override changes its label. `stats` and `capacity` (§12.2) show the tier beside each agent.

- **Fallback** (cap-0 rule): a task whose tier has eligible agents that are all cap-blocked waits in the queue (§8.1): a cheap wait beats a heavier model. A cap that is merely full waits, but an agent whose model cap or account cap is exactly 0 can never run, so it counts as unavailable: a tier whose agents are all capped at 0 falls back as if it had no ready agent. A tier whose agents are all cooling for no more than an hour (`longCooling`, a constant of the engine, not a config key) waits too, held as the cooling hold holds a job (bounded by the reset time): only a reset within that hour is waited out, and heavy models drain the same windows faster. An agent cooling for longer, such as under a multi-day or even a 5-hour limit, has an end too far off to wait for and counts like a broken one. A tier with no registered agent, or whose agents are all broken (no end in sight) or cooling for more than an hour, climbs to the next tier up; from heavy, or when no higher tier has an agent, it steps down instead. This holds for work, fix and review jobs alike, with the family rule for reviews applied first: a review of a Claude-written task does not wait days for a Codex reviewer while a standard reviewer of another family is ready. When no tier has an available agent but some are cooling, the job waits in the tier whose agent resets first. A job pinned to its agent (a fix round on the author's session) is not moved and waits for it. The decision record names the tier asked for and the tier served.
- **Escalation:** a task climbs a ladder of effort, then tier. The task carries an effective effort beside its effective tier, starting as its own effort (possibly empty); the lease resolves the job's effort from the effective effort, then the agent's explicit effort, then medium. When a task's check or review rounds are spent, or a worker ends with the result-block status `failed` (§5.4), and the retry rules of §3 (the transient retry, the quota re-dispatch, the automatic restart) have declined or are spent, the engine first retries on the same tier with the effective effort one step up — low → medium → high, starting from the resolved effort, never stepping to max — with the event `task_effort_bumped` (old and new effort, the reason). Only when the effort is already high (or max) does it raise the effective tier one step, with the effective effort reset to the task's own, and the event `task_tier_bumped`. Each step queues a fresh attempt as the quota re-dispatch does (§3: the next `-r<n>` branch, the previous job's summary carried, counted toward the restart cap on every step); neither event wakes the foreman. A run that ended without a readable result block may be the runner's fault, so it takes the effort steps like any failure but never raises the tier: a no-result at high effort goes to the foreman with the reason. A job that failed for a transient reason (quota, auth, a lost runner) belongs to those retry rules, never to escalation. The task reaches the foreman (`needs_foreman`) only at heavy and high effort, or when its attempts are spent. A stalled worker still always goes to the foreman. The foreman may change the tier or effort again with `plan_amend`'s `retier`: a new effort sets the effective effort with it, and a tier change resets the effective effort to the task's own.
- **Review tier and effort.** A review job asks for the review tier and runs at the review effort, not the task's: the task's `review_tier` and `review_effort` if it has them, else the engine default of `review.tier` (`below` the task's effective tier, or `same`) and `review.effort` (default `medium`), as §7 describes. The tier choice, the candidates and the lease's effort resolution read them for every job of kind review, the retries and resumed re-reviews included; the escalation ladder above moves only the task's own effective tier and effort and never a review's. The long-cooling fallback and the retry exclusion work as for any job, on the review tier asked.
- **Effort** (§6.1) is per job: the runner passes the task's effort to the adapter, so two jobs on one agent may run at different levels. It is not a cap layer (§8.1).

### 8.1 Concurrency caps

**Layered caps.** A job may start only if every layer has room; the effective capacity is the minimum across the layers:

- **Runner:** max parallel jobs per runner, for the host's CPU, memory and parallel builds and tests. The runner advertises its own cap when it registers; the effective runner cap is the smaller of that and the config's.
- **Account:** max parallel jobs per adapter account, for the vendor's session and rate limits; parallel sessions also drain the 5-hour window faster.
- **Model** (optional): a per-model cap, such as 1 for a heavy model.
- **Plan:** max parallel tasks per plan, because tasks touching the same files end in merge conflicts. A task counts while it has a live job (`running`, `checking` or `reviewing`, §6.1).
- **Global:** an overall ceiling for the engine.

A task job (a task's first run, a fix round or a review) that cannot start because some layer is full waits in the queue, oldest first, and starts when a slot frees; it does not park (§3) and does not notify the user.

**The foreman is never starved.** Foreman turns count toward the runner, account and global caps (not the plan or model caps), and a pending foreman turn outranks every queued task job at each of those layers: the next slot that frees on its path goes to it. Its wait is therefore bounded by the running jobs' class time caps (§5.6). An attached chat (§4.2) is not a job, but it is a live session on the foreman's account: it counts toward that account's cap while held, without ever waiting for room, so the dispatcher starts no new task job there until there is room again.

Each agent also carries a **cost weight** (default 1), a relative cost the user sets, which the foreman sees through `capacity` (§12.2) when it chooses which tasks can wait for a cheaper agent. The dispatcher uses it too: agents of one tier rank by `weight / p` (§8), so a dearer agent is picked less often, and a weight of 0 makes an agent free, ranked before every paid one.

**Effort and caps.** A task's effort (§6.1) is not a layer: a `max` job and a `low` job on one agent share that agent's caps. A high effort drains the account's window faster per job.

**Defaults set by init.** Init asks one number, tasks at once (§13.1), and writes it as `caps.global` and the runner's `--max-parallel`; the account caps come from a per-harness default table (claude 3, codex 2, kimi 1, opencode 2), each clamped to that number and shown in init's plan block; `caps.plan` is set to 3. Unset `--max-parallel` still means one job at a time. `brigada config` shows the config file to edit afterwards; the engine reads caps when it starts.

**Config example.** Conservative per-adapter defaults are set in the engine's config file:

```
caps.global = 6
caps.plan = 3
# a runner may advertise its own (--max-parallel); the smaller wins
caps.runner = 4
# per account label
caps.account.claude = 3
caps.account.codex = 2
caps.account.kimi = 1
caps.model.<heavy-model> = 1
# cost weight per agent, default 1
cost.<harness>/<model> = 2
```

Comments go on their own line; the parser does not strip trailing comments.

### 8.2 Foreman headroom

The foreman's session uses quota on its own account, so task workers must not drain that account and leave the foreman `limited` mid-plan (§4.4). A task job — work, fix or review — on the foreman's account sees an account cap one lower than the configured cap, never below 0 (`max(cap − 1, 0)`), so one slot stays reserved for the foreman even while no foreman turn runs. At an account cap of 1 that is 0: task workers never run on the foreman's account. The rule is on by default and can be turned off in the config (`headroom`).

## 9. History

Everything is kept and readable.

- **Messages:** one table of conversation items per project: user ⇄ foreman turns (a user message, §4.2 item 3, is kept with author `user`), foreman tool calls and their results, worker task specs and results, questions and answers, reviews, notifications. A job's `discoveries` (§5.4) stay with that job's result message. `brigada history [--plan|--task]` shows them as one timeline.
- **Transcripts:** after every job, the runner uploads the session's full transcript (the CLI's own event log) to the engine as an artifact, linked from the job. The foreman's chat transcript is archived the same way after each attach and each headless turn.
- **Events:** an append-only event log is the backbone. Messages and transcripts reference events.
- Retention is configurable; the default keeps everything.

## 10. Notifications

Local OS notifications plus a "needs you" queue in `brigada status`: a plan, a landing or a push held by a rule at its gate (§6.3), user-directed questions, the foreman's limit, the foreman's budget out, a broken agent, a task parked with no eligible agent, a plan done. The queue holds only what a rule or the foreman gave the user; a landing or a push that went through is a report in the history, not an entry.

`notify.webhook` in the user config file adds one optional webhook URL — never `.brigada/project.yaml` or the KB, which others may read, for the URL may carry a token. The same moments the desktop notification fires are also one small JSON POST: project, kind, the banner's one-line text, the task and plan ids, the time. The JSON is plain, so ntfy, Slack or a Telegram bot relay can take it; there are no per-service adapters. Delivery is fire-and-forget: a short timeout bounds each attempt, a failed attempt is retried once, and a failing webhook is logged — never with the URL — and never blocks the engine: the posts leave the engine's tick on their own bounded queue, so a slow relay delays nothing but its own backlog. The URL appears nowhere else: not in the status, the history or an error.

## 11. Data model (SQLite, one file)

`projects` (canonical repo URL, default branch, settings with the provenance of each (§13.1), foreman harness and model) · `plans` · `tasks` (+ `task_deps`) · `jobs` (task, kind: `work`|`fix`|`review`|`foreman`|`land`, agent, mode, prompt, lease and fence, status, result, check result, last progress, transcript ref) · `sessions` (key, agent, runner, harness session id, state) · attach holds (§4.2) · `runners` · `agents` (runner, adapter, harness, model, family, account, classes, health, cooling until) · `outcomes` · `events` (append-only) · `messages` · `questions` · `tokens` (hashed) · `artifacts` (transcripts, check logs).

## 12. Interfaces

### 12.1 Engine API

JSON over HTTP; locally on a Unix socket, remotely over TLS. Bearer tokens with roles: `client`, `foreman` (scoped to its project), `runner`, `admin`. Groups: projects, plans (approve and reject are `client` or `admin` actions; a `foreman` credential cannot call them), tasks (create, amend, cancel, restart), questions (answer), foreman messages (a user message, §4.2 item 3: `client` and `admin` only, idempotent; a message identical to one the same token sent to the same project within the last minute is a duplicate — a double Enter, a shell retry — answered with the first one's id), events (long-poll and SSE), history, stats, budget, agents and runners, artifacts.

**Plan version.** A plan carries a version, 1 at creation, that every amendment moves (`plan_amend`, including a cancel-only one). `status` shows it for a plan awaiting approval, and `POST /v1/plans/{id}/approve|reject` take an optional body `{repo_url, version}`: a `repo_url` confines the plan to that project, and a `version` other than the plan's current one is refused whole with 409 `stale_plan`, applying nothing. The CLI sends neither and checks nothing; the coordinator's `plan_approve` and `plan_reject` require both.

**Idempotency.** The caller is often an LLM whose tool calls may repeat. `plan_create`, `plan_amend`, `task_restart`, `answer` and a foreman message (§4.2 item 3) take an idempotency key (client-supplied, or derived: task + round for restart and answer); a repeat returns the first call's result. The key is minted by the `brigada mcp` bridge per logical tool call (a hash of the call's content within the session), not left to the LLM; identical `plan_create` content within a short window also dedupes. Task jobs are keyed `task:<id>`: one live job per key makes duplicate job creation coalesce into the follow-up flag, which `status` shows.

**Credentials.** Foreman credentials are short-lived and scoped to one turn or one chat: a headless turn keeps the job-lease-scoped credential of §12.2, and an attached chat gets a hold-scoped foreman token, minted at attach, carried by the MCP config the client writes for the chat and revoked at detach, so the chat's tools die with it. No direct store access and the engine-as-mailbox rule stand.

### 12.2 MCP tools: three sets on one bridge

`brigada mcp` is one bridge with three tool sets. Authority comes from the credential the engine accepts, never from the flag: a selector only chooses which tools are listed.

**Project foreman set.** `plan_create` · `plan_amend` · `task_restart` · `task_cancel` · `answer` (a task worker's question) · `ask_user` · `events` (long-poll, for the attached session) · `status` · `stats` · `history` · `capacity`. It is scoped to one project and has no plan approval or rejection authority, and no land tool (§7.1): merging stays with the user. `ask_user` carries only intent or product questions that no rule answers; a decision a rule already makes is held by the engine, and the foreman never asks the user to release that hold. The same set serves a headless turn and an attached chat (§4.2): a turn's lease is its authority, an attached chat's hold-scoped token (§12.1); heartbeat and release are the bridge's or the client's own, not tools. `capacity` returns, per agent: its effective cap and the layer that sets it (§8.1; on the foreman's account, after headroom, §8.2), running jobs, quota state (`ready`, or `cooling` until a time, plus the percent used of the 5-hour and weekly windows when CodexBar data is available), cost weight, tier and the agent's configured effort, or `default` when its runner sets none. It also returns each layer's cap, use and queue depth: per runner, account and any capped model, per active plan of the foreman's project, and global. A queued task has no agent yet, so queue depth is reported per layer, not per agent. The MCP server is a `brigada mcp` stdio process started by the foreman's harness; it calls the engine API with the foreman token. The token is lease-scoped: the engine mints a short-lived one when it leases a foreman turn — only its hash is stored, the runner keeps the secret in memory alone — and revokes it when the turn ends, so a runner never holds a long-lived foreman token.

**Ordinary client set.** `brigada mcp --client` is the same bridge for any other harness acting for the user: `ask_foreman` (a user message, §4.2 item 3), `status`, `history`. It authenticates with a client token from the state directory and never holds a foreman token, so a harness can talk to the foreman and watch the work without a person relaying between the two. Every client token speaks with the user's voice, which is the point; the token file can hold several, each with its own label (one per device or harness) and revocable on its own, and the label travels with each message into the foreman's prompt and the history (§9), so it's clear which surface sent what. Any local process that can read the state directory, a task worker with a shell included, can use a client token; containers (backlog) are the answer.

**Coordinator set.** `brigada mcp --coordinator` is the client set plus `list_projects`, `plan_approve` and `plan_reject`, every tool taking the project's canonical repo URL (§4.6). It authenticates with a client token, never a foreman credential. Approval is an explicitly user-directed act with a visible confirmation (§4.6): the result "awaiting approval" is never itself a reason to approve.

**Selectors** are mutually exclusive: two together is a startup error.
- `--client`: the ordinary client set.
- `--coordinator`: the coordinator set. It never reads a foreman credential.
- A bare `brigada mcp --socket PATH` is what the runner starts for a headless foreman turn and what the client writes into an attached chat's MCP config (§4.2): it works with the foreman credential the holder hands it and refuses to start without one.

Selecting a flag mints nothing, and a selector that the credential in hand does not match is refused. A client token never appears in the foreman set, nor a foreman credential in the other two.

### 12.3 Runner protocol

**Usage completion.** Completion optionally carries `usage` with `input_tokens`, `output_tokens`, `cached_input_tokens`, `reasoning_tokens`, `model_calls` and `cost_usd`, plus `wall_seconds` for this job's elapsed wall time before delivery. Each usage field is optional. Older runners may omit usage and wall time; these remain NULL. Retries of a completion do not add usage again. Counters describe only the job's own CLI invocation, even for fix and resumed jobs, and do not steer dispatch.

`register` · `lease` (long-poll) · `heartbeat` (progress, last activity) · `complete` (result or error; an outcome of `stalled`/`time_cap` when the runner stopped the run itself, §5.6; check result; artifacts) · `release`. Fencing as described in the glossary.

## 13. Engine lifecycle

Single instance (a lock on the store); started by any `brigada` command when not running; shuts down after `idle_minutes` with no live jobs, attached sessions, pending wake-ups or unsent notifications (it flushes them first); crash or reboot recovery through lease expiry and fencing, then pending foreman wake-ups are re-evaluated.

**Suspension.** The engine and its runners sleep together: a laptop's sleep looks, to the sweep, like minutes or hours of wall clock in a single gap. The sweep therefore measures the wall-clock gap between its own ticks — the engine sweeps on the idle tick and before every call — and when the gap is far past the sweep interval (a few intervals, `suspensionFactor` in the code) it knows the engine itself was suspended. Then it restarts every wall-clock deadline from the wake instead of acting on it: lease expiry, the kind's wall-time cap (`last_leased`, the current lease's clock, shifts past the gap, so the sleep never counts against it), the runner-stale window, attach-hold expiry and the queue TTL. A deadline that lapsed during the gap proves nothing about a runner or a client that slept too. One `engine_suspended` event records the detection, naming the gap.

### 13.1 `brigada init`

One step sets a repo up. The GUIDE's §1 describes the questions: the foreman model and effort, worker models, tasks at once, then the check. Init has two phases: it probes and prints what it would do (no writes), then applies on confirmation. Nothing is silent.

1. **Identity.** Read the repo's `origin` and normalize it to the **canonical repo URL**, the project's name. With no `origin`, or several remotes and none named `origin`, ask; a local-only repo is rejected (product §5 rule 4). Scp-like SSH (`git@host:org/repo`), `ssh://` and HTTPS URLs of the same host and path give one project. Userinfo is dropped and never stored, logged or shown, so a token in an HTTPS URL stays out of everything. The host is lowercased; the path is not, because paths can be case-sensitive. One trailing `.git` and trailing slashes are removed. The scheme is dropped, and a port is kept only when it is not the scheme's default, so a non-default SSH port stays a different project from that host's HTTPS URL unless the user confirms they are the same. Anything the string alone cannot settle is ambiguous (a leading-slash or `~` scp path, an SSH config alias that is not a hostname) and init asks; it never guesses. The canonical form is `host[:port]/path`. Each runner still fetches with its own URL and credentials (§5.1).
2. **Probe harnesses.** Find installed harness CLIs and check whether each is signed in, by the harness's own cheapest status check or by asking the user. Detected login state is local and never goes in the shared file. A binary name proves neither a subscription nor a model family: the family comes from the model an agent is configured with, and the user confirms which models an account serves.
3. **Agents and review families.** With zero usable agents init refuses, starts nothing and writes nothing. It counts distinct model *families* among review-capable agents, not CLIs: two CLIs on one family are one. With fewer than two it does not report ready. It stops the normal setup with an actionable warning (sign in to a harness of another family, or add a model of one) and continues only on the user's explicit acknowledgement of a **limited setup** (`--accept-limited`). A limited setup never disables cross-family review (§7): reviews it cannot serve are named in `status` and park as designed, and init never presents such a setup as fully ready.
4. **Foreman.** Pick the foreman harness and model from the usable agents (it needs headless resume, §4.1). The pick is shown and overridable.
5. **Defaults.** Suggest a default check and a worker tool scope from the repo's build files (for example `go.mod`, `package.json`, `Cargo.toml`, a Makefile target). They are shown, overridable, and never executed during discovery. They are repo-relative commands (product §5 rule 7). The suggested scope is the narrowest that runs that check (§5.2); init never silently grants a wider one, and a scope the user sets replaces the default as §5.2 says.
6. **Start.** Start the engine on demand and the runner with the detected agents.
7. **Write the project file only.** Init writes no harness wiring: in a repository it writes `.brigada/project.yaml` and nothing else. A rerun, and `brigada remove`, strip the wiring an older init left — the bridge in `.mcp.json`, the hooks in private `.claude/settings.local.json` and the old `brigada hold` hooks in shared `.claude/settings.json`, the `.codex/config.toml` table, `.brigada/foreman.md` with its router block in `AGENTS.md` and `CLAUDE.md`'s import section, and the foreman skill — editing only brigada's own entries, so a file the user never touched comes back byte for byte; the git exclude line for the private settings goes too. `--no-wiring` skips the strip in a repository (in a parent folder it still skips the coordinator's wiring, below). No secret is written to any repo file, and init never commits or pushes.

**Tiers, effort and tasks at once.** With tiers (§6.1, §8) the user chooses which models may work: the foreman picks a tier and an effort per task, and the engine picks the agent. The questions are:

1. **The foreman.** After the sign-in probes, a numbered menu of every model the signed-in claude and codex CLIs list (Claude's aliases, Codex's `debug models` catalog, models of unknown family left out), then its effort: the effort menu, asked once, for the foreman only. Enter picks the first usable resume-capable model, claude before codex. A foreman model whose harness is not used for tasks is registered as an agent with no classes, so it serves foreman turns and nothing else. The runner accepts `classes=none`, and the engine exempts foreman turns from the class filter: the harness-and-model pair is their constraint, so this agent takes no task job.
2. **Workers.** Per installed CLI, the sign-in check; Claude and Codex then ask `Use <cli>'s models for tasks (<models>)? [Y/n]:` in place of a model menu (Enter is yes on the first run; the `Use kimi? [y/N]:` and `Use opencode? [y/N]:` questions are asked when sign-in is unconfirmed): every model the CLI lists with a family brigada can tell becomes an agent at its tier (§8); unknown-family models stay out, because the family drives review routing. Kimi keeps its writing question. opencode keeps a menu, because its list spans providers, and the menu accepts several numbers. There is no effort question for workers.
3. **Tasks at once.** One number, default `min(4, max(1, cores/2))`, explained with the machine's core count and the per-account caps it implies (§8.1); it becomes `caps.global` and the runner's `--max-parallel`.
4. **The check.**

The plan block gains a tier column in the agents table, the foreman's effort, and an "at once" line with the per-account caps. Every prompt keeps the four parts: what is chosen, why, the valid answers, what Enter does. A rerun defaults to the saved choices. `--agent` keeps working, once per model, so `--yes` runs name each agent; `--foreman HARNESS/MODEL@EFFORT` and `--parallel N` answer steps 1 and 3 without a question; omitting `@EFFORT` leaves the interactive effort question.

**Parent folder (the coordinator).** Init in a folder that is not a repo scans only its direct children by default. It does not descend into a repo (submodules are not projects), does not follow symlinks out, and skips hidden directories. It prints a visible list: path, canonical URL, new or known, and a skip reason (no `origin`, ambiguous). The user selects, and only the selection is registered. Two children with the same canonical URL are one project. It wires the coordinator set in the folder's project scope and writes nothing into the child repos.

`brigada init` outside a repository scans the direct children (a symlink, or a `.git` that is a symlink, is listed as skipped and never followed; a directory counts as a repository only when its own top level is itself), prints `path  canonical URL  new|known|unknown (engine not running)` or `skipped: <reason>`, and registers what the user picks at the prompt (`1,3`, `all`, blank for none) or everything new with `--all`. A second child with a canonical URL already seen is a duplicate, not a second project. New projects take the foreman of `--foreman harness/model`, else that of a project the engine already has; with neither, init refuses before writing. It writes the folder's `.mcp.json` entry `brigada-coordinator` (`brigada mcp --coordinator`, additive and idempotent, a damaged file left alone) and the brigada-owned skill `.claude/skills/brigada-coordinator/SKILL.md` (coordinator instructions, `foreman.CoordinatorInstructionsVersion`, golden-tested). It adds no hook and no permission entry, so `plan_approve` and `plan_reject` stay on the harness's own "ask". It starts no runner: agents and a default check come from `brigada init` inside a repository.

**`.brigada/project.yaml`.** The portable, versioned, shareable repository configuration, committed by the user so it travels to colleagues and machines. The cost: one brigada-owned file in the user's repo. Only nonsecret repo-level intent goes in it: the canonical repo identity, the default check, the worker-tool policy, `instructions_file` (a repo-relative path to the project's worker instruction text, read by the client at import, §5.9), and project defaults and preferences. Accounts, credentials and tokens, local executable and state paths, detected login state and machine overrides never do; they stay local. Init writes it additively and reviewably (a new file, or a diff the user approves) and never commits or pushes it. The client reads the file and sends its content over the API, so the engine never reads a repo path (product §5 rule 1).

Schema 1 of the file holds `schema: 1`, `repo` (the canonical identity, written in canonical form and checked against the origin), `default_check`, `worker_tools` (the `tools=` spelling), `approval_max_tasks`, `approval_classes`, `approval_protected_paths`, the gates and land rules of §6.3 (`gate_plan`, `gate_land`, `gate_push`, `approval_tiers`, `approval_restarted`, `land_target`, `after_land` — stored, shown and enforced: `gate_plan: ask` holds every plan at the plan gate, the land-gate rules hold a task's landing, the land job obeys `gate_push` and runs `after_land`, §7.1), the environment step's `setup`, `setup_cache_key_files` and `setup_timeout_minutes` (§5.7), the default `extra_repos` (§5.8), and the foreman's `foreman_rotate_tokens` (§4.2), and nothing else; an unknown key or schema version is refused with the key named. `brigada project import [--repo URL] [--file PATH] [--yes]` reads the file in the client and sends its bytes; the store records the hash of the last import and, per key, the value it set. A key whose stored value is still that import's counts as imported; any other stored value is a local override, and `project set` always makes a key local. `project show` prints `(default)`, `(set)` for a local override, or `(imported <hash>)`. `status` flags a file whose hash differs from the last import, reading the file in the client and changing nothing.

The store holds the *effective runtime settings*, each with its provenance. Precedence, highest first: a local override the user set on this machine; the last imported file value; the built-in default. Detected suggestions only propose. Import is explicit (init, or a sync command), never a side effect of `git pull`, and `status` flags a file that differs from the store. On import, a file change over a store value that is still the previous import's applies. Over a local override it does not: the conflict is shown with both values for the user to resolve. A file against a hand-set store value on first import shows the diff and asks. An unknown schema version is refused. Neither the file nor the store wins silently, and the engine never writes the file back after init.

## 16. Open questions

1. Gemini CLI's headless resume support.
