# Changelog

The format of this file follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
The project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [1.0.0-rc.2] - 2026-10-23

Second release candidate of 1.0.0. Since rc.1: with `land_target` set, new tasks start from the land target and may depend on landed tasks of other plans (#59); a plan review's `changes` verdict parks the plan at `needs_foreman` and its findings are kept whole (#66, #70); a Z.ai limit reset is read in its own zone (#54); the foreman's report is no longer cut at 500 bytes (#52); a landed commit's subject comes from the worker's commit message (#48) and its `Co-Authored-By` trailer carries every shipped family's address (#74); the foreman's task size guide and the plan review's size check (#50); `brigada init` writes `.brigada/operator.md`, the guide for your own coding agent (#73); CI runs the race tests in shards. The changes are listed under 1.0.0 below.

## [1.0.0-rc.1] - 2026-10-22

First release candidate of 1.0.0. The changes are listed under 1.0.0 below.

## [1.0.0] - Unreleased

### Changed

- The interactive foreman is `brigada attach`: it joins the brigada-owned foreman session, so your chat and the headless turns are one transcript, and it runs in the foreman's reading checkout with your own harness config and user-scope MCP servers; `attach --model M --effort E` overrides the project's foreman choice for that chat alone. Mode A — your own harness session as the foreman, wired by `brigada init` — is retired: `brigada init` writes `.brigada/project.yaml` and `.brigada/operator.md` and nothing else, and a rerun or `brigada remove` strips an older init's wiring. The `hold` command, `brigada mcp --foreman`, the settings `hold_idle_minutes`, `hold_max_minutes` and `interactive_quiet_minutes`, and the tools `hold_acquire`, `hold_yield` and `decision_note` are gone; `brigada hold yield` and `hold confirm` remain as no-ops so old hooks do not block. A repository whose `.mcp.json` still carries an older init's `brigada` entry must drop it (`brigada remove`, or a rerun of `brigada init`), or the two `brigada` servers clash.
- A fix round whose CLI fails for a transient reason — a quota error, an authentication error, a server error, a lost runner — is retried once instead of parking the task (issue #41): the author's session resumes on the author's agent when it can still take it, else the round runs fresh on another agent of the tier with the round's feedback (the check output or the review findings) in its prompt. A second transient failure, or a failure that is not transient, parks the task for the foreman.
- With `land_target` set, a new task's work starts from the land target instead of the default branch (issue #59): its worktree is built on that branch and its land job diffs against that base, both at `plan_create` and for a task `plan_amend` adds. A plan task may also depend, by id, on a landed task of another plan of the same project when its work is on the land target — done and pushed there: such a dep counts as done from the start, no edge waits on it, and one landed on another branch, not pushed, not landed, or belonging to another project is refused with the reason.
- The `Co-Authored-By` trailer of a landed task carries the vendor's conventional noreply address for all five shipped model families — anthropic, openai, moonshot, deepseek and zhipu — instead of anthropic alone; any other family (google, alibaba, meta, mistral, xiaomi, meituan, nvidia, or opencode's unknown default) still gets the model name alone and the missing address is still reported (design §7.1).

### Fixed

- Credentials leaked to the code a task runs and to the files it writes: workers, setup commands and checks inherited the runner's `GH_TOKEN`, `SSH_AUTH_SOCK`, cloud keys and registry tokens (design §5.8 promised a scrub that nothing configured). They now run without those, and setup commands and checks also without brigada's own variables, keeping `PATH`, `HOME` and the build caches. The runner refuses to commit and push a new env file, key, `credentials*`, `.netrc` or other hidden file a worker left behind, failing the job with the files named; its git commands run with `GIT_TERMINAL_PROMPT=0`; URLs in its errors and in the plan mirror's lose a lone token as well as a password. Token-file and config parse errors give the line number and not the line; the `history` tool fences its text in `<event>` delimiters like `events`; the webhook requires https (http only on a loopback host), follows no redirect, and leaves a failed check's output out of its text; `notify-send` takes `--` before the message; snapshots, run records and artifact blobs are written owner-only.
- A task landed by hand, or by a cherry-pick, stayed parked: the trailer scan recorded the landing but left a task parked by a land conflict or a rejected push at needs_foreman with its needs-you lines, and a landing still waiting at the push gate kept showing `waits to push`. The scan now returns such a task to done, marks its waiting landing pushed and releases its dependents; a waiting `refs/brigada/land/<target>` ref the target no longer fast-forwards to is dropped by the next landing; and a push rejected for a task already recorded landed raises nothing.
- opencode and dsh workers could not run `go test` or `git status`: opencode denied all bash and now allows the commands of the project's `worker_tools` scope (the Go default scope when unset; a review still none), and dsh workers now get a `GOCACHE` under the temp directory and `GIT_OPTIONAL_LOCKS=0`, so the sandbox no longer refuses the build cache or git's index lock.
- A failure before an agent's CLI started counted against that agent's health (issue #39): a worker, reviewer or foreman command that could not be started, or a worktree that could not be built from its base ref, is the environment's failure, never the agent's. These failures now complete the job with the error kind `infra`, as a failed fetch already does, so they never count toward the failure streak, and a work job behind one is retried like a fetch failure instead of charging the agent.
- The wall-time hard cap measured from a job's first lease, so a job that lost its lease and was re-leased could be cut short partway into its next lease (issue #36); the cap now measures from the current lease, so a re-leased job gets the whole cap again.
- claude and opencode workers could not read a task's extra repositories (§5.8): their read and search tools were denied outside the worktree, and their scoped Bash could not echo the `BRIGADA_REPO_<NAME>` path. The runner now grants each checkout's absolute path as a read dir (claude `--add-dir`, opencode `external_directory` allow) and names the paths in the job's prompt.
- dsh jobs failed at start with "unknown option '--patch'"; the adapter now passes the launcher's `--patch` before the app's `--json`.
- A land job diffed a task whose recorded base was its dependency's branch against that branch even after the dependency landed as a squash and the task's branch was rebuilt on the target, so the patch carried every change the target made since the stale merge-base: bogus conflicts in files the task never touched, different ones each attempt. The land diff now starts a branch that no longer descends from its recorded base at the merge-base with the base it lands on, so the patch holds the task's own changes alone.
- A dependent could still fail to land with "the task's diff no longer applies onto main" when its branch descended from its dependency's old lineage while its tree was the target's content plus its own work — a restart's or a continuing task's rebuild — and the dependency had landed, by hand or as a squash, its `Brigada-Task` trailer on the land target: the three-dot diff from the dependency's branch started at the stale merge-base and conflicted in the very files the task touched. When the base's task has landed — the trailer read on the history the squash lands on — and the branch's tree still holds that history's whole content (the trivial three-way merge of the two over their merge-base resolves to the branch's own tree), the landing patches with the tree diff of the branch against that base, so the patch holds the task's own change alone; a branch that lacks the base's later changes — another task landed in between and the branch was never rebuilt — keeps its three-dot diff, which lands its own change without reverting them.

### Added

- A real version for every install path (issue #79): when the release build has not set `brigada`'s version with `-ldflags -X`, the binary now resolves it from its build info — the tag `go install …@v1.0.0` records, without its leading `v`, else `0.0.0-dev+<rev12>` (the first 12 characters of the git commit) with `-modified` appended for a dirty tree, else `0.0.0-dev`; the pseudo-version of `go install …@<sha>` and the `(devel)` of a plain `go build` are not taken as the version. Release binaries keep printing the tag without its leading `v`, and the README's install section says what each path prints.

- `brigada init` writes `.brigada/operator.md` (issue #73): a generated, harness-agnostic guide for your own coding agent, the operator. It covers how to ask the foreman (`brigada ask -`), how to watch (`status`, `history --task`, `history --job`, `diff --stat`), what to do after a landing, how to recover after an outage, and what stays yours alone (plan, land and push approval, `--and-stop-asking`, tags and releases, rule changes). A rerun overwrites it, `--no-wiring` does not skip it, `brigada remove` deletes it, and init prints one line pointing at it. Init still never touches `AGENTS.md` or `CLAUDE.md`. The README now opens with the first five minutes (install, init, tell your agent "ask brigada to fix #12", watch `brigada top`, approve what the needs-you queue holds), and `brigada attach` moves under "Talking to the foreman yourself".

- A plan review's `changes` verdict with a round left parks the plan at a new `needs_foreman` plan state (issue #66): the plan waits with its findings in the "needs you" queue — `brigada status` shows it as `needs_foreman (round 1)` with the findings as the entry's reason — no work queued and nothing retried on its own, surviving an engine restart. The foreman answers with `plan_amend` (allowed from the parked state; added and edited tasks go to round 2, an amendment that cancels or retiers only lets the plan proceed) or with the new `plan_accept` MCP tool (`plan` and a required `reason`), which accepts the plan as reviewed and runs the same evaluation a spent round's verdict does — the plan starts or waits for your yes, and the reason is recorded in its history. The second-round `changes` verdict still proceeds as before, and a review that gave no verdict still keeps the plan `reviewing`.
- Plan review findings are kept whole under their own 16 KB bound instead of a note's 500 bytes (issue #70): a multi-KB verdict reaches the foreman's wake and round 2's prompt intact, while the short views — the status plan line and the needs-you entry — cut at render time and end with `… (full: brigada history --job N)` pointing at the review job's history.

- NOTICE and a generated THIRD_PARTY_NOTICES.md carry the attribution the release binaries owe their embedded dependencies: `internal/tools/licenses` runs go-licenses v1.6.0 over `./cmd/brigada`'s dependency tree and writes every module's name, version, licence and full licence text, refusing anything not compatible with brigada's Apache-2.0 licence; `sh internal/tools/licenses/regenerate.sh` regenerates the file. The go-licenses CLI itself cannot be run here (its `go run` needs an approval the worker sandbox denies, and its v1.6.0 report carries neither version nor licence text), so the pinned tool lives in a nested module — not a trivial script — and a root-module test runs its golden test, which the nested module alone would escape.

- A new plan, and an amendment of an active plan that adds or respecifies tasks, is reviewed before its tasks are queued: an agent of another family checks the plan against the code and the docs, and at most two rounds send findings to the foreman. `plan_review` turns the review off; `plan_review.tier` and `plan_review.effort` set the reviewer (§7.2).
- The approval rule that stands on by default is the plan budget: `approval_budget` holds a whole number of tokens, a `$` amount, or both joined with `+` (for example `2000000+$5`), a plan's spend is the usage the engine records per job — input plus output tokens, and dollars when the CLI reported them — summed over the plan's jobs, and when the spend passes the budget the engine holds the plan's new jobs: every task that would newly start, a freed dependent or an amendment's addition alike, parks at the plan gate with a needs-you line naming the rule and the spend, while work already running goes on. Only the claude CLI reports dollars; codex, opencode, kimi and dsh report tokens, so on a subscription harness without a price the budget counts tokens and a `$` side never trips. `approval_max_tasks` defaults to `0`, off: set a count to bring the count rule back (`gate_plan: ask` still holds every plan).

- `brigada agents` compares the models your CLIs list (claude, codex, opencode) with the runner's agents file and prints the unregistered ones, each with its name-based tier and account, and the registered models a CLI no longer lists (issue #49); `brigada agents add <harness>/<model> [--classes ...] [--effort ...]` appends one validated line and keeps every other line. `brigada status` and `brigada top` show a one-line hint when unregistered models exist, from a listing cached for 12 hours. Nothing registers a model automatically.
- Landing is a job (§7.1): a task that is done, approved and whose dependencies are landed is squashed by a runner onto `land_target` as one commit, the default check reruns on the result, and the push follows the push gate — `auto` pushes, `ask` (the default) waits for `brigada push approve`, `never` leaves the push to you: the commit waits on the remote's `refs/brigada/land/<target>` and the needs-you queue carries the exact command, runnable from your own repository. Landing is per task, so a stack lands in dependency order; a conflict or a failed check on the landed result parks the task for the foreman, nothing pushed. `after_land` runs after a successful land; its failure is reported — in the landing record and `brigada history`, where the commit, the push state, the push command and the after_land failure all show — and never undone.
- `land_ready` gates the landing (issue #87): a repo-relative command path inside the repository (for example `scripts/land-ready.sh`) the land job runs in its landing clone before anything lands, and the push phase runs again before it pushes, under the environment of a check and the check timeout. Exit 0 lands; exit 1 holds the landing on the command's first output line — nothing squashed, pushed or recorded; any other exit, a command that could not start, or a timeout is not ready, and the landing is requeued on the growing not-before backoff (5 s to a 2-minute cap) with no failure and no restart spent, the next try time and the last exit kept on the task for `brigada status`. The repository ships `scripts/land-ready.sh`, a `land_ready` command that reads the latest `gh run list` run on `brigada/landed` — exit 0 when it succeeded or the branch has no runs, 1 when it failed (its URL the first output line), 2 while queued or in progress or when `gh` fails. It is not enabled and not executable as committed: run `chmod +x scripts/land-ready.sh` and `git add --chmod=+x scripts/land-ready.sh` once, then `brigada project set land_ready scripts/land-ready.sh`.
- A task landed outside the land job — a hand squash, or `brigada land` in your clone — is no longer invisible to the engine: whenever the runner refreshes the default branch (a headless foreman turn, or `brigada attach`), it scans for `Brigada-Task: <id>` trailers and records each task it finds as landed (`source: trailer`), so `brigada status` and the plan's done report can tell "already merged" from "not yet landed", and the read is idempotent with a task the land job landed.
- Gates and rules (§6.3): the loop is brigada's and you stop it with flat keys in `.brigada/project.yaml` — `gate_plan`, `gate_land`, `gate_push`, `approval_tiers`, `approval_restarted` and `land_target` join `approval_max_tasks`, `approval_classes` and `approval_protected_paths`, which now also holds at the land gate. Held landings and pushes appear in the needs-you queue; `brigada land approve <task>` and `brigada land reject <task>` decide a held landing, `brigada push approve` releases every waiting push. The foreman has no tool to pass a gate.
- The foreman session rotates when it grows large: after a turn that read more input tokens (input plus cached) than the project's `foreman_rotate_tokens` (default 400000, `0` = never), the next headless turn or attach starts a fresh session and logs `foreman_session_rotated`. The fresh session's first prompt carries a bounded digest of the active plans, what needs you and the latest history. Set it with `brigada project set` or in `.brigada/project.yaml`.
- Mode B: `brigada init` in a parent folder registers several repositories under one coordinator session (`brigada-coordinator` in `.mcp.json`).
- Plans with dependencies, created and amended by the foreman, mirrored to the `brigada/plans` branch.
- Workers run in git worktrees on their own branches; the project's check runs after every result; fix rounds, and restarts with notes (`task_restart`).
- Cross-family review of each `implement` change, and `brigada review --branch` for any branch.
- Dispatch by outcome record and cost weight within a tier (Thompson sampling); concurrency caps per runner, account, model and plan.
- Quota cooling per account, until the vendor's reset time when the CLI gives one.
- An agent broken by repeated failures recovers by itself: a few minutes after it was marked broken the runner probes its CLI, a passing probe clears it, and a failing one backs off with a growing, capped delay; an auth failure still waits for `brigada agent reset`.
- Tiers (`light`, `standard`, `heavy`) and effort per task, with an escalation ladder that raises effort first, then the tier.
- A task may `continue` one of its deps: its first work job resumes the dep author's session on its own agent, saving the cold start; fresh whenever the session or its agent is not available.
- `brigada stats`: usage per job and cost per success.
- `brigada land`, the hand-driven form of the land job: squashes approved tasks onto your branch locally; it never pushes.
- Adapters for Claude Code, Codex, Kimi and opencode.
- `brigada status`, `brigada history`, `brigada logs`, `brigada diff` and desktop notifications.
- `docs/COMPATIBILITY.md` states what 1.0 promises until 2.0.
