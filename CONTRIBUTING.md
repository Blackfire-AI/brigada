# Contributing

Thanks for helping with brigada. Coding agents working on this repository
should also read [AGENTS.md](AGENTS.md), which holds the agent-specific notes.

## Setup

You need Go at the version in `go.mod`, and `git`.

    git clone https://github.com/Blackfire-AI/brigada
    cd brigada
    go build ./cmd/brigada

To only check that it compiles, run `go build -o /dev/null ./cmd/brigada`.

Read these before you change behaviour:

- `docs/design.md`: how brigada works inside, an index of the section files under `docs/design/`;
- `docs/product.md`: what it is for;
- `docs/glossary.md`: the terms used in the code and docs;
- `docs/GUIDE.md`: how to use it.

## Checks

CI runs these. Run them before you push:

    test -z "$(gofmt -l .)"
    go run ./internal/tools/guard
    go vet ./...
    go test -count=1 ./...
    CGO_ENABLED=1 go test -race -count=1 ./...
    (cd internal/tools/licenses && go test -count=1 .)

`guard` scans for private addresses and similar leaks. Never commit
secrets, tokens, private hostnames or private IP addresses.

`THIRD_PARTY_NOTICES.md` is generated by the nested module in
`internal/tools/licenses`, which has its own `go.mod`. That module keeps
go-licenses out of the main `go.mod` and makes the notices reproducible:
the generator runs go-licenses once per platform the release workflow
builds and unions the module sets, so the file is identical on every
host.
The `./...` patterns do not reach it, so the root `go test` runs its
golden test through `TestThirdPartyNoticesFresh`. Locally that test
skips when go-licenses, the module cache or the network is unavailable;
in CI (`CI=true`) it fails instead. After a dependency change, regenerate
the notices from the nested module:

    cd internal/tools/licenses
    go test -count=1 -run TestThirdPartyNoticesGolden -update .

## Pull requests

- For anything non-trivial, open an issue first and agree on the approach.
- Keep one change per PR.
- Put tests beside the code they test.
- Update the docs in the same PR when behaviour changes.
- Add no new dependency without a reason. Say why in the PR.

## Review

Every change is reviewed by another model: one from a different family
than its author's when one is available (`review.family=prefer`), else
another agent of the author's family, or the author's own agent in a
fresh session. `brigada review --branch <branch>`. A maintainer also
reviews every change before it merges.

## Commits

Use Conventional Commits with a scope, as in `git log`:
`fix(init): ...`, `feat(engine): ...`, `docs: ...`. The subject says what
the change does, in plain words. A commit that completes an issue ends
its body with a line of its own, `Closes #N`, before any trailers; one
that does part of it says `Refs #N`.

## Releasing

Maintainers tag a version and push the tag:

```sh
git tag v1.0.0-rc.1
git push origin v1.0.0-rc.1
```

A tag with a suffix such as `-rc.1` is published as a prerelease and does not update Homebrew. A release tag without a suffix also updates `Formula/brigada.rb` in [Blackfire-AI/homebrew-tap](https://github.com/Blackfire-AI/homebrew-tap). The maintainer creates that repository and configures the `HOMEBREW_TAP_TOKEN` secret with write access to its contents before releasing.

The `release` workflow builds `brigada-<os>-<arch>` binaries (darwin and linux, amd64 and arm64) with the tag as the version, plus a `.tar.gz` of each and `SHA256SUMS`, and attaches them to a new GitHub release. For tags without a suffix, it then generates the complete Homebrew formula from the release checksums and commits and pushes it to the tap. Verify `brew audit` by hand after the release. `brigada version` prints the tag without its leading `v`; a source build prints `0.0.0-dev+<rev12>` (see [the installation guide](docs/GUIDE.md#1-install-and-brigada-init)).
